# 제품 구조

[문서 홈](../README.md)

negaflow는 macOS와 Windows용 앱입니다. 필름 이미지를 가져오거나 스캔한 뒤 반전, 현상, GrainMend, 출력, 보존을 거칩니다. 모든 편집은 원본과 분리해 둡니다.

> [!IMPORTANT]
> 원본, 편집 기록, 캐시, 출력 파일은 서로 다른 자료입니다. 캐시를 잃어도 원본이나 편집 기록을 잃어서는 안 되며, 필요한 결과를 다시 만들 수 없으면 내보내기는 실패합니다.

## 바뀌지 않는 안전 규칙

1. 원본 이미지와 타사 사이드카는 자동으로 덮어쓰지 않습니다.
2. 라이브러리에서 제거하는 것과 원본을 휴지통으로 옮기는 것은 별개의 동작입니다.
3. 스캐너 화면에는 플러그인이 보고한 것만 나옵니다.
4. 데모 스캐너는 직접 선택할 때만 씁니다.
5. 편집한 결과를 다시 만들 수 없을 때 원본을 대신 내보내지 않습니다.
6. 오래 걸리는 작업은 결과를 적용하기 직전에 프레임, 편집 버전, 세션을 다시 확인합니다.
7. 캐시는 원본과 편집 기록에서 다시 만들 수 있어야 합니다.
8. 프로파일, 출력 묶음, 아카이브는 필요한 검사를 통과한 뒤에만 게시합니다.

## 모듈

`negaflowApp`과 `negaflowCLI`는 모두 `Chromabase`와 `ScannerKit`을 씁니다. `Chromabase`는 이미지와 메타데이터를 다루고 `ScannerKit`은 외부 스캐너 플러그인과 통신합니다.

### `Chromabase`

Chroma Engine과 이미지 처리의 핵심입니다.

- 이미지 읽기와 방향 처리
- 필름 베이스 측정
- 네거티브와 포지티브 현상
- 톤, 색, 국소 보정
- 필름, 룩, 스캐너 프로파일
- GrainMend RGB와 IR
- 히스토그램과 색 측정
- 출력 인코딩과 메타데이터

자세한 내용:

- [Chroma Engine](../product/CHROMA_ENGINE.md)
- [GrainMend](../product/GRAINMEND.md)

### `ScannerKit`

외부 플러그인을 잇는 규약을 맡습니다.

- 스캐너 ID와 기능
- 요청과 응답 JSON
- 외부 프로세스 실행, 제한 시간, 취소
- 플러그인의 소유자, 권한, 승인, 해시
- 임시 출력을 확인한 뒤 최종 파일 게시
- 스캔 세션과 작업 이력
- 직접 켜야 하는 데모 스캐너

SANE 구현은 별도 GPL 프로젝트 [`negaflow-scanner-sane`](https://github.com/habinsong/negaflow-scanner-sane)에 있습니다. 앱과 플러그인은 JSON과 CLI로만 통신합니다.

### `negaflowCLI`

GUI와 같은 엔진과 `ScannerKit`을 씁니다.

- 스캐너 찾기, 기능 확인, 스캔
- 여러 이미지 현상
- 스캐너 프로파일 목록
- GrainMend `defect-bench`
- IT8과 스캐너 상대 비교
- 자체 점검과 JSON 자동화

### `negaflowApp`

SwiftUI와 AppKit으로 만든 사용자 인터페이스입니다.

- 라이브러리, 현상, 인화, 캔버스
- 스캔, GrainMend, 내보내기
- 버전, 설정, 단축키
- 카탈로그, 캐시, 백업, 보존 아카이브
- 제품 버전을 공용 버전 리소스에서 가져오는 현지화된 정보 창

## 사용자 흐름

1. 가져오기 또는 스캔.
2. 라이브러리 정리.
3. 필름 종류와 베이스 지정.
4. Chroma Engine에서 현상하거나 GrainMend로 복원하거나 버전과 가상 사본으로 가지를 칩니다.
5. 확인하고 인화하거나 이미지 파일, 사이드카, 렌더 기록으로 또는 보존 아카이브로 내보냅니다.

각 단계는 원본을 건드리지 않고 카탈로그와 편집 기록에 더합니다.

## 입력과 원본

### 파일 가져오기

기본 입력 경로입니다. TIFF, JPEG, PNG와 macOS Image I/O가 읽을 수 있는 카메라 RAW를 다룹니다. 내장 ICC와 방향을 읽고 원본 ID를 카탈로그에 넣습니다.

### 스캔

설치된 플러그인은 아래 기능을 보고할 수 있습니다.

- 해상도와 비트 심도
- 스캔 영역과 미리보기
- 노출
- IR
- 배치와 홀더 동작

앱은 모델명 표로 기능을 지어내지 않습니다. 스캔이 끝나면 플러그인이 실제로 적용한 설정과 출력 파일을 다시 확인합니다.

### 원본 ID

파일 경로만으로는 원본을 식별할 수 없습니다. 지금의 규약에 필요한 값, 곧 파일 관측, 바이트 수, 수정 시각, SHA-256, 영구 북마크를 보관합니다.

파일이 옮겨졌을 때 경로가 바뀌는 것은 사용자가 직접 다시 연결하거나 북마크 복구에 성공한 경우뿐입니다.

## 카탈로그

주 저장소는 `library.sqlite`입니다. 이전의 `library.json`은 확인된 옛 자료를 가져오거나 다른 컴퓨터로 옮길 수 있는 백업을 쓸 때 씁니다. 두 저장소를 동시에 갱신하는 일은 없습니다.

SQLite에 들어가는 것:

- 프레임과 원본
- 롤, 폴더, 컬렉션, 검색
- 순서와 스캔 작업
- 현상 값과 버전별 편집 기록

들어가지 않는 것:

- 원본 픽셀
- 썸네일과 미리보기
- GrainMend 캐시

### JSON에서 옮기기

1. 기존 JSON의 스키마와 상태를 확인합니다.
2. 복구용 복사본을 남깁니다.
3. 트랜잭션 하나로 임시 SQLite에 씁니다.
4. 옮기기 전후의 카탈로그를 비교합니다.
5. SQLite 무결성과 앱의 안전 조건을 확인합니다.
6. 모두 맞을 때만 주 저장소를 바꿉니다.

실패한 JSON을 빈 카탈로그로 취급하지 않습니다. 수치는 [카탈로그 저장 구조](CATALOG_STORAGE.md)에 있습니다.

## 라이브러리

정리 방법:

- 폴더, 롤, 수동 컬렉션, 스마트 컬렉션, 저장된 검색, 스택
- 별점, 선택과 제외, 컬러 라벨
- 그리드, 비교, 서베이
- 중복 후보 검토

폴더 보기에서 폴더마다 펼침 삼각형, 폴더, 이름, 개수, 현상 프로세스, 타깃, 적용이 있는 띠가 나옵니다. 띠는 그 아래 썸네일을 접습니다. 접힌 폴더는 사이드바의 파일 목록과 따로 실행 사이에 기억됩니다.

폴더 보기는 그리드 하나를 쓰며 폴더마다 섹션이 되고 띠가 섹션 머리글이 됩니다. 이 구조를 유지하세요. 폴더마다 별도 그리드를 쌓으면 레이아웃이 보이는 폴더 전체의 높이를 계산하고 카드를 한꺼번에 만들어야 하지만, 그리드 하나는 화면에 들어올 때 한 행씩 카드를 만듭니다. 사진이 수백 장이어도 스크롤이 매끄러운 이유입니다.

여러 가상 사본이 원본 하나를 공유할 수 있습니다. 삭제하기 전에 원본에 대한 참조를 확인합니다. 라이브러리에서 제거하는 것은 카탈로그의 참조만 바꾸며 휴지통으로 옮기는 것은 별개의 동작입니다.

외부 디스크의 연결이 끊겨도 편집은 보존됩니다. 원본은 오프라인으로 표시되고 파일 단위나 폴더 단위로 다시 연결합니다. ID가 기대한 것과 다르면 자동으로 바꿔 끼우지 않습니다.

등록된 실제 원본 폴더마다 파일 시스템 감시자가 하나씩 있습니다. 이벤트를 잠깐 모은 뒤 바뀐 폴더만 다시 훑습니다. Finder가 원본을 옮기거나 이름을 바꿔도 북마크 기반 재연결이 카탈로그 폴더 ID를 보존하고, 새로 생긴 직접 하위 이미지는 폴링이나 라이브러리 전체 재검색 없이 가져옵니다.

## 현상과 GrainMend

프레임마다 아래를 갖습니다.

- 원본 ID와 필름 종류
- 필름 베이스
- 현상 값
- GrainMend 편집 기록
- 버전 기록
- 내보내기 상태

조정하는 동안은 낮은 해상도의 미리보기를 씁니다. 완성된 결과는 프레임 ID와 편집 버전이 현재 선택과 여전히 맞을 때만 화면에 도달합니다.

다른 사진을 고르면 편집 대기 없이 정착 렌더링을 시작합니다. macOS에서는 이렇습니다.

- 카메라 RAW 네거티브가 정착하면 다음에 보이는 RAW를 백그라운드에서 디코딩할 수 있습니다. 이웃 하나만, 기존 마스터 캐시(최대 160MiB) 안에서 준비합니다. 편집, 다른 선택, 메모리 압박이 오면 그 작업을 취소하고, 이미 준비 중인 사진을 고르면 그 디코딩을 공유합니다.
- 차가운 카메라 RAW 선택은 센서 데이터를 한 번만 풉니다. 모자이크가 허용하면 정식 디모자이크가 끝나기 전에 임시 카메라 RGB 미리보기가 나타납니다. 마스터 캐시는 메모리 압박 동안 꺼지고, 프레임을 내보내면 그 RAW 마스터도 버립니다.
- 차가운 TIFF 선택은 디코딩한 원본 하나를 인터랙티브 미리보기와 정착 미리보기가 공유하고 GPU에서 축소합니다. DNG를 포함한 Apple RAW 미리보기는 두 패스에 `CIRAWFilter` 하나를 유지합니다.
- 보정한 RAW TIFF는 편집할 때마다가 아니라 픽셀 버퍼가 메모리를 떠날 때 씁니다. 디스크 정리는 한도 안에서 최근 파일을 남기고, 쓰는 중인 파일은 보호하며, 다음 실행에서 이전 세션이 남긴 캐시를 지웁니다. 편집 레시피는 사이드카에 남습니다.

Windows에서는 JPEG 썸네일이 LRU 바이트 예산을 쓰고 BGRA 미리보기가 관리되는 표시 예산의 나머지를 쓰며, 메모리 압박이 심하면 놀고 있는 JPEG를 버립니다. D3D 스테이징 버퍼에는 캐시 한도가 있고 메모리 부족 신호, 내보내기 완료, 장치 재설정이 이를 해제합니다.

내보내기는 화면의 미리보기 비트맵을 저장하지 않습니다. 원본과 고정해 둔 편집 값에서 전체 해상도 이미지를 다시 만듭니다.

GrainMend는 자동, 가이드, 브러시, 복제 도장, IR을 순서가 있는 목록으로 보관합니다. 캐시는 파생 파일입니다. 원본과 편집 기록에서 결과를 다시 만들 수 없으면 내보내기는 실패합니다.

자세한 내용은 [GrainMend](../product/GRAINMEND.md)에 있습니다.

## 버전

- 기록과 스냅샷: 현상 상태를 직접 기록해 두고 비교하거나 되돌아갑니다.
- 가상 사본: 원본 파일을 복제하지 않고 편집의 다른 가지를 둡니다.
- 복사·붙여넣기: 톤, 색, 디테일, 지오메트리 같은 범위를 골라 붙여넣습니다. 원본 좌표가 필요한 마스크는 안전 조건을 확인합니다.

## 내보내기

시작할 때 아래 값을 한 묶음으로 고정합니다.

- 원본 ID
- 현상과 GrainMend 편집 기록
- 스캐너 프로파일의 바이트와 SHA-256
- 출력 설정과 메타데이터 정책
- 파일 이름과 위치

내보내기를 멈췄다가 다시 시작해도 같은 묶음을 씁니다.

### 출력 파일이 여럿일 때

내보내기 한 번에 JPEG/TIFF, 사이드카, XMP, `-main-flat`이 함께 나올 수 있습니다.

1. 위치와 이름 충돌을 먼저 확인합니다.
2. 모든 파일을 임시 폴더에 씁니다.
3. 이미지를 다시 열어 픽셀 크기를 확인합니다.
4. 바이트 수와 SHA-256을 계산합니다.
5. 사이드카와 렌더 기록을 씁니다.
6. 커밋 기록을 남깁니다.
7. 묶음 전체를 최종 위치로 옮깁니다.
8. 실패하면 롤백하거나 다음 실행 때 정리합니다.

일부 파일만 있는 상태를 성공으로 표시하지 않습니다.

### 렌더 기록 v3

아래 사이의 SHA-256 관계를 기록합니다.

- 원본 바이트
- 실제로 쓴 렌더 입력
- 현상과 GrainMend 기록
- 스캐너 프로파일
- 디코더와 렌더러 버전
- 출력 바이트, 픽셀 크기, 형식

전자 서명도 인증서도 없으므로 C2PA Content Credentials가 아닙니다. 자세한 내용은 [렌더 기록](../reference/RENDER_MANIFEST.md)에 있습니다.

## 인화와 소프트 프루프

지원하는 레이아웃:

- 단일 이미지
- 콘택트 시트
- 사진 패키지
- 사용자 패키지
- 시아노타입
- 유리 건판
- 젤라틴 실버
- 워터마크

단일 이미지와 고전 레이아웃 셋은 선택한 사진마다 세로로 쌓인 한 페이지를 만듭니다. 콘택트 시트, 사진 패키지, 사용자 패키지는 대신 완성된 페이지 수를 보고하고 내보냅니다. 사진 39장이면 6 × 7 콘택트 시트 한 페이지, 4장짜리 사진 패키지 10페이지, 기본 사용자 패키지 한 페이지, 또는 개별 파일 39개가 됩니다.

패키지 미리보기는 있는 썸네일과 현상 이미지를 재사용하고 없을 때만 작은 빠른 미리보기를 만듭니다. 최종 내보내기는 메타데이터로 위치를 계산하고, 칸마다 필요한 픽셀만 현상하며, 서로 다른 원본을 2~4개씩 한꺼번에 준비하고, 페이지를 쓸 때까지 Core Image 그래프를 이어 두며, 페이지당 원본 래스터 예산 512MiB를 지킵니다.

패키지의 모든 배치는 자신에게 배정된 프레임을 따릅니다. 프린터 출력 ICC는 레이아웃이 끝난 뒤 완성된 최종 페이지에 한 번 적용하므로 반복 배치와 여러 원본을 섞은 패키지가 같은 출력 규약을 씁니다. 이 ICC는 라이브러리나 현상 미리보기를 바꾸지 않으며 원본 스캔 TIFF나 `-main-flat`에는 프린터 프로파일을 붙이지 않습니다.

유효한 RGB 프린터 ICC가 없으면 다른 프로파일로 대신하지 않습니다. 고른 프로파일의 바이트와 SHA-256이 출력 기록에 들어갑니다.

## 보존 아카이브

`.negaflowarchive`에 들어가는 것:

- 이식 가능한 카탈로그 JSON
- 원본 파일
- IR 원본
- 필요한 GrainMend 기록
- 가상 사본과 그들이 공유하는 원본의 관계

썸네일, 미리보기, GrainMend 캐시, 내보낸 파일은 다시 만들 수 있어서 넣지 않습니다. 아카이브는 SHA-256 목록이 있는 RFC 8493 BagIt 구조를 쓰며, 묶음을 최종 위치로 옮기기 전에 모든 파일과 관계를 확인합니다.

- [라이브러리 보존 아카이브](LIBRARY_ARCHIVE.md)
- [RFC 8493](https://www.rfc-editor.org/info/rfc8493/)
- [PREMIS](https://www.loc.gov/standards/premis/)

장기 보존에는 다른 매체, 외부 보관본, 정기적인 해시 확인도 필요합니다.

## 스캐너 플러그인 안전

플러그인을 찾으면 아래를 확인합니다.

- 현재 사용자가 소유하는지
- 그룹이나 다른 사용자가 쓸 수 있는지
- 심볼릭 링크인지
- 목록과 실행 파일의 ID와 SHA-256
- 승인한 ID가 지금 눈앞의 ID와 같은지

파일이 바뀌었으면 이전 승인은 다시 쓰지 않습니다.

프로토콜 v2는 요청 ID와 순번을 쓰고 최종 결과가 정확히 하나여야 합니다. 출력 크기에는 상한이 있고, 시간 초과나 취소 뒤에는 프로세스와 파이프를 정리합니다.

플러그인은 최종 위치에 스스로 파일을 게시하지 않습니다. 앱이 임시 위치를 넘겨주고, 형식, 크기, ID, 실제로 적용된 설정을 확인한 뒤 파일을 앱의 저장소로 옮깁니다.

전체 규약은 [스캐너 플러그인 구조](SCANNER_PLUGINS.md)에 있습니다.

## 성능의 경계

이미지:

- 공유하는 `CIContext` 하나
- 필요할 때 계산하는 이미지 그래프
- 전체 해상도 출력과 분리한 낮은 해상도 조정
- 취소, 그리고 오래된 결과 거부
- 영역, 타일, 패치 단위로 처리하는 GrainMend
- 메모리 압박 시 캐시 버리기

카탈로그:

- SQLite 트랜잭션과 엔티티별 행
- 복제를 통한 백업
- 무결성 검사
- 5만 프레임에서 측정

지금은 시작할 때 카탈로그 전체를 메모리에 올립니다. 같은 Mac에서 SQLite를 읽는 데 약 7.4초가 걸렸고 JSON과 비슷합니다. 인덱스로 필요한 행만 읽는 것이 다음 단계입니다.

저장소는 큰 퇴보를 잡으려고 넓은 성능 한계를 둡니다. 지원하는 모든 Mac에서의 반응성을 보장하지는 않습니다.

- 다른 Mac에서의 성능
