# macOS 측에 요청 (3차) — 마지막 한 단계: `CIVibrance`

2차 요청(프록시 실측 + f32 덤프) 덕분에 축소 커널을 찾아 넣었고, 8100 은 여섯 지점이 정확히
일치합니다. V700 도 G 는 +0.2 레벨(8비트)까지 좁혔습니다.

남은 것은 **한 단계**입니다. 그리고 그 단계는 Windows 쪽에서 더 좁힐 수 없습니다 —
`CIVibrance` 는 Apple 내장 필터라 커널 소스가 공개돼 있지 않기 때문입니다.

## 왜 여기라고 단정하는가 (측정 근거)

`GT-X900_frame_4.tiff`, `a-default-main-srgb` 기준입니다.

**1. base 는 대입으로 배제했습니다.** 맥이 잰 base `(0.338134765625, 0.293212890625,
0.233398437500)` 을 Windows 에 그대로 넣었더니 R median 이 45654 → 45670, **+16** 만
움직였습니다. 잔차 +762 는 그대로 남습니다.

**2. 반전 직후까지는 R 이 1 레벨 미만으로 같습니다.** Windows 실측
`dmin=(0.3377,0.2921,0.2321)`, `dmaxNorm=(0.7243,0.9647,0.9648)` 을 맥 로그와 견주면
정규화 밀도 차이는 R 에서 Δd = +0.0000183 입니다(dmin 이 낮아 어두워지는 몫과 dmaxNorm 이
낮아 밝아지는 몫이 R 에서 상쇄됩니다). 인화 응답 기울기와 sRGB 인코딩 기울기를 곱하면
**16비트 0.8 레벨**입니다. G 는 53, B 는 74 레벨입니다.

**3. vibrance 를 끄고 재 보니 그 단계가 잔차와 같은 크기입니다.**

| | Windows vib 없음 | Windows vib 0.252 | macOS vib 0.259 |
| --- | ---: | ---: | ---: |
| R median | 46051 | 45654 | 44908 |
| G median | 47885 | 47946 | 47896 |
| B median | 49171 | 49500 | 49865 |
| R min | 239 | 0 | 132 |
| B min | 107 | 0 | 49 |

2번의 기준선 보정을 넣고 amount 1.0 으로 환산하면:

| 채널 | Windows | macOS | macOS/Windows |
| --- | ---: | ---: | ---: |
| R | −1575 | −4409 | **2.80** |
| G | +242 | +247 | **1.02** |
| B | +1306 | +2965 | **2.27** |

**가운데 채널은 2% 안에서 맞는데 양끝 채널만 두세 배 갈립니다.** `amount` 자체의 차이
(0.252 대 0.259)로는 R 에서 16 레벨밖에 설명되지 않습니다. 수식이 다른 것입니다.

Windows 는 아래 수식을 씁니다(`src/Native/imaging/vibrance_math.h`).

```cpp
chroma = clamp(max(r,g,b) - min(r,g,b), 0, 1)
factor = 1 + amount * (1 - chroma)
L      = 0.2126 r + 0.7152 g + 0.0722 b
out    = L + (in - L) * factor
```

`CIVibrance` 의 실제 사상을 모르므로 이 이상은 추측이 됩니다. 이 조사에서 방향만 보고 세운
가설 여덟 개가 전부 측정에서 떨어졌기 때문에, 추측으로 고치지 않겠습니다.

## 요청 A — `CIVibrance` 입출력 격자 (필수·결정적)

수식이 아니라 **사상**만 있으면 됩니다. 알려진 RGB 격자를 넣고 나온 값을 주십시오.

만들 이미지: 폭 128, 높이 39 (4,992 화소), `RGBAf`, **linear sRGB**. 앞 4,913 화소에
17³ 격자를 채우고 나머지는 0 으로 둡니다.

```swift
let W = 128, H = 39
var input = [Float](repeating: 0, count: W * H * 4)
for i in 0..<4913 {
    input[i * 4 + 0] = Float(i / 289) / 16.0        // R
    input[i * 4 + 1] = Float((i / 17) % 17) / 16.0  // G
    input[i * 4 + 2] = Float(i % 17) / 16.0         // B
    input[i * 4 + 3] = 1.0
}
```

이 버퍼로 `CIImage` 를 만들고, **현상 파이프라인이 쓰는 것과 같은 working color space
(linearSRGB) 와 같은 컨텍스트**로 아래 amount 마다 `CIVibrance` 를 걸어 `RGBAf` 로 렌더한 뒤
그대로 파일에 쓰십시오.

| amount | 파일 이름 |
| --- | --- |
| 0.000 | `civibrance-a0.000-128x39.f32` |
| 0.100 | `civibrance-a0.100-128x39.f32` |
| 0.252 | `civibrance-a0.252-128x39.f32` |
| 0.259 | `civibrance-a0.259-128x39.f32` |
| 0.500 | `civibrance-a0.500-128x39.f32` |

`amount = 0` 을 함께 주시는 이유는 필터가 항등인지(그리고 렌더 경로가 값을 건드리지 않는지)
확인하기 위해서입니다. `0.252` 와 `0.259` 두 개를 다 주시면 amount 방향의 기울기까지
잡힙니다.

크기는 한 파일당 4,992 × 4 × 4 = **79,872 바이트**입니다.

## 요청 B — 실제 프레임으로 검증 (강력 권장)

A 로 사상을 맞춘 뒤, 그것이 진짜 사진에서도 맞는지 봐야 합니다. 격자에 맞추고 사진에서
틀리면 격자에 맞춘 것뿐입니다.

같은 `GT-X900_frame_4.tiff` 를 현상하면서 **vibrance 직전과 직후**의 이미지를 각각 320 폭
축소본으로 렌더해 `RGBAf` 로 덤프해 주십시오. 2차 때 주신 `NEGA_DUMP_PROXY` 와 같은 방식이면
됩니다.

| 시점 | 파일 이름 |
| --- | --- |
| `applyDensityEncoding` 직후 (vibrance 전) | `frame4-preview-320x488.f32` |
| `applyMutedSceneVibrance` 직후 | `frame4-postvib-320x488.f32` |

한 파일당 320 × 488 × 4 × 4 = **2,498,560 바이트**입니다(2차 때와 같은 크기).

## 요청 C — 160 폭 채도 프록시 (선택)

`sceneMeanSaturation` 이 재는 값이 Windows 0.1561, macOS 0.1538 로 **1.5%** 다릅니다.
320 폭 프록시 때와 같은 방법으로 닫을 수 있습니다 — `sceneMeanSaturation` 안의 축소본
(160 × 244)을 `RGBAf` 로 한 번 덤프해 주십시오.

| 파일 이름 | 크기 |
| --- | --- |
| `frame4-satproxy-160x244.f32` | 624,640 바이트 |

이건 잔차의 3% 짜리 2차 항이라 A·B 보다 급하지 않습니다.

## 확인차 — 값의 의미

- 격자 값은 **linear** 입니다(sRGB 인코딩 전). 파이프라인이 vibrance 를 거는 지점과 같은
  좌표계입니다.
- 알파는 1.0 으로 채웠습니다. 2차에서 확인했듯 알파는 변수가 아닙니다.
- 리틀엔디언 `Float32` 로 읽겠습니다(2차 프록시와 같은 규약, 그때 아홉 지점 0.000% 로
  재현했습니다).
