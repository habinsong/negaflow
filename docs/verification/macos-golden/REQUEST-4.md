# macOS 측에 요청 (4차) — CIVibrance 격자를 촘촘하게

3차 자료로 많이 나아갔습니다. 먼저 그 자료에서 **무엇이 나왔는지** 알려 드립니다. 다음
요청의 근거이기도 하고, 맥 쪽에서도 쓸모가 있을 것 같아서입니다.

## 3차 자료에서 나온 것

**1. `CIVibrance` 는 화소마다 정확히 아핀입니다.**

각 화소에서 세 채널을 `out = α·in + β` 로 맞추면 잔차가 **7.5 × 10⁻⁸** 입니다(4,913점 전부,
amount 0.259 와 0.500 둘 다). float32 반올림 수준이므로, 이 필터는

```
out = A + (in − A) · f
```

로 완전히 기술됩니다. 화소마다 정하는 것은 **스칼라 하나** 뿐입니다.

**2. 그 앵커 `A` 는 산술 평균 (R+G+B)/3 입니다.**

| 앵커 후보 | \|A − 후보\| 최대 | 중앙값 |
| --- | ---: | ---: |
| **(R+G+B)/3** | **0.0004** | **0.0000** |
| 0.2126R+0.7152G+0.0722B (Rec.709) | 0.3821 | 0.1074 |
| (max+min)/2 | 0.1669 | 0.0416 |

Windows 구현이 Rec.709 휘도를 앵커로 쓰고 있었습니다. 그쪽이 보내 주신 표본
(0.25,0.75,0.125) 에서 G 방향이 갈린 이유가 이것입니다.

**3. 배율 `f` 는 한 변수의 함수가 아닙니다.** 같은 값을 갖는 화소끼리 `f` 의 퍼짐을 보면
채도 0.122, 크로마 0.111, (채도,명도) 0.095, **(채도,명도,색상) 0.033** 입니다. 색상이
들어가야 줄어듭니다 — 문서에 적힌 "피부색 보호" 와 맞습니다. 그래서 수식을 지어내지 않고
**잰 사상을 그대로 구현**하기로 했습니다.

**4. amount 방향은 `g = (f−1)/a` 로 보간하면 잘 맞습니다.** `f@0.259` 를 0.100·0.500 에서
예측했을 때, `f` 를 직접 선형보간하면 RMS 0.0235 인데 `g` 를 보간하면 **0.0034** 입니다.

**5. 17³ 표로 실제 프레임을 재현해 봤습니다.** 요청 B 로 주신 vibrance 전/후가 독립 시험
자료였습니다.

| 방법 | 최대 | RMS (16비트 레벨) |
| --- | ---: | ---: |
| 지금 Windows 수식 | 2071 | **707** |
| 9³ 표 | 1622 | 437 |
| **17³ 표** | 887 | **137** |

격자를 반으로 촘촘히 할 때마다 RMS 가 698 → 437 → 137 입니다. 삼선형의 h² 수렴과 맞습니다.

## 요청 A — 33³ 격자, 규칙적인 amount 사다리 (필수)

3차와 **같은 형식**입니다. 격자만 33³ 으로, amount 는 파이프라인이 실제로 내는 범위
(0 … 0.5)를 고르게 덮도록 해 주십시오.

격자 규약(3차와 같은 꼴, 크기만 다름):

```
N = 33*33*33 = 35937
i → (R, G, B) = (i / 1089, (i / 33) % 33, i % 33) / 32,  alpha = 1
```

담을 이미지: **폭 256 × 높이 141 = 36,096 화소**, `RGBAf`, linear sRGB. 앞 35,937 개가 격자,
나머지는 0. 파일당 **577,536 바이트**입니다.

| amount | 파일 이름 |
| --- | --- |
| 0.05 | `civibrance33-a0.050-256x141.f32` |
| 0.10 | `civibrance33-a0.100-256x141.f32` |
| 0.15 | `civibrance33-a0.150-256x141.f32` |
| 0.20 | `civibrance33-a0.200-256x141.f32` |
| 0.25 | `civibrance33-a0.250-256x141.f32` |
| 0.30 | `civibrance33-a0.300-256x141.f32` |
| 0.35 | `civibrance33-a0.350-256x141.f32` |
| 0.40 | `civibrance33-a0.400-256x141.f32` |
| 0.45 | `civibrance33-a0.450-256x141.f32` |
| 0.50 | `civibrance33-a0.500-256x141.f32` |

입력 격자도 한 번 같이 주시면 인덱스 규약을 다시 만들 필요가 없습니다
(`civibrance33-input-256x141.f32`).

열 판 합쳐 약 **5.8 MB** 입니다.

`amount` 는 파이프라인에서 `min(0.5, max(0, (0.24 − meanSat) × 3))` 이라 0.5 를 넘지 않고,
0.01 이하에서는 단계 자체를 건너뜁니다. 그래서 0.05 아래는 필요 없습니다.

## 요청 B — 65³ 한 판 (정확도 확인용, 권장)

33³ 로 충분한지를 **33³ 자신으로 판정하면 안 됩니다.** amount 하나만 65³ 으로 주시면 독립
자료로 잴 수 있습니다.

```
N = 65*65*65 = 274625
i → (R, G, B) = (i / 4225, (i / 65) % 65, i % 65) / 64,  alpha = 1
```

담을 이미지: **폭 640 × 높이 430 = 275,200 화소** → **4,403,200 바이트**.

| amount | 파일 이름 |
| --- | --- |
| 0.25 | `civibrance65-a0.250-640x430.f32` |

## 요청 C — 실제 프레임 한 쌍 더 (권장)

요청 B(3차)로 주신 `frame4-preview` / `frame4-postvib` 한 쌍은 이제 **표를 맞추는 데** 쓰게
됩니다. 맞춘 표를 검증하려면 **다른 사진** 한 쌍이 필요합니다 — 같은 사진으로 맞추고 같은
사진으로 검증하면 그 사진에 맞춘 것입니다.

8100 프레임 아무거나 한 장으로, 같은 방식(320 폭, vibrance 전/후)이면 됩니다. 채도가 다른
장면일수록 좋습니다(amount 가 달라지므로).

| 시점 | 파일 이름 |
| --- | --- |
| `applyDensityEncoding` 직후 | `frame8100-preview-320xNNN.f32` |
| `applyMutedSceneVibrance` 직후 | `frame8100-postvib-320xNNN.f32` |

높이와 그 실행의 `[vib] meanSat=… amount=…` 로그를 함께 적어 주십시오.

## 참고 — 알려 주신 리스크에 대해

- **격자 사이 보간**: 33³ + 65³ 검증으로 닫으려 합니다. 위 표가 그 계획의 근거입니다.
- **`sceneMeanSaturation` 이 inset 없이 전체 화소를 쓰고 알파가 1 미만인 가장자리가 섞이는
  것**: 알려 주셔서 감사합니다. 요청 C(3차)의 160 × 244 프록시로 그 축소본 자체를 먼저 맞춘
  뒤에 채도를 견주겠습니다 — 알파 차이를 모르고 견주면 원인을 축소기에 잘못 씌웠을
  것입니다.
- **CIVibrance 의 내부 색공간**: 파이프라인과 같은 컨텍스트로 렌더된 값이므로, 표로 옮기는
  한 내부 색공간을 몰라도 됩니다. 위 1·2번이 그 근거입니다.
