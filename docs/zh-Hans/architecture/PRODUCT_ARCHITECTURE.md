# 产品结构

[文档首页](../README.md)

negaflow 是 macOS 和 Windows 上的应用。你导入或扫描胶片图像，然后经过反相、显影、GrainMend、输出和保存。每一次编辑都与原始文件分开保存。

> [!IMPORTANT]
> 原始文件、编辑历史、缓存和输出文件是不同的东西。丢失缓存不能导致丢失原始文件或编辑历史，所需的结果无法重建时，导出会失败。

## 始终不变的安全规则

1. 原始图像和第三方旁注文件，绝不自动覆盖。
2. 从图库中移除，与把原始文件移到废纸篓，是两个独立的操作。
3. 扫描仪界面只显示插件报告的内容。
4. 演示扫描仪只在你明确选择时使用。
5. 编辑后的结果无法重建时，不会用原始文件代替导出。
6. 耗时较长的任务在应用结果之前，会立即重新检查画幅、编辑版本和会话。
7. 缓存必须能从原始文件和编辑历史重建。
8. 配置文件、输出包和归档，只在通过所需检查之后才发布。

## 模块

`negaflowApp` 和 `negaflowCLI` 都使用 `Chromabase` 和 `ScannerKit`。`Chromabase` 处理图像和元数据，`ScannerKit` 与外部扫描仪插件通信。

### `Chromabase`

Chroma Engine 与图像处理核心。

- 读取图像与处理方向
- 片基测量
- 负片与正片显影
- 影调、色彩与局部调整
- 胶片、风格与扫描仪配置文件
- GrainMend 的 RGB 与 IR
- 直方图与色彩测量
- 输出编码与元数据

详细内容：

- [Chroma Engine](../product/CHROMA_ENGINE.md)
- [GrainMend](../product/GRAINMEND.md)

### `ScannerKit`

负责连接外部插件的约定。

- 扫描仪 ID 与能力
- 请求与响应 JSON
- 运行外部进程、超时与取消
- 插件的所有者、权限、批准与哈希
- 检查临时输出后再发布最终文件
- 扫描会话与任务历史
- 需要你自己打开的演示扫描仪

SANE 的实现在单独的 GPL 项目 [`negaflow-scanner-sane`](https://github.com/habinsong/negaflow-scanner-sane) 中。应用与插件只通过 JSON 和 CLI 通信。

### `negaflowCLI`

使用与 GUI 相同的引擎和 `ScannerKit`。

- 查找扫描仪、检查能力、扫描
- 批量显影多张图像
- 列出扫描仪配置文件
- GrainMend 的 `defect-bench`
- IT8 与扫描仪之间的相对比较
- 自检与 JSON 自动化

### `negaflowApp`

用 SwiftUI 和 AppKit 构建的用户界面。

- 图库、显影、印相、画布
- 扫描、GrainMend、导出
- 版本、设置、快捷键
- 目录、缓存、备份、保存归档
- 产品版本取自共用版本资源的本地化关于窗口

## 用户流程

1. 导入或扫描。
2. 整理图库。
3. 设定胶片类型和片基。
4. 在 Chroma Engine 中显影，用 GrainMend 修复，或用版本与虚拟副本分出分支。
5. 检查后印相，或导出为图像文件、旁注文件和渲染记录，或导出为保存归档。

每一步都不动原始文件，只向目录和编辑历史中添加内容。

## 输入与原始文件

### 导入文件

默认的入口。支持 TIFF、JPEG、PNG 以及 macOS Image I/O 能读取的相机 RAW。读取内嵌的 ICC 和方向，并把原始文件 ID 写入目录。

### 扫描

已安装的插件可以报告这些能力：

- 分辨率与位深
- 扫描区域与预览
- 曝光
- IR
- 批量与片夹行为

应用不会靠型号表凭空编造能力。扫描完成后，会再次核对插件实际应用的设置和输出文件。

### 原始文件 ID

仅凭文件路径无法识别一个原始文件。会保存当前约定所需的值：文件观测、字节数、修改时间、SHA-256 和持久书签。

文件被移动后，只有在你自己重新链接或书签恢复成功时，路径才会改变。

## 目录

主存储是 `library.sqlite`。旧的 `library.json` 用来导入已确认的旧资料，或写出可以在不同电脑之间移动的备份。两个存储不会同时更新。

放进 SQLite 的内容：

- 画幅与原始文件
- 卷、文件夹、收藏集、搜索
- 排序与扫描任务
- 显影值与各版本的编辑历史

不放进去的内容：

- 原始像素
- 缩略图与预览
- GrainMend 缓存

### 从 JSON 迁移

1. 检查现有 JSON 的架构和健康状况。
2. 保留一份恢复副本。
3. 在一个事务里写入临时的 SQLite。
4. 对比迁移前后的目录。
5. 检查 SQLite 的完整性和应用的安全条件。
6. 只有全部吻合时，才切换主存储。

失败的 JSON 不会被当作空目录。具体数值见[目录存储结构](CATALOG_STORAGE.md)。

## 图库

整理方式：

- 文件夹、卷、手动收藏集、智能收藏集、已保存的搜索、堆叠
- 星级、留用与排除、颜色标签
- 网格、对比、总览
- 查看重复候选

在文件夹视图里，每个文件夹显示一条横带，包含展开三角、文件夹、名称、数量、显影流程、目标和应用。横带可以折叠其下的缩略图。折叠的文件夹会在多次启动之间被记住，与侧边栏的文件列表分开。

文件夹视图只用一个网格，每个文件夹是一个分区，横带是分区标题。请保持这种结构。如果给每个文件夹单独叠一个网格，布局就要计算所有可见文件夹的完整高度，并一次创建它们的全部卡片；单个网格则在卡片进入视野时一行一行创建。这样即使有几百张照片，滚动也很顺畅。

多个虚拟副本可以共用一个原始文件。删除前会检查对原始文件的引用。从图库中移除只改变目录里的引用，移到废纸篓是另一个操作。

外接磁盘断开时，编辑会被保留。原始文件被标记为离线，你可以按文件或按文件夹重新链接。如果 ID 不是预期的那个，不会自动替换。

每个已登记的实际源文件夹有一个文件系统监视器。事件会先短暂合并，然后只重新扫描有变动的文件夹。Finder 移动或重命名源文件时，基于书签的重新链接会保留目录里的文件夹 ID，新增的直接子级图像无需轮询或重新扫描整个图库就会被导入。

## 显影与 GrainMend

每个画幅带有：

- 原始文件 ID 与胶片类型
- 片基
- 显影值
- GrainMend 编辑历史
- 版本历史
- 导出状态

调整过程中使用较低分辨率的预览。只有当画幅 ID 和编辑版本仍与当前选择一致时，完成的结果才会显示到屏幕上。

选择另一张照片会直接开始其稳定后的渲染，没有编辑时的停顿。在 macOS 上：

- 相机 RAW 负片稳定后，可以在后台解码下一张可见的 RAW。只准备相邻的一张，且在现有的主缓存（最多 160 MiB）之内。编辑、改选其他照片或内存紧张都会取消这项工作，选中正在准备的那张照片则共用它的解码。
- 冷启动选择相机 RAW 时，只解包一次传感器数据。马赛克允许时，在标准去马赛克完成之前会先显示临时的相机 RGB 预览。主缓存在内存紧张时保持关闭，淘汰某个画幅也会丢弃它的 RAW 主数据。
- 冷启动选择 TIFF 时，交互预览和稳定预览共用一份解码的源数据，并在 GPU 上缩小。包括 DNG 在内的 Apple RAW 预览，在两个阶段都保持同一个 `CIRAWFilter`。
- 清理过的 RAW TIFF 在其像素缓冲离开内存时写入，而不是每次编辑后写入。磁盘清理会在限额内保留较新的文件，保护正在使用的文件，并在下次启动时删除上次会话遗留的缓存。编辑配方保存在旁注文件里。

在 Windows 上，JPEG 缩略图使用 LRU 字节预算，BGRA 预览使用受管显示预算的其余部分，内存严重紧张时会丢弃闲置的 JPEG。D3D 暂存缓冲有缓存上限，低内存信号、导出完成和设备重置会将其释放。

导出不会保存屏幕上的预览位图，而是依据原始文件和已固定的编辑值重建全分辨率图像。

GrainMend 把自动、引导、画笔、克隆图章和 IR 放在一个有顺序的列表里。缓存是派生文件。如果无法从原始文件和编辑历史重建结果，导出就会失败。

详细内容见 [GrainMend](../product/GRAINMEND.md)。

## 版本

- 历史与快照：自己记录一个显影状态，之后可以对比或回到它。
- 虚拟副本：不复制原始文件，另开一条编辑分支。
- 复制粘贴：粘贴选定的范围，例如影调、色彩、细节或几何。需要原始坐标的蒙版会检查其安全条件。

## 导出

开始时，这些值被固定成一个整体：

- 原始文件 ID
- 显影与 GrainMend 编辑历史
- 扫描仪配置文件的字节与 SHA-256
- 输出设置与元数据策略
- 文件名与目的地

导出暂停后再继续，使用的是同一个整体。

### 多个输出文件

一次导出可以同时生成 JPEG/TIFF、旁注文件、XMP 和 `-main-flat`。

1. 预先检查目的地和名称冲突。
2. 把所有文件写入临时文件夹。
3. 重新打开图像并核对像素尺寸。
4. 计算字节数和 SHA-256。
5. 写入旁注文件和渲染记录。
6. 留下提交记录。
7. 把整个整体移到最终位置。
8. 失败时回滚，或在下次运行时清理。

只有一部分文件的状态，绝不会标记为成功。

### 渲染记录 v3

它记录下列对象之间的 SHA-256 关系：

- 原始文件字节
- 实际使用的渲染输入
- 显影与 GrainMend 历史
- 扫描仪配置文件
- 解码器与渲染器版本
- 输出字节数、像素尺寸、格式

它没有数字签名和证书，所以不是 C2PA Content Credentials。详见[渲染记录](../reference/RENDER_MANIFEST.md)。

## 印相与软打样

支持的版式：

- 单张图像
- 接触印相表
- 照片套版
- 自定义套版
- 蓝晒
- 玻璃干版
- 明胶银盐
- 水印

单张图像和三种历史版式，为每张选中的照片生成纵向堆叠的一页。接触印相表、照片套版和自定义套版则按成品页数报告和导出。对于 39 张照片，就是一页 6 × 7 的接触印相表、10 页四联照片套版、一页默认的自定义套版，或 39 个单独的文件。

套版预览复用已有的缩略图和已显影图像，只在缺失时才生成小的快速预览。最终导出根据元数据计算位置，只显影每个格子所需的像素，同时准备两到四个不同的源文件，在页面写入之前保持 Core Image 图形连接，并遵守每页 512 MiB 的源光栅预算。

套版里的每个位置都遵循分配给它的画幅。打印机输出 ICC 在布局完成后，对完整的最终页面只应用一次，所以重复放置和混合多个源文件的套版使用同一份输出约定。它不会改变图库或显影的预览，原始扫描 TIFF 和 `-main-flat` 也不会带上打印机配置文件。

没有有效的 RGB 打印机 ICC 时，不会用其他配置文件代替。你所选配置文件的字节与 SHA-256 会写进输出记录。

## 保存归档

`.negaflowarchive` 包含：

- 可移植的目录 JSON
- 原始文件
- IR 原始文件
- 需要的 GrainMend 历史
- 虚拟副本与它们共用的原始文件之间的关系

缩略图、预览、GrainMend 缓存和导出的文件都可以重建，所以不放进去。归档采用带 SHA-256 清单的 RFC 8493 BagIt 结构，在整体移到最终位置之前，会检查每个文件和每一项关系。

- [图库保存归档](LIBRARY_ARCHIVE.md)
- [RFC 8493](https://www.rfc-editor.org/info/rfc8493/)
- [PREMIS](https://www.loc.gov/standards/premis/)

长期保存还需要其他介质、异地副本和定期的哈希检查。

## 扫描仪插件的安全

发现插件时，会检查：

- 是否归当前用户所有
- 组或其他用户是否可写
- 是否为符号链接
- 清单和可执行文件的 ID 与 SHA-256
- 你批准过的 ID 是否仍是眼前这个 ID

文件变化后，不会再沿用之前的批准。

协议 v2 使用请求 ID 和序号，并要求恰好有一个最终结果。输出大小有上限，超时或取消之后，会清理进程及其管道。

插件从不自己把文件发布到最终位置。应用交给它一个临时位置，核对格式、尺寸、ID 和实际应用的设置，然后再把文件移入应用的存储。

完整的约定见[扫描仪插件结构](SCANNER_PLUGINS.md)。

## 性能边界

图像：

- 共用一个 `CIContext`
- 需要时才计算的图像图
- 低分辨率调整与全分辨率输出分开
- 取消，以及拒绝过期的结果
- GrainMend 按区域、图块和图块内的补丁处理
- 内存紧张时丢弃缓存

目录：

- SQLite 事务与按实体划分的行
- 通过复制进行备份
- 完整性检查
- 以 5 万画幅测量

目前启动时会把整个目录加载进内存。在同一台 Mac 上，读取 SQLite 花了约 7.4 秒，与 JSON 接近。下一步是通过索引只读取所需的行。

仓库使用宽松的性能上限来捕捉大幅退步。它们不保证在所有受支持的 Mac 上都响应流畅。

## 验证了什么

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift test
bash scripts/run-app.sh build
```

自动检查无法判定的内容：

- 真实的扫描仪和插件
- 真实的 RGB/IR 对位与胶片兼容性
- 100% 下的 GrainMend 质量
- 包括显示尺寸和无障碍在内的界面
- Developer ID、公证、Gatekeeper
- 在全新的 Mac 上安装
- 在其他 Mac 上的性能
