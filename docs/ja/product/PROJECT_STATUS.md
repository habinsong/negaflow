## カタログ

主な保存先は`library.sqlite`です。
既存の`library.json`は読み取り専用で開いて健全性を確認し、バックアップしてから一時SQLiteへ移しま
す。
2つのカタログの内容とSQLiteの整合性がどちらも合ったときだけ、主な保存先を切り替えます。

途中の作業を続けるときに証拠が合わなければ、閉じた状態で失敗します。
JSONは移動できるバックアップ・アーカイブの交換形式として残りますが、2つの主保存先を同時には使い
ません。

詳しくは[カタログ保存構造](../architecture/CATALOG_STORAGE.md)にあります。

## スキャナー

このリポジトリにあるのは、装置に依存しない外部プロセスのホストとJSON規格だけです。
SANEの実装、依存、設定、配布ファイルは入れません。
そのコードは別のGPLプロジェクト
[`negaflow-scanner-sane`](https://github.com/habinsong/negaflow-scanner-sane)にあります。

アプリは、インストールしたプラグインが報告した機能だけを見せます。
モデル名から機能を推測しません。
ユーザーがデモを選ばない限り、偽のスキャナーで代用することもありません。

詳しい規格:

- [スキャナープラグイン構造](../architecture/SCANNER_PLUGINS.md)
- [スキャナーCLI JSON](../reference/CLI_JSON.md)
- [フラットベッドの自動フレーム検出](../reference/FRAME_DETECTION.md)

## ビルドと配布

<details>
<summary>ローカル確認と配布のコマンド</summary>

ローカル確認:

```bash
bash scripts/ci-gate.sh
bash scripts/run-app.sh build
bash scripts/run-gui-e2e.sh  # macOSのAutomation Modeが必要
```

配布ファイルを作る:

```bash
bash scripts/build-release.sh
```

</details>

`scripts/run-app.sh build`はアプリを組み立てるだけで、アプリやUIテストRunnerは起動しません。
GUI自動化は別の`scripts/run-gui-e2e.sh`を明示的に実行したときだけ始まります。

2026年7月31日の現在の作業ツリーでは、Swift厳格並行性ビルド、並列テスト1,800件、
時間依存の直列テスト9件が通過しました。`scripts/run-app.sh build`でarm64 Releaseアプリも
作り直し、実行ファイルとdSYMのUUID一致を確認しました。GUI実使用、実機スキャナー、
Developer ID、公証の確認を代わりにする記録ではありません。

`build-release.sh`を一度実行すると、Apple Silicon(`arm64`)とUniversal(`arm64`、`x86_64`)のアプリ
をそれぞれビルドし、ZIP、PKG、DMG、dSYM、SHA-256の一覧を作ります。
ローカルでは一時的な署名を使い、実際の配布にはDeveloper ID ApplicationとDeveloper ID Installerの
署名が両方必要です。

手動の`Distribution` workflowは、保護されたDeveloper IDとApp Store Connect APIキーを使います。
アプリアーカイブ、DMG、PKGをAppleに送り、公証チケットを貼り付けてから、チェックサムとGatekeeper
をもう一度確認します。
実際のworkflowとAppleの応答がなければ、外部署名と公証に成功したとは言いません。

性能検査は、カタログ、ライブラリ検索、高解像度の調整、GrainMendの領域処理、実際のピクセルのロー
ルを対象にします。

あるMacでの最近のRelease測定:

|---|---:|
| 50,000フレームのJSON読み込みp95 | 約7.4秒 |
| 50,000フレームのSQLite読み込みp95 | 約7.4秒 |
| 50,000フレームのSQLiteコミットp95 | 約3.7秒 |
| 変更なしのSQLiteコミットp95 | 約3.9秒 |
| 50,000フレームのフィルターと名前並べ替え | 約158 ms |

| 48フレームの現像 | 約20.9秒、最大RSS約1,012 MiB |

2026年7月31日にこのMacで任意実行した`PrintExportPerformanceTests`は、別々の

| 6列×7行コンタクトシート、39枚 → 1ファイル | 1.177秒 | — |

## GrainMendの測定

FILM-R v2の資料は、DOI、44ペア、437,570,872バイト、FigshareのMD5情報で固定しています。

リリースの自動経路は感度0.7と過検出の安全線を使います。直前の回帰基準3.0と比べた結果です。

| 指標 | 直前の基準3.0 | 安全な自動0.7 |
|---|---:|---:|
| 加重の悪化ピクセル | 0.792% | 0.017% |
| 加重の変更ピクセル | 0.794% | 0.043% |
| 平均PSNR変化 | -1.688 dB | +0.466 dB |
| 最低PSNR変化 | -18.952 dB | -1.338 dB |
| 改善 / 悪化 / 同じ画像 | 11 / 33 / 0 | 34 / 6 / 4 |

観測値の回帰検査とは別に、平均と中央のPSNRが0 dB以上、悪化10枚以下、最低-1.5 dB以上という絶対的
な下限も検査します。
自動の安全線は3枚で復元を止め、その場合はガイドの使用を案内します。

FILM-RはGrainMend RGBの自動経路だけを検証します。
ハードウェアIRとの同等性や、実機スキャナーの RGB・IR整列の品質を主張する根拠にはなりません。

手動の`GrainMend corpus` workflowは44ペアを取得し、Releaseの既定経路を実行してから、回帰検査とレ
ポートのアップロードを行います。

## 自動検査で終わらない項目

- 対応する画面サイズとアクセシビリティ設定での最終UI確認
- 実際のプラグインとスキャナー
- 実際のネガとIRの画質
- Developer ID、公証、Gatekeeper、きれいなMacへのインストール
- 対応するすべてのMacでの性能

最終的な画面と実機の確認はユーザーが担当します。
ビルド成功で代用せず、[実機点検リスト](../validation/REAL_QA_CHECKLIST.md)に結果を残します。
