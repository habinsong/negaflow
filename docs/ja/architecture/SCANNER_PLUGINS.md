# スキャナープラグイン構造

[ドキュメントホーム](../README.md)

negaflow の基本の入力は画像の読み込みです。実際のスキャナーは、外部プラグインがあるときだけ接続されます。

> [!IMPORTANT]
> アプリは、スキャナーの機種名から機能を推測しません。プラグインが報告したものだけが画面と要求に入り、デモ機器は、ユーザー自身がデモモードを選んだときだけ現れます。

## 構成要素

| 要素 | 役割 |
|---|---|
| 画像の読み込み | RAW、DNG、TIFF、PNG、JPEG を現像の経路に送ります。 |
| 外部プラグイン | 別プロセスで動き、実際の機器を操作して、JSON でやり取りします。 |
| デモスキャナー | 開発用の `negaflow Scanner` と `negaflow Flatbed Scanner` を提供します。デモを自分で選ばないと使えません。 |
| ImageCaptureCore の連携 | macOS のイメージキャプチャ機器向けの互換コードで、今は無効です。 |

このリポジトリには SANE の実装がありません。そのコードは別の GPL プロジェクトにあります。

- <https://github.com/habinsong/negaflow-scanner-sane>

## 接続のしくみ

画面は `ScannerKit` と通信し、`ScannerKit` は3つのバックエンドのどれかに振り分けます。

1. `ExternalScannerBackend`: インストール済みの外部プラグインを実行します。
2. `MockScannerBackend`: 開発用の合成画像を作ります。
3. `InactiveImageCaptureBackend`: 今は無効です。

画面が見るのは `ScannerBackend` だけです。プラグインの機器 ID は、アプリでは `plugin:<pluginId>:<deviceId>` として現れます。

プラグインを実行するときは、`plugin:<pluginId>:` を取り除き、プラグイン自身の機器 ID だけを送ります。

## プラグインを探す

既定のフォルダーは `~/Library/Application Support/negaflow/Plugins/<id>/manifest.json` です。テストやローカルでの開発では、`NEGAFLOW_PLUGINS_DIR` で別のフォルダーを指します。

| フィールド | 規則 |
|---|---|
| `schemaVersion` | 現在はちょうど `1` |
| `protocolVersion` | 省略時は `1`。`1` と `2` に対応 |
| `id` | 一意のプラグイン ID |
| `name` | 画面に表示する名前 |
| `kind` | プラグインの種類 |
| `license` | 配布ライセンス |
| `homepage` | プロジェクトのアドレス |
| `executable` | 実行ファイルのパス |

`id` は ASCII 文字で1〜64文字です。先頭は英字か数字で、残りは英字、数字、`.`、`_`、`-` です。`:` は機器 ID の区切りなので使えません。

マニフェストと実行ファイルの両方が確認できたときだけ、プラグインが開きます。古いスキーマ、将来のスキーマ、未知のプロトコルは、推測で読みません。

### ファイルの安全確認

> [!WARNING]
> マニフェストや実行ファイルのバイト列が変わると、以前の承認は破棄されます。所有者、権限、シンボリックリンクかどうか、SHA-256 は、実行の直前にもう一度確かめます。

- プラグインのフォルダー、マニフェスト、実行ファイルの所有者が現在のユーザーでなければなりません。
- グループやその他のユーザーが書き込める場合は拒否します。
- シンボリックリンクは拒否します。
- マニフェストと実行ファイルの SHA-256 を記録します。
- 初めて使うときに、ユーザーが承認します。
- ファイルのバイト列が変わると、承認は無効になります。
- ID は実行の直前に計算し直します。

## コマンド

プラグインは別プロセスとして動きます。

| コマンド | 結果 |
|---|---|
| `detect` | JSON の機器リスト |
| `capabilities <deviceId>` | JSON の機能リスト。`detect` が報告した機器 ID、ベンダー、モデルの JSON を stdin で受け取れる |
| `scan` | stdin で設定 JSON を受け取り、stdout に進行状況の NDJSON と最終結果を出す |

## スキャンのプロトコル

### バージョン 1

古い互換仕様です。要求と NDJSON に `protocolVersion`、`requestID`、`sequence` がありません。実際に適用された設定を報告できないので、結果は `.unknownLegacy(protocolVersion: 1)` として記録します。要求の値を、検証済みのようにそのまま写すことはしません。

### バージョン 2

マニフェストに `"protocolVersion": 2` があるときだけ使います。

要求には次が入ります。

- `protocolVersion: 2`
- アプリが作る `requestID` の UUID

`capabilities` の応答は、任意のフィールド `capabilityToken` を返すことがあります。アプリはこれを解釈せず、同じ機器の次の v2 `scan` 要求にだけそのまま渡します。v1 の要求には入れず、トークンを機器の間で混ぜることはありません。トークンの形式と有効性は、プラグイン自身が確かめる必要があります。

同じバックエンドの別モデルへ誤って再接続するのを防ぐため、アプリは直前の `detect` の `deviceID`、`vendor`、`model` を、`capabilities` の任意の stdin JSON として渡し直します。既存のプラグインはこの入力を無視してかまいません。機器のアドレスが変わりうるプラグインは、この識別情報を機能のスナップショットに結び付け、次の `scan` で改めて確かめるべきです。

NDJSON のイベントはどれも同じバージョンとリクエスト ID を繰り返し、前のイベントより大きい0以上の `sequence` を持ちます。許されるのは `progress`、`result`、`error` だけです。`result` と `error` は最終のイベントで、その後に何か来れば失敗です。エラーで終わらなかったスキャンには、`result` がちょうど1つあります。

次はすべて、閉じたまま失敗します。

- 読み取れないイベント
- バージョンやリクエスト ID がない、または違う
- 繰り返された、または順序が乱れた sequence
- 未知のイベント
- 重複した result
- 最終イベントの後の余分な出力
- 不正な UTF-8

v2 の仕様に違反すると、通常のタイムアウトを待たずにプラグインをすぐ終了させます。

### 実際に適用された設定

v2 の `result` には `appliedOptions` が必要です。

- `deviceID`、`resolutionDPI`、`bitDepth`、`colorMode`、`filmType`
- `scanArea`: `originXMM`、`originYMM`、`widthMM`、`heightMM`。プラグインがバックエンドに実際に送った領域です。スキャンサイズを誤って計算するバックエンドを避けるため、1mm 未満の調整が許されます。アプリは返ってきたピクセルサイズをこの領域と照合するので、要求をそのまま写すと検査の意味がなくなります。
- `infrared`、`multiExposure`
- `hardwareExposureTime`、`brightnessAdjustment`、`contrastAdjustment`
- `outputRawTIFF`

後ろの3つの調整値は、値が `null` でもキーが必要です。

`resolutionDPI: 0` はプレビューを表します。0 でないプレビュー、または0の本スキャンは拒否します。未知の値、別の機器、結果のヘッダーと `appliedOptions` で食い違う解像度・ビット深度・IR の状態も拒否します。

検査に通ると、アプリはプラグイン ID の代わりに自分のスキャナー ID とリクエスト ID を記録し、最終的な出力パスを保ちます。そこで初めて `.verified(options)` と印を付けます。

v1 では、`ScanResult.resolution` と `bitDepth` が要求値に置き換わることがあります。出どころを示す `reportedResolution` と `reportedBitDepth` は、結果が自分で報告した正しい値だけを受け取ります。

## 位置を指定するフラットベッドのスキャン領域

このワークフローのプレビューは、機器に任せず、300dpi にもっとも近い対応値を解像度として明示して要求します。機器の既定値は25dpi まで低いことがあり、それではコマの位置合わせにも検出にも粗すぎます。解像度が付いたプレビューは通常のスキャンなので、プラグインのプレビュー経路は使いません。

位置を選んだフラットベッドのスキャンは、プラグインが次のすべてを報告したときだけ有効になります。

- プレビュー
- `supportsPositionedScanArea`
- mm 単位の `scanOriginXRange` と `scanOriginYRange`
- mm 単位の `scanWidthRange` と `scanHeightRange`

アプリは、選んだ領域をプラグインのステップ幅まで外側に広げ、領域ごとに本スキャンのジョブを1つ作ります。機種名から推測することはありません。任意のフィールドがない古いプラグインは、固定フレームの流れのままです。

## プロセスの制限とキャンセル

- stdout の上限: 4MiB
- stderr の上限: 1MiB

上限を超えるとプロセスを終了して失敗にします。後始末では、すでに届いたバイトだけを読みます。子プロセスがパイプを引き継いでいても、EOF を待ちません。

`cancelScan()` は、プラグインが終了し、パイプのハンドラーが閉じ、次のジョブの枠が空いてから戻ります。

## スキャンファイルの公開

プラグインは、アプリが渡した `outputPath` にぴったり元画像を書き、結果にも同じパスを返します。このパスは、最終フォルダーと同じディスク上の一時的な場所です。流れは次のとおりです。

1. アプリが設定 JSON と `outputPath` をプラグインに送る。
2. プラグインがスキャンファイルを一時フォルダーに書く。
3. プラグインが同じ `outputPath` を含む結果を返す。
4. アプリが形式、サイズ、パスを確かめる。
5. 通ればアプリは最終のスキャンフォルダーにアトミックに公開する。キャンセル、失敗、誤った出力のときは、一時的な資料を削除する。

アプリが確かめること:

- 空でない通常のファイル
- ImageIO が読める画像
- 期待した形式とピクセルサイズ
- 要求と結果で同じパス

キャンセル、タイムアウト、誤った出力、プラグインの失敗があれば、一時フォルダーを削除し、不完全なスキャンは公開しません。

v2 の IR ファイルも、アプリが渡した一時フォルダーの中になければなりません。ファイルの種類、読み取れるか、ピクセルサイズを確かめます。v1 は、すでに出回っているプラグインとの互換のため、外部の IR パスを受け付けられます。

## SANE との境界

SANE の実装、依存関係、設定、機器ごとの処理、テスト、配布ドキュメントは、すべて別リポジトリの [`negaflow-scanner-sane`](https://github.com/habinsong/negaflow-scanner-sane) にあります。

そのプロジェクトは、Homebrew 標準の SANE を使う標準の macOS 14+ インストーラーと、公式の SANE 1.4.0 を上流の最小限の `coolscan2`/`coolscan3` の割り当て修正つきでビルドする別の macOS 26+ Coolscan インストーラーを配布しています。標準の経路は Coolscan を前もって止めることはしませんが、その修正は含みません。

このリポジトリが文書化して検査するのは、機器に依存しない外部プロセスの仕様だけです。画像ファイルを読み込むだけのユーザーに、スキャナープラグインは要りません。

negaflow アプリは、SANE の実装をリンクせず、アプリの配布物にも入れません。プラグインは、自前のリポジトリ、実行ファイル、ソース配布、GPL ライセンスを持ちます。この文書は構造を記録するだけで、二次的著作物かどうかは判定しません。実際のリリースの前に、両方の成果物のファイルと通信の規約をもう一度確かめます。

## 検査

アプリのテストは、偽の外部プラグインを実際のプロセスとして動かし、次を確かめます。

- プラグインの探索
- 機器の探索
- 機能の接続
- 進行イベント
- 最終結果
- キャンセルと失敗の後の後始末

SANE の実装は、プラグインのリポジトリにある SwiftPM のテストと Release ビルドで別に検査します。
