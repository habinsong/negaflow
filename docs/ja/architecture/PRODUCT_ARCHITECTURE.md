# 製品構造

[ドキュメントホーム](../README.md)

negaflow は macOS と Windows のアプリです。フィルムの画像を読み込むかスキャンして、反転、現像、GrainMend、出力、保存を経ます。すべての編集は元ファイルと分けて保ちます。

> [!IMPORTANT]
> 元ファイル、編集履歴、キャッシュ、出力ファイルは別々の資料です。キャッシュを失っても、元ファイルや編集履歴を失ってはならず、必要な結果を作り直せないときは、書き出しが失敗します。

## 変わらない安全の規則

1. 元の画像と他社製のサイドカーは、自動では上書きしません。
2. ライブラリから外すことと、元ファイルをゴミ箱に移すことは別の操作です。
3. スキャナーの画面には、プラグインが報告したものだけが表示されます。
4. デモスキャナーは、自分で選んだときだけ使います。
5. 編集した結果を作り直せないときに、元ファイルを代わりに書き出すことはしません。
6. 時間のかかる処理は、結果を適用する直前に、フレーム、編集バージョン、セッションを確かめ直します。
7. キャッシュは、元ファイルと編集履歴から作り直せなければなりません。
8. プロファイル、出力一式、アーカイブは、必要な検査に通った後にだけ公開します。

## モジュール

`negaflowApp` と `negaflowCLI` は、どちらも `Chromabase` と `ScannerKit` を使います。`Chromabase` は画像とメタデータを扱い、`ScannerKit` は外部のスキャナープラグインと通信します。

### `Chromabase`

Chroma Engine と画像処理の中核です。

- 画像の読み込みと向きの処理
- フィルムベースの測定
- ネガとポジの現像
- トーン、色、部分補正
- フィルム、ルック、スキャナーのプロファイル
- GrainMend の RGB と IR
- ヒストグラムと色の測定
- 出力のエンコードとメタデータ

詳細:

- [Chroma Engine](../product/CHROMA_ENGINE.md)
- [GrainMend](../product/GRAINMEND.md)

### `ScannerKit`

外部プラグインをつなぐ規約を受け持ちます。

- スキャナー ID と機能
- 要求と応答の JSON
- 外部プロセスの実行、タイムアウト、キャンセル
- プラグインの所有者、権限、承認、ハッシュ
- 一時的な出力を確かめてから最終ファイルを公開
- スキャンのセッションとジョブ履歴
- 自分で有効にするデモスキャナー

SANE の実装は、別の GPL プロジェクト [`negaflow-scanner-sane`](https://github.com/habinsong/negaflow-scanner-sane) にあります。アプリとプラグインは JSON と CLI だけでやり取りします。

### `negaflowCLI`

GUI と同じエンジンと `ScannerKit` を使います。

- スキャナーの検出、機能の確認、スキャン
- 複数画像の現像
- スキャナープロファイルの一覧
- GrainMend の `defect-bench`
- IT8 とスキャナー間の相対比較
- 自己確認と JSON による自動化

### `negaflowApp`

SwiftUI と AppKit で作ったユーザーインターフェースです。

- ライブラリ、現像、プリント、キャンバス
- スキャン、GrainMend、書き出し
- バージョン、設定、ショートカット
- カタログ、キャッシュ、バックアップ、保存アーカイブ
- 製品バージョンを共通のバージョンリソースから取る、ローカライズされた情報ウィンドウ

## ユーザーの流れ

1. 読み込みまたはスキャン。
2. ライブラリを整理する。
3. フィルム種別とベースを決める。
4. Chroma Engine で現像するか、GrainMend で復元するか、バージョンと仮想コピーで枝分かれさせる。
5. 確認し、プリントするか、画像ファイル、サイドカー、レンダー記録に、または保存アーカイブに書き出す。

どの段階も元ファイルには触れず、カタログと編集履歴に足していきます。

## 入力と元ファイル

### ファイルの読み込み

標準の入口です。TIFF、JPEG、PNG と、macOS の Image I/O が読めるカメラ RAW を扱います。埋め込みの ICC と向きを読み、元ファイルの ID をカタログに入れます。

### スキャン

インストール済みのプラグインは、次の機能を報告できます。

- 解像度とビット深度
- スキャン領域とプレビュー
- 露出
- IR
- バッチとホルダーの挙動

アプリは、機種名の表から機能をこしらえることはしません。スキャンが終わると、プラグインが実際に適用した設定と出力ファイルをもう一度確かめます。

### 元ファイルの ID

ファイルのパスだけでは元ファイルを特定できません。現在の規約が必要とする値、つまりファイルの観測、バイト数、更新時刻、SHA-256、永続ブックマークを保管します。

ファイルが移動していても、パスが変わるのは、ユーザーが自分で再リンクしたときか、ブックマークの復旧に成功したときだけです。

## カタログ

主な保存先は `library.sqlite` です。旧来の `library.json` は、確認済みの古い資料の取り込みや、別のマシンへ持ち運べるバックアップの書き出しに使います。両方を同時に更新することはありません。

SQLite に入るもの:

- フレームと元ファイル
- ロール、フォルダー、コレクション、検索
- 並び順とスキャンジョブ
- 現像値とバージョンごとの編集履歴

入らないもの:

- 元のピクセル
- サムネイルとプレビュー
- GrainMend のキャッシュ

### JSON からの移行

1. 既存の JSON のスキーマと健全性を確かめる。
2. 復旧用のコピーを残す。
3. 1つのトランザクションで一時的な SQLite に書き込む。
4. 移行の前後でカタログを比べる。
5. SQLite の整合性とアプリの安全条件を確かめる。
6. すべて合ったときにだけ、主な保存先を切り替える。

失敗した JSON を空のカタログとして扱うことはありません。数値は[カタログ保存構造](CATALOG_STORAGE.md)にあります。

## ライブラリ

整理の方法:

- フォルダー、ロール、手動コレクション、スマートコレクション、保存した検索、スタック
- 星評価、採用と除外、カラーラベル
- グリッド、比較、サーベイ
- 重複候補の確認

フォルダー表示では、フォルダーごとに、開閉の三角、フォルダー、名前、数、現像プロセス、ターゲット、適用が並んだ帯が表示されます。帯は、その下のサムネイルをたたみます。たたんだフォルダーは、サイドバーのファイル一覧とは別に、起動をまたいで記憶されます。

フォルダー表示はグリッドを1つ使い、フォルダーごとにセクションとし、帯をセクションの見出しにします。この構造を保ってください。フォルダーごとに別のグリッドを積むと、レイアウトが見えているすべてのフォルダーの全体の高さを計算し、カードを一度にすべて作ることになりますが、グリッド1つなら、画面に入るときに1行ずつカードを作ります。写真が数百枚あってもスクロールがなめらかなのは、そのためです。

複数の仮想コピーが1つの元ファイルを共有できます。削除の前に、元ファイルへの参照を確かめます。ライブラリから外すことは、カタログの参照を変えるだけで、ゴミ箱に移すのは別の操作です。

外付けディスクの接続が切れても、編集は保たれます。元ファイルはオフラインと表示され、ファイル単位かフォルダー単位で再リンクします。ID が期待したものと違えば、自動では差し替えません。

登録された実際の元フォルダーごとに、ファイルシステムの監視が1つあります。イベントを短い間まとめてから、変更のあったフォルダーだけを再スキャンします。Finder が元ファイルを移動したり名前を変えたりしても、ブックマークによる再リンクがカタログのフォルダー ID を保ち、新しく加わった直下の画像は、ポーリングやライブラリ全体の再スキャンなしで読み込まれます。

## 現像と GrainMend

フレームごとに次を持ちます。

- 元ファイルの ID とフィルム種別
- フィルムベース
- 現像値
- GrainMend の編集履歴
- バージョン履歴
- 書き出しの状態

調整している間は、低解像度のプレビューを使います。完成した結果は、そのフレーム ID と編集バージョンが現在の選択とまだ一致しているときだけ、画面に届きます。

別の写真を選ぶと、編集の待ち時間なしで確定のレンダリングが始まります。macOS では次のようになります。

- カメラ RAW のネガが確定すると、次に見える RAW をバックグラウンドでデコードできます。準備するのは隣の1枚だけで、既存のマスターキャッシュ(最大160MiB)の範囲内です。編集、別の選択、メモリの逼迫でその作業は取り消され、すでに準備中の写真を選べばそのデコードを共有します。
- 冷えた状態でのカメラ RAW の選択では、センサーのデータを一度だけ展開します。モザイクが許せば、正規のデモザイクが終わる前に、仮のカメラ RGB のプレビューが現れます。マスターキャッシュはメモリが逼迫している間は無効で、フレームを追い出すとその RAW マスターも捨てます。
- 冷えた状態での TIFF の選択では、デコードした元ファイルを、操作中のプレビューと確定のプレビューが共有し、GPU で縮小します。DNG を含む Apple RAW のプレビューは、2つのパスで `CIRAWFilter` を1つ保ちます。
- 補正した RAW の TIFF は、編集のたびにではなく、ピクセルバッファがメモリを離れるときに書きます。ディスクの整理は、上限の範囲で新しいファイルを残し、使用中のファイルは守り、次の起動で前のセッションが残したキャッシュを削除します。編集のレシピはサイドカーに残ります。

Windows では、JPEG のサムネイルが LRU のバイト予算を使い、BGRA のプレビューが管理された表示予算の残りを使い、メモリが危機的に逼迫すると、使われていない JPEG を捨てます。D3D のステージングバッファにはキャッシュの上限があり、メモリ不足の信号、書き出しの完了、デバイスのリセットで解放されます。

書き出しは、画面にあるプレビューのビットマップを保存しません。元ファイルと、固定した編集値から、全解像度の画像を作り直します。

GrainMend は、自動、ガイド、ブラシ、クローンスタンプ、IR を順序のあるリストで保ちます。キャッシュは派生ファイルです。元ファイルと編集履歴から結果を作り直せなければ、書き出しは失敗します。

詳細は [GrainMend](../product/GRAINMEND.md) にあります。

## バージョン

- 履歴とスナップショット: 現像の状態を自分で記録し、比べたり戻ったりします。
- 仮想コピー: 元ファイルを複製せずに、編集の別の枝を持ちます。
- コピー・ペースト: トーン、色、ディテール、ジオメトリなど、選んだ範囲を貼り付けます。元の座標が必要なマスクは、安全の条件を確かめます。

## 書き出し

開始時に、次の値を1つの束として固定します。

- 元ファイルの ID
- 現像と GrainMend の編集履歴
- スキャナープロファイルのバイト列と SHA-256
- 出力設定とメタデータの方針
- ファイル名と保存先

書き出しを止めて再開するときも、同じ束を使います。

### 出力ファイルが複数のとき

1回の書き出しで、JPEG/TIFF、サイドカー、XMP、`-main-flat` が一緒にできることがあります。

1. 保存先と名前の衝突を先に確かめる。
2. すべてのファイルを一時フォルダーに書く。
3. 画像を開き直してピクセルサイズを確かめる。
4. バイト数と SHA-256 を計算する。
5. サイドカーとレンダー記録を書く。
6. コミット記録を残す。
7. 束全体を最終の場所に移す。
8. 失敗したらロールバックするか、次の実行で後始末する。

一部のファイルだけがある状態を、成功と表示することはありません。

### レンダー記録 v3

次のものの間の SHA-256 の関係を記録します。

- 元ファイルのバイト列
- 実際に使ったレンダー入力
- 現像と GrainMend の履歴
- スキャナープロファイル
- デコーダーとレンダラーのバージョン
- 出力のバイト数、ピクセルサイズ、形式

電子署名も証明書もないので、C2PA Content Credentials ではありません。詳細は[レンダー記録](../reference/RENDER_MANIFEST.md)にあります。

## プリントとソフトプルーフ

対応するレイアウト:

- 単一画像
- コンタクトシート
- ピクチャーパッケージ
- カスタムパッケージ
- サイアノタイプ
- ガラス乾板
- ゼラチンシルバー
- ウォーターマーク

単一画像と3つの歴史的なレイアウトは、選んだ写真ごとに縦に積んだ1ページを作ります。コンタクトシート、ピクチャーパッケージ、カスタムパッケージは、代わりに完成したページ数を報告して書き出します。写真39枚なら、6 × 7 のコンタクトシート1ページ、4枚組のピクチャーパッケージ10ページ、既定のカスタムパッケージ1ページ、または個別ファイル39個になります。

パッケージのプレビューは、既存のサムネイルと現像画像を再利用し、ないときだけ小さな高速プレビューを作ります。最終の書き出しは、メタデータから配置を計算し、各セルに必要なピクセルだけを現像し、異なる元ファイルを2〜4個ずつ同時に準備し、ページを書き終えるまで Core Image のグラフをつないだままにし、1ページあたり512MiBの元ラスター予算を守ります。

パッケージのすべての配置は、割り当てられたフレームに従います。プリンター出力 ICC は、レイアウトが終わった後の完成した最終ページに1回だけ適用するので、繰り返しの配置も、複数の元ファイルを混ぜたパッケージも、同じ出力の規約を使います。この ICC がライブラリや現像のプレビューを変えることはなく、元のスキャン TIFF や `-main-flat` にもプリンタープロファイルは付きません。

有効な RGB プリンター ICC がなければ、ほかのプロファイルで代用しません。選んだプロファイルのバイト列と SHA-256 が、出力記録に入ります。

## 保存アーカイブ

`.negaflowarchive` に入るもの:

- 持ち運べるカタログ JSON
- 元ファイル
- IR の元ファイル
- 必要な GrainMend の履歴
- 仮想コピーと、それらが共有する元ファイルとの関係

サムネイル、プレビュー、GrainMend のキャッシュ、書き出したファイルは作り直せるので、入れません。アーカイブは、SHA-256 の一覧を持つ RFC 8493 BagIt の構造を使い、束を最終の場所に移す前に、すべてのファイルと関係を確かめます。

- [ライブラリ保存アーカイブ](LIBRARY_ARCHIVE.md)
- [RFC 8493](https://www.rfc-editor.org/info/rfc8493/)
- [PREMIS](https://www.loc.gov/standards/premis/)

長期の保存には、別の媒体、遠隔地のコピー、定期的なハッシュの確認も必要です。

## スキャナープラグインの安全

プラグインが見つかると、次を確かめます。

- 現在のユーザーが所有しているか
- グループや他のユーザーが書き込めるか
- シンボリックリンクか
- 一覧と実行ファイルの ID と SHA-256
- 承認した ID が、いま目の前にある ID と同じか

ファイルが変わっていれば、以前の承認は再利用しません。

プロトコル v2 は、要求 ID と連番を使い、最終結果がちょうど1つであることを求めます。出力のサイズには上限があり、タイムアウトやキャンセルの後は、プロセスとパイプを後始末します。

プラグインが自分で最終の場所にファイルを公開することはありません。アプリが一時的な場所を渡し、形式、サイズ、ID、実際に適用された設定を確かめてから、ファイルをアプリの保存先に移します。

完全な規約は[スキャナープラグイン構造](SCANNER_PLUGINS.md)にあります。

## パフォーマンスの境界

画像:

- 共有の `CIContext` を1つ
- 必要になったときに計算する画像グラフ
- 全解像度の出力とは分けた低解像度の調整
- キャンセルと、古い結果の拒否
- 領域、タイル、パッチ単位で処理する GrainMend
- メモリが逼迫したときのキャッシュの破棄

カタログ:

- SQLite のトランザクションとエンティティごとの行
- 複製によるバックアップ
- 整合性の検査
- 5万フレームで測定

現在は、起動時にカタログ全体をメモリに読み込みます。同じ Mac で SQLite の読み込みに約7.4秒かかり、JSON に近い値でした。インデックスで必要な行だけを読むのが、次の段階です。

リポジトリは、大きな退行を捉えるために、広い性能の限界を設けています。対応するすべての Mac での応答性を保証するものではありません。

## 検証しているもの

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift test
bash scripts/run-app.sh build
```

自動検査では決められないもの:

- 実際のスキャナーとプラグイン
- 実際の RGB/IR の位置合わせとフィルムとの相性
- 100%での GrainMend の品質
- 画面サイズとアクセシビリティを含む UI
- Developer ID、公証、Gatekeeper
- まっさらな Mac へのインストール
- 別の Mac での性能
