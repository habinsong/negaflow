# ADR-0024: ColorSync 의 섀도우 toe 를 지금은 재현하지 않는다

- 상태: 채택
- 날짜: 2026-08-06

## 문제

`docs/research/colorsync-icm-parity-windows-measurement.md` 의 실측으로 macOS 와 Windows 의 색 변환
차이가 수치로 확정됐습니다.

- 34패치 중 21개가 비율 1.000, 최대 편차 0.04%. 중간톤·하이라이트·프라이머리·스킨톤은 동일합니다.
- 깊은 섀도우 한 구간에서만 갈리며 device 값 0.005 에서 20.37배입니다.
- 원인은 intent 도 black point compensation 도 아닙니다. Windows ICM 은 프로파일이 선언한 감마를
  사양대로 적용하고, macOS ColorSync 는 0.0991 아래를 기울기 1/16 직선으로 대체합니다.
- 현상 후 8비트 sRGB 코드로 2~6 차이가 남고, 채널이 균등하게 밀리지 않아 최대 5코드의 하이라이트
  색상 캐스트가 생깁니다.

즉 두 플랫폼이 같은 스캔에서 미묘하게 다른 그림을 냅니다. 이것을 지금 맞출지 결정해야 합니다.

## 먼저 정리되는 것

**CMS 교체는 해법이 아닙니다.** LittleCMS 는 ICC 사양을 구현하므로 ICM 과 같은 거듭제곱 결과를 냅니다.
차이의 원인은 Windows 쪽 CMS 선택이 아니라 ColorSync 가 사양에서 벗어나 있다는 사실입니다.

따라서 `progress/overall-roadmap.md` 의 "차이가 허용 범위를 넘을 때만 LittleCMS 를 dependency gate 에
올린다" 항목은 이 사안에 대해 폐기합니다. ADR-0004 의 OS 우선 결정과 네이티브 엔진 제3자 runtime
dependency 0개는 이 사안 때문에 흔들리지 않습니다.

남는 선택지는 둘입니다.

1. ColorSync 의 toe 를 Windows 에서 재현한다.
2. 사양대로 두고 측정된 플랫폼 차이로 문서화한다.

## 결정

**2번을 택합니다. 지금은 재현하지 않습니다.**

## 근거

**측정 범위가 한 종류의 프로파일뿐입니다.** 이번 fixture 는 `curv` 태그의 `count = 1`, 즉 감마 하나짜리
순수 거듭제곱 TRC 입니다. 실제 스캐너 프로파일은 다점 `curv` 테이블이나 `para` 파라메트릭 커브를 쓰는
경우가 많습니다. **ColorSync 가 그런 곡선에도 같은 16:1 게인 제한을 거는지는 측정하지 않았습니다.**
한 종류에서 관측한 규칙을 모든 프로파일에 적용하는 것은 근거를 넘어서는 일반화입니다. 잘못 일반화하면
지금 맞는 경로까지 틀어집니다.

**크기가 긴급하지 않습니다.** 8비트 코드 2~6, 그것도 하이라이트에 한정됩니다. 이미지가 깨지는 수준이
아니라 나란히 놓고 봐야 보이는 차이입니다.

**색 경로가 아직 확정되지 않았습니다.** 제품은 M0~M18 중 약 15% 지점이고 GPU/WARP 경로(M5)는 착수
전입니다. GPU 가 들어오면 색 변환 경로가 다시 바뀝니다. 확정되지 않은 경로 위에 의도적 사양 이탈을
먼저 심는 것은 순서가 틀렸습니다.

**되돌리기 쉬운 쪽을 택합니다.** 문서화는 나중에 재현으로 바꿀 수 있습니다. 반대로 지금 재현해 두면
출력이 바뀌고, 그 위에 사용자 recipe 가 쌓인 뒤에는 되돌리는 비용이 훨씬 큽니다.

## 재검토 조건

다음 중 하나라도 성립하면 이 결정을 다시 엽니다.

1. **다점 `curv` 또는 `para` TRC 프로파일로 같은 측정을 했더니 ColorSync 가 거기서도 같은 게인 제한을
   건다.** 이것이 가장 중요한 후속 실험이며, 성립하면 재현 쪽 근거가 크게 강해집니다.
2. 실제 스캐너 프로파일과 실제 필름 스캔으로 잰 하이라이트 캐스트가 8비트 코드 6 을 넘는다.
3. 톤 커브를 실제 값으로 태웠을 때 차이가 확대된다. 이번 측정은 톤 identity 상태입니다.
4. 두 플랫폼 출력이 같아야 한다는 제품 요구가 명시적으로 생긴다.

## 재현하기로 할 경우의 방법

미리 적어 둡니다. 결정이 바뀌었을 때 다시 조사하지 않기 위해서입니다.

ICM 에 넘기기 전에 source 프로파일의 TRC 를 같은 하한으로 다시 쓰는 방식입니다. 우리 코드 안에서
끝나며 새 의존성이 없습니다. `x` 가 device 값일 때 출력은 `max(x / 16, x^gamma)` 이고, 두 식은
`x = (1/16)^(1/(gamma-1))` 에서 연속입니다.

이 형태 자체는 공개된 표준 기법입니다. sRGB 전달 함수가 같은 구조이고 ICC 파라메트릭 커브 타입 3/4 도
직선 구간을 갖습니다. 맞추는 것은 상수 하나(1/16)뿐이며 Apple 의 코드나 표현을 옮기는 것이 아닙니다.
다만 ADR-0021 이 macOS 관측을 test-only 로 한정했으므로, 제품 코드에 상수를 넣는 시점에는 그 경계를
명시적으로 확장하는 판단을 함께 기록해야 합니다.

## 결과

- 현재 Windows 색 경로는 그대로 둡니다. 코드 변경 없음.
- 차이는 측정값과 함께 문서로 남습니다. 나중에 "왜 다르지"를 다시 조사하지 않습니다.
- LittleCMS 검토 항목은 이 사안에 한해 닫힙니다.
- 다음 색상 작업은 재현이 아니라 **다점 TRC 프로파일 측정**입니다.

## 검증 한계

측정은 x64 Windows 11 26200 과 macOS 26.5.0 각 한 대에서 수행했습니다. ARM64 Windows 와 다른 macOS
버전은 확인하지 않았습니다. 합성 패치 34개는 실제 스캔의 밀도 분포를 대표하지 않습니다.
