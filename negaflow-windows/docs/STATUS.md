## 2026-08-15 적외선이 검출부터 복원까지 닫혔습니다

IR 사슬 전체가 실기로 이어집니다 — 스캔 → 가져오기 → IR 적용 → 레시피 → 현상 → 내보내기.
복원을 켜고/끄고 낸 두 파일을 비교했고, **결과는 정상입니다.**

| 임계 | 화소 | 전체 대비 |
| --- | ---: | ---: |
| 65535 중 100 초과 | 24,123 | **0.417%** |

검출이 보고한 결함 면적이 **0.4179%** 입니다. 크게 바뀐 화소가 결함 자리와 세 자리까지
일치합니다. 나머지 화소는 6~15(만분의 일) 움직이며, 이는 IR 채널의 자연 편차가 만드는 이득

**이 조사에서 남길 것.** 원인을 세 번 지목했고(검출기 · 복원 가드 · 감쇠 적용 범위) 셋 다
정상 코드였으며 결함도 없었습니다. 처음에 **"몇 개가 바뀌었나"** 라는 잘못된 지표를 고른
탓입니다. **"얼마나 크게 바뀌었나"** 를 물었어야 했고, 그 한 번의 측정이 소스를 세 번 읽는
것보다 빨랐습니다. 증상이 확실할수록 지표부터 의심할 것.

## 2026-08-15 적외선 채널이 실기에서 나옵니다

**IR 이 끝났습니다.** Epson V700(GT-X900)에서 플러그인이 별도 IR 패스를 돌려 16-bit 1채널
TIFF 를 받습니다 — `hasInfrared: true`, 본 스캔과 같은 424×283. IR 값은 min 9 / median 40 /
max 65,411 로 **65535 에 몰려 있지 않습니다**. macOS 가 감마 없이 찍었을 때 보고한 "프레임의
2~3.4% 가 65535 에 잘린다" 는 상태가 아니므로, `3d9c3d3` 이식이 이 장치에서 유효합니다.

막힌 곳이 세 번 있었고 **셋 다 다른 자리**였습니다. 값이 있어 적어 둡니다.

1. **빌드는 성공하는데 기능만 사라졌습니다.** epson2 가 이미 깔려 있던 옛 `sane.h` 로
   컴파일돼 `SANE_FRAME_IR` 이 정의되지 않았고 모드 목록 항목이 통째로 빠졌습니다. 로그에는
   아무 말도 없습니다 — 만든 DLL 에서 문자열을 찾아야 보입니다. PKGBUILD 가 소스 트리의
   include 를 최우선으로 두도록 고쳤습니다.
2. **백엔드만 바꾸고 프론트엔드를 안 바꿨습니다.** IR 파일 크기가
   `239,984 = 424 × 283 × 2` 로 화소 데이터와 정확히 같았습니다 — 헤더가 0바이트라는 뜻이고,
   패치 009 의 두 번째 헝크가 없는 옛 `scanimage.exe` 가 돌고 있었습니다.
3. **시험이 틀렸습니다.** 감마가 IR 에서 거부되는 줄 알았는데 그 값이 이 장치 목록에 없었을
   뿐입니다. 올바른 값으로는 IR + 감마 + 초점이 전부 정상입니다.

**아직 아닌 것: 필름을 올리지 않은 스캔입니다.** IR 이 실제 결함을 짚는지, 그 지도가
GrainMend 복원과 화소 단위로 맞는지는 확인하지 않았습니다.

## 2026-08-15 색 관리 — 소프트 프루프와 색역 경고

macOS 설정의 색 관리 구획을 같은 순서로 옮겼습니다. 소프트 프루프 토글, 프루프 시뮬레이션,
색역 경고, 그리고 값 줄(스캐너 에뮬레이션 / 작업 공간 / 내보내기 / 소프트 프루프).

**색역 판정은 ICM 이 합니다** — `CreateMultiProfileTransform` 에 `ENABLE_GAMUT_CHECKING` 을
주고 `CheckBitmapBits` 로 화소당 1바이트를 받습니다. **행렬 뒤 클리핑으로 근사하지
않습니다**: macOS 가 그것을 명시적으로 거부하며, 근사하면 같은 그림에서 다른 화소가
표시되어 이식이 아니라 다른 기능이 됩니다. 표시 색도 macOS 와 같은 빨강 alpha 166 입니다.

첫 판정에서 sRGB 를 sRGB 로 봤는데 흰색과 검정이 색역 밖으로 나왔습니다. macOS 가 같은 것을
겪고 적어 둔 대로, **판정 전용 사본만 1 LSB 안쪽으로** 밀어 고쳤습니다. 고친 뒤 회색·흰색·
검정은 안쪽이고 순수 빨강 원색 꼭짓점만 남습니다 — 시험을 통과시키려 값을 늘리지 않고,
명백히 안쪽인 색과 넓은 목표 공간만 주장합니다.

ICM 이 변환을 만들지 못하면 **아무것도 칠하지 않고** 토글도 켜지지 않습니다.

**아직 아닌 것:** 프루프용 ICC 파일을 고르는 줄이 없습니다. 프로파일 이름은 내보내기
색공간으로 대체되며, 이는 macOS 가 프로파일 미선택 시 보여주는 것과 같습니다.

## 2026-08-14 스캐너가 실제로 돌았습니다 — 두 대, 플러그인만으로

**"실장치 검증 0회" 가 끝났습니다.** Plustek OpticFilm 8100 과 Epson Perfection V700 이 둘 다
detect → capabilities → scan 전 구간을 돕니다. 8100 은 600dpi 16bit 848×566 을 16.4초, V700 은
300dpi 16bit 424×283 을 46초에 냅니다. V700 은 SANE 이 내부명 **GT-X900** 으로 보고합니다.

**플러그인이 자립합니다.** 8100 이 그동안 열린 이유는 SilverFast 가 깔아 둔 `oem113.inf` 가 그
장치를 Windows 자신의 `usbscan.sys` 에 묶어 놓았기 때문이지 플러그인의 공이 아니었습니다. 이제
플러그인이 자기 INF 를 갖고, **SANE 의 기기표(`doc/descriptions/*.desc`)에서 생성한 332종**을
덮습니다 — 손으로 적은 목록이 아니므로 다른 OpticFilm 이나 다른 Epson 평판도 같이 붙습니다.
바이너리는 하나도 설치하지 않고 `Include=sti.inf` 로 Windows 가 이미 가진 파일을 가리킵니다.
서명은 설치 스크립트가 자체 서명 인증서로 처리하며 테스트 서명 모드가 필요 없습니다.

이 과정에서 **한 번 스캐너를 못 쓰게 만들었습니다.** 설치가 되는지 확인하기 전에 벤더 INF 를 먼저
지우게 했고, 서명이 없어 설치가 실패해 장치가 드라이버 없이 남았습니다. 스크립트는 이제 **설치가
성공해야만** 다른 것을 건드립니다. 실패하면 기계는 발견한 그대로 남습니다.

**초점이 실기로 확인됐습니다.** V700 옵션 덤프에 `--autofocus` 와 `--focus 0..254` 가 실제로
있고, 같은 자리를 0 과 254 로 찍으니 SHA-256 이 다릅니다(`070ECA25…` 대 `7800F6C3…`). Windows
어댑터에는 초점 개념 자체가 없었으므로, macOS 에서 이식한 것이 픽셀까지 닿은 것입니다. IR 패스
감마 테이블도 같이 이식했으나 **그쪽은 실기 검증이 없습니다.**

**IR 은 원인이 확정됐고 패치를 넣었습니다.** epson2 는 GT-X700/X800/X900/X980 의 적외선을 이미
완전히 구현해 두었고(V700 이 GT-X900), 막고 있는 것은 `SANE_FRAME_IR` 이 `sane.h` 의 `#if 0` 안에
갇혀 있는 것뿐입니다. 플러그인 저장소의 패치 009 가 상수를 꺼내고, `scanimage` 가 IR 프레임을
`default: break;` 로 흘려 **헤더 없는 파일**을 쓰던 것도 같이 고칩니다. 1.4.0 소스에 dry-run 으로
적용을 확인했습니다. **빌드는 돌리지 못했습니다** — 이 기계에 MSYS2 의 `makepkg-mingw` 와 빌드
툴체인이 없습니다. 그러므로 **V700 이 IR 채널을 낸다고 말하지 않습니다.**

**실제 필름으로 프레임 검출을 확인했습니다.** V700 프리뷰 10장에서 적재량이 검출 행 수로 그대로
나옵니다 — `_1slot` 6컷, `2x2slot` 12컷, 전체 18컷. 합성 스트립에는 빈 슬롯이 없어 확인할 수 없던
부분입니다. 다만 **사각형이 실제 컷 자리에 맞는지는 확인하지 않았습니다.**

## 2026-08-14 내보내기 메타데이터 정책

게시 파일에 **아무 메타데이터도 들어가지 않던 상태**를 끝냈습니다. ABI 0.47 / v33 이 정책과 값을
싣고, WIC `IWICMetadataQueryWriter` 로 프레임 커밋 전에 씁니다. 실촬영 스캔에서 정책만 바꿔 세 번
내보내 IFD 를 읽었습니다 — `copyrightOnly` 는 스캐너·소프트웨어·날짜·EXIF 하위 IFD 를 실제로
지우고 권리 표시만 남깁니다. Orientation 은 어느 정책에서도 1 입니다(기하가 픽셀에 구워져 있음).

**JPEG 에서는 조용히 버려지고 있었습니다.** WIC 의 JPEG 인코더는 `WriteSource` 뒤에 들어온
메타데이터를 버립니다. TIFF 는 받아들여서, 같은 코드가 TIFF 에는 태그를 가득 넣고 JPEG 에는 APP1
세그먼트조차 만들지 않았습니다. 실파일을 열어 `Exif` 마커를 찾기 전에는 보이지 않았습니다.

TIFF 검증기 허용 목록에 일곱 태그를 넣으며 **버그를 하나 만들었다가 잡았습니다** — 목록은
`binary_search` 로 찾는데 뒤에 붙였더니 254 를 못 찾아 TIFF 게시가 통째로 막혔습니다. 번호 순서로
정렬해 고쳤습니다. 기존 시험 하나가 "허용 목록이 Make 를 거부한다" 를 보고 있었는데 이제 일부러
쓰는 태그이므로 **GPS IFD 거부**로 바꿨습니다 — 위치가 새는지 보는 편이 값집니다.

**원본 메타데이터 복사는 만들지 않았습니다.** 사용자 파일 세 종류(OpticFilm 스캔, V700 프리뷰,
플러그인 출력)를 재 보니 **서술 태그가 하나도 없고** 구조 태그 16개뿐입니다. 복사 코드를 만들어도
이 파일들에서 옮길 것이 없어, `removeLocation` 과 `all` 이 현재 같은 결과를 냅니다. 카메라 JPEG
같은 소스가 들어올 때 의미가 생깁니다.

## 2026-08-14 출력 색공간 — 색 변환과 ICC 생성

**출력 색공간의 색 부분이 생겼습니다.** 선형광에서 3×3 행렬로 목표 primaries 로 옮기고, 목표의
전달 곡선으로 부호화하며, 그 공간의 ICC 프로파일을 만듭니다. 세 공간(sRGB · Display P3 ·
Adobe RGB)은 모두 D65 이므로 **픽셀에는 색순응이 들어가지 않습니다** — D50 Bradford 적응은
프로파일의 XYZ 태그에만 들어갑니다. ICC 의 연결 공간이 D50 이어서지 그림이 D50 이어서가 아닙니다.

**프로파일은 직접 만듭니다.** Windows 는 sRGB 프로파일은 갖고 있지만 Display P3 와 Adobe RGB 는
갖고 있지 않습니다. 있을지 없을지 모르는 파일을 내보내기의 전제로 삼을 수 없습니다. v2
matrix/TRC 에 태그 아홉 개이며, 세 프로파일 모두 **스캐너 프로파일에 쓰는 것과 같은 검증기**를
통과합니다.

**검사가 한 번 틀렸고, 그 틀림이 기록할 값이 있습니다.** 처음에 "넓은 공간으로 옮기면 대각 항이
1 보다 작아야 한다" 고 적었는데, Adobe RGB 의 초록 대각은 정확히 1.0 입니다. 우연이며, 같은 열의
빨강 0.2849·파랑 0.0412 가 함께 있어야 sRGB 초록이 됩니다. 지금 검사는 대신 **넓은 공간에서
sRGB primary 를 내려면 그 공간의 primary 가 덜 필요하다**와 **공유하는 primary 는 다른 채널을
섞지 않는다**를 봅니다. 계산된 행렬과 그 해석은
`verification/2026-08-14-output-color-space-matrices.md` 에 적었습니다.

native 68/68 통과(새 시험 `native.output_color_space` 포함).

## 2026-08-14 프리뷰 픽셀 캡처와 자동 프레임 찾기

**프리뷰가 더 이상 카탈로그에 올라가지 않습니다.** 프리뷰는 판을 보려고 찍는 것이지 사용자의
사진이 아닙니다. gateway 에 스캔만 하고 게시하지 않는 길(`ScanAsync`)을 내고, 프리뷰는 그 길로

읽지 못한 프리뷰는 없는 프리뷰로 다룹니다. 찾은 척하지 않습니다.

**프리뷰가 끝나면 자동으로 찾습니다.** 찾기 방식이 자동이면 프리뷰 직후 프레임을 세어 판 위에
놓고, 수동이면 사용자가 놓은 자리를 건드리지 않습니다. 새로고침 단추는 이제 프리뷰가 있으면

카탈로그 수를 늘리지 않는지, 파일을 남기는지, 그리고 그 실행이 성공으로 보고되는지입니다.

**여전히 확인하지 않은 것.** 실제 필름 스캐너로는 한 장도 스캔하지 않았습니다. 그리고 자동 프레임
찾기가 **실제 필름이 놓인 평판 프리뷰**에서 몇 개를 어떻게 찾는지는 확인하지 않았습니다 —
시뮬레이터의 합성 그림에는 필름 스트립이 아니라 한 장짜리 장면이 들어 있어, 검출기가 세는 대상이
실제와 다릅니다.

## 2026-08-14 8-bit PNG/TIFF 출력과 출력 디더

**ABI 0.45 / v31** 이 `output_bit_depth`(8 또는 16)를 append-only 로 더합니다. PNG 과 TIFF 가
이 값을 지키고, JPEG 은 정의상 8-bit 이라 무시하며, preview 는 출력 전용 값을 전부 무시합니다.

**8-bit 은 양자화 직전에 디더를 겁니다.** macOS `OutputDither` 와 같은 자리·같은 크기입니다 —
양자화가 일어나는 sRGB 인코딩 공간에서 ±0.5/255 백색 잡음을 더해, 매끄러운 그라디언트의 경계
픽셀이 인접 스텝으로 흩어지게 합니다. 밴딩이 stipple 로 보이고 디테일과 평균 톤은 보존됩니다.
16-bit 에는 걸지 않습니다 — macOS 도 8-bit 출력에만 겁니다.

잡음은 macOS 의 `CIRandomGenerator` 대신 **절대 좌표의 해시**입니다(grain 단계와 같은 mix).
Apple 의 생성기는 문서화돼 있지 않아 비트 단위로 재현할 수 없고, 우리 쪽은 재현성이 **필수**입니다 —
게시 뒤 readback 검증이 같은 변환을 다시 돌려 바이트 단위로 비교하므로, 행 블록을 어떻게 나누든
같은 값이 나와야 합니다. 백색 잡음이라는 성질과 진폭은 같습니다.

**16-bit 경로는 바이트 하나 바뀌지 않았습니다.** 같은 입력·같은 설정의 16-bit TIFF SHA-256 이
이 작업 전과 같습니다(`DF74FA5B…9053`).

실촬영 확인(5088×3401 OpticFilm 8100, 긴 변 2048·300 DPI·LZW·선명도 0.5):

| 출력 | 결과 |
| --- | --- |
| TIFF 16-bit | 21,987,848 바이트, SHA `DF74FA5B…9053` (이전과 동일) |
| TIFF 8-bit | 8,671,578 바이트, BitsPerSample 태그 확인 |
| PNG 8-bit | 4,796,832 바이트, IHDR bit depth 8 · colour type 2 |

게시 전 readback 검증이 8-bit 에서도 그대로 돕니다 — 디코드한 픽셀이 같은 디더 변환의 결과와
바이트 단위로 같아야 파일이 공개됩니다. PNG 구조 검사는 8 과 16 만 받고, TIFF 는 IFD 의
BitsPerSample 세 칸이 고른 깊이와 같은지 봅니다.

검사: native 67/67, interop contract 198 assertions(실제 DLL ABI 0.45/x64), catalog 710,
shell 642 통과.

**품질 탭에 비트 심도 줄이 붙었습니다.** macOS 처럼 형식마다 따로 기억합니다 — 보관용 TIFF 는 16,
화면용 PNG 는 8 로 두는 사람이 형식을 오갈 때마다 다시 고르지 않아야 합니다. JPEG 에서는 고를
것이 없으므로 줄이 사라집니다.

**아직 없는 것.** 알파 보존과 출력 색공간입니다. Working image 가 불투명 RGB 이므로 알파를 켜도
언제나 255 인 채널이 하나 늘 뿐이고, 색공간은 인코더가 sRGB ICC 만 붙입니다.

## 2026-08-14 Pending restore Defects 교체 중단 복구

pending restore는 새 Defects directory를 live로 올린 뒤 catalog를 commit합니다. 이 둘 사이에 process가
중단되면 이전에는 남은 `.previous` artifact 때문에 다음 시작도 막혔습니다. 이제 새 live directory가
pending manifest의 sidecar 집합과 정확히 같으면 직전에 만든 safety generation을 그대로 보존한 채 catalog
commit·applied marker·cleanup만 재개합니다. 첫 directory move 뒤 중단은 old Defects를 write-through move로
되돌린 뒤 다시 준비하며, 모호하거나 reparse point·비정상 파일을 포함한 artifact는 여전히 fail-closed입니다.

Catalog test는 selected generation과 current generation에 각각 Defects sidecar를 만든 뒤, 실제 Defects
교체만 실행하고 의도적으로 commit/rollback/marker 갱신을 생략했습니다. 다음 `CatalogSession.Open`이 selected
catalog와 sidecar를 다시 결합하고 swap artifact를 정리하는 것을 확인했습니다. x64 Debug Catalog 698
assertions를 통과했습니다. disk-full·실제 power-loss와 다른 transaction 경계 process-kill은 아직 없습니다.

x64 Debug에서 `native.grain_mend`는 선택한 0.25,0.25,0.5,0.5 ROI가 top-first `(24,18,48,36)`만
분석함을 확인했고, 전체 native CTest는 **65/65** 통과했습니다. `native.develop_export_abi`는 실제
TIFF에서 v2 크기 조회와 마스크 호출이 같은 원본 ROI를 보고함을 확인했습니다(1/1, 27.77초).
관리형 전체 게이트는 Catalog 684·Shell 540 assertions, 실제 DLL interop contract는 ABI 0.39/x64
191 assertions를 통과했습니다. Shell 검사는 별도 성분을 클릭해 하나를 제외하면 그 성분의 RGBA8
마스크만 0이 되고, 전부 제외하면 수락 항목이 사라지는 것을 확인합니다. 렌더된 가이드 UI를 실제
WinUI 창에서 드래그·성분 클릭·제거/취소까지 관찰한 증거와 macOS 동일 입력 pixel golden, 순수
ARM64 Windows 실행은 아직 없습니다.

세 조각으로 나눠 각각 시험했습니다. **좌표 되돌리기**(`DevelopDisplayGeometry`)가 가장 위험한
자리입니다 — 결함 편집은 원본 이미지의 정규 좌표·좌상단 원점으로 저장되는데 캔버스가 주는
점은 변형이 다 적용된 표시 좌표라, 그냥 이으면 회전·크롭이 걸린 프레임에서 엉뚱한 화소를
지웁니다. 네이티브가 적용하는 orient → straighten → crop 세 단계가 모두 "출력 → 입력" 식이라
같은 식을 그대로 이어 붙였고, 항등·반전·90도·180도·크롭(저장은 y-up)·수평보정·복합 변형까지
13 개 어서션으로 확인했습니다. **획 만들기**(`DefectStrokeRecipeBuilder`)와 **저장 경로**는
실제 파일로 확인했습니다 — 획 하나가 sidecar 와 catalog 를 지나 엔진 요청의
`DefectBrushes` 까지 도달하고, 두 번째 획이 앞 획을 지우지 않으며, 도구별 초기화가 다른
도구의 편집을 남깁니다.

**캔버스에서 실제로 그어 확인했습니다.** 실제 스캔을 씨앗으로 넣고 현상 화면에서 사진을
고른 뒤(미리보기 2360×1577 렌더 확인), 브러시를 켜고 캔버스를 끌었더니 결함 sidecar 가
1개 생기고 도구별 초기화 단추가 켜졌습니다.

한동안 미리보기가 안 그려지는 줄 알았는데 원인은 검증 스크립트였습니다 — BOM 없는 `.ps1` 을
PowerShell 5.1 이 CP949 로 읽어 한글 경로가 깨진 채 카탈로그에 심겼고, 앱은 없는 파일을
정확히 그대로 보고하고 있었습니다. 그 과정에서 미리보기 실패 이유를 캔버스 아래에 내도록
고쳤습니다. 전에는 현상 실패와 사진 없음이 같은 빈 화면이라 구별되지 않았습니다.

**정보 탭에 내용이 생겼습니다.** 여섯 인스펙터 탭 중 하나가 아무것도 내지 않고 있었습니다.
macOS 와 같은 여섯 줄(원본·Sidecar·카메라·날짜·제목·키워드)이며, 지금 확실히 아는 것만
값으로 냅니다 — 원본은 출처와 파일명, Sidecar 는 옆에 `.xmp` 가 없으면 "없음", 있으면
"미확인"입니다. 읽지 않은 것을 "읽음"이라고 하지 않기 위해서입니다. 카메라·날짜·제목·키워드는
EXIF/IPTC 를 아직 읽지 않으므로 macOS 의 빈 상태와 같은 "— · —" 입니다.

**자동 GrainMend 세기를 보존합니다.** `params.defectRemoval` 을 읽고 쓰고 엔진 요청에 싣습니다.
macOS 앱 UI 에는 이 슬라이더가 없고 CLI·프리셋·붙여넣기로만 들어오는데, 값을 버리면 그렇게
들어온 frame 이 Windows 에서 다르게 현상됩니다.

**흑백 토닝이 닿게 됐습니다.** 네이티브 엔진(`imaging/bw_toning.cpp`)과 ABI 는 진작 구현돼
있었는데 catalog recipe 가 없어 요청에 실을 값 자체가 없었습니다. `params.bwToning` 로
macOS 와 같은 네 값(mode·shadowHue·highlightHue·strength)을 저장하고, 흑백 필름에서만 나오는
섹션을 컬러 그레이딩과 캘리브레이션 사이에 두었습니다. 미묘한 규칙 둘을 그대로 옮겼습니다 —
색조 키가 없으면 0 이 아니라 **그 모드의 기본 색조**(sepia 32/48, selenium 285/34)이고, 모드를
켤 때 세기가 0 이면 최소 0.45 로 올립니다(0 인 채로 켜면 아무 일도 일어나지 않아 고장으로
보입니다). 실제 흑백 스캔으로 확인했습니다: 세피아를 고르니 세기 0.45, 색조 32/48 이 붙고
다시 띄워도 남아 있었습니다.

**현상 편집이 앱을 닫아도 남습니다 — 이번 세션에서 찾은 가장 큰 결함입니다.** 슬라이더 편집은
메모리에만 있었고, 카탈로그 저장은 내보내기·버전 담기 같은 몇몇 동작에서만 일어났으며, 창을
닫는 경로는 세션을 그냥 놓아 주었습니다. 그래서 노출·색·질감을 아무리 만져도 내보내지 않고
끄면 전부 사라졌습니다. `LibraryDocument` 가 마지막 저장 이후 변경 여부를 들고, 편집 셋이
모두 지나는 `LibraryHostService` 의 한 자리에서 macOS 와 같은 1.5 초 지연 저장을 예약하며,
창을 닫을 때 예약이 남아 있으면 마지막으로 씁니다. 예약 자리를 호출부가 아니라 host 에 둔
이유는 프리셋 합성과 같습니다 — 한 군데만 빠져도 그 편집이 조용히 사라지기 때문입니다.
실제 스캔 두 장으로 확인했습니다: 색온도 0.42 로 바꾸고 0.6 초 뒤(지연 저장이 울리기 전)
창을 닫았다가 다시 띄우니 0.42 가 그대로 있었습니다.

**룩 프리셋이 현상 파이프라인에 걸렸습니다.** frame 은 macOS 와 같이 `presetID` 를 `params`
바깥에 들고, `DevelopRequestFactory` 가 엔진 요청을 만들면서 프로파일과 사용자 값을 합칩니다.
합성 자리를 팩토리 한 곳으로 잡은 것이 핵심입니다 — preview·thumbnail·export 가 전부 이
함수를 지나므로 세 경로가 같은 레시피를 쓴다는 계약이 구조로 지켜집니다. 축마다 합치는 법이
다르고 그 차이가 곧 룩입니다: 톤·색은 더하고, grain·sharpness·halation 은 큰 쪽을 쓰며(프리셋이
넣은 질감이 사용자 0 에 지워지지 않도록), 프로파일이 정하지 않는 축은 사용자 값 그대로입니다.
`highlightRollOff` 는 macOS 가 과거 버그로 기록해 둔 부호 반전까지 그대로 옮겼습니다.

**현상 설정 복사/붙여넣기와 사용자 프리셋을 붙였습니다.** 다섯 붙여넣기 묶음(베이스·기본 톤·
색상·디테일·편집)과 각 묶음에 무엇이 드는지가 macOS 와 같고, 프리셋은 톤과 함께 움직입니다.
frame 의 신원·출처와 `DefectRecipe` 는 옮기지 않습니다 — 결함 편집은 그 이미지의 좌표와 원본
해시에 묶여 있어 다른 사진에 옮기면 엉뚱한 자리를 지웁니다. 사용자 프리셋은 레시피를 frame
record 모양으로 담아 앱 데이터 폴더의 JSON 하나에 두며, 저장·적용이 붙여넣기와 같은 writer 를
지납니다. 실제 앱에서 프리셋 탭의 컨트롤과 범위 메뉴가 다국어 리소스로 뜨고 프레임이 없을 때
비활성인 것까지 확인했고, 붙여넣기가 저장·재시작을 넘겨 살아남는 것도 재 봤습니다. 사진 두
장으로 눌러 보는 확인은 아직 하지 않았습니다.

**현상 프로세스를 고를 수 있게 됐습니다 — 이번 세션에서 찾은 가장 큰 공백입니다.** 가져오기가
전부 C-41 로 못박혀 있었고 셸에 바꿀 길이 없어서, macOS 여섯 프로세스 중 다섯(E-6, D-76,
B&W Reversal, Digital Color, Digital B&W)에 **영영 닿을 수 없었습니다.** 필름 룩도 digital
source 에서만 걸리므로 함께 막혀 있었습니다. 라이브러리 폴더 머리줄에 macOS 와 같은 자리·같은
여섯 항목·같은 이름의 선택기를 두었고, 고르면 그 폴더에 적용하고 저장합니다.
`DevelopPanelState.SetDevelopmentProcess` 와 macOS 유도 규칙(디지털 표시는 포지티브에만)을
따르는 reader 를 더했습니다. 프로세스를 바꿔도 고른 필름과 세기는 유지합니다.

**42종 필름 에뮬레이션을 드디어 고를 수 있습니다.** 엔진은 M2 부터 전부 갖고 있었는데 셸에
고르는 자리가 없어 카탈로그를 손으로 고치지 않는 한 쓸 수 없었습니다. 현상 왼쪽 필름 소스가
macOS 순서로 냅니다 — None 먼저, 그다음 그 필름 종류의 묶음(컬러는 슬라이드·음화·시네, 흑백은
반전·음화)이고 위에 강도 슬라이더가 있습니다. macOS 처럼 digital source 에서만 고를 수 있고
스캔 프레임에는 같은 안내 문장을 냅니다. 스캔 route 에 룩을 걸려 하면 기록하지 않고 거부합니다.
route 편집 경로가 따로 필요해(recipe 는 `LibraryFrameWriter`, route 는 `DevelopRouteWriter`)
`LibraryDocument.EditRoute` / `LibraryHostService.EditRoute` 를 더했습니다.

현상 왼쪽에 출력 소스가 붙었습니다. 지금까지 내보내기는 원본 옆에 `<원본>-negaflow.png` 하나만
쓸 수 있었는데, 이제 형식(TIFF/PNG)·폴더·파일명 패턴을 정하고 실제 파일명을 미리 보고 내보냅니다.
목적지 규칙은 `ExportDestination` 에 있어 창 없이 시험됩니다 — 폴더가 비면 원본 옆, 패턴이 비면
원본 이름, 패턴 속 경로 문자는 치환합니다. 토큰은 `{name}` 하나만 냅니다(나머지는 projection 이
읽지 않는 값이 필요합니다).

**검증:** x64 Debug 로 실제 앱을 띄워 라이브러리 격자·소스 트리·현상 화면·필름스트립·crop

확인했습니다. 출력 패널에서 실촬영 프레임을 실제로 내보내 631×403 48bpp TIFF 가 나왔고 원본

프로세스 전환과 필름 룩의 **핵심 경로는 단위 시험으로 증명했습니다**(Shell 462 assertion):
C-41 스캔 → Digital Color 로 바꾸면 필름 룩이 열리고 → Ektar 100 을 고르고 → D-76 으로 바꾸면
룩은 다시 닫히되 **고른 필름은 남습니다.** 42종 목록·묶음·표시 이름, 강도 clamp, 스캔 route

**화면에서도 끝까지 확인했습니다.** 앞서 "자동화로 항목 선택이 먹지 않는다"고 적었던 것은
코드가 아니라 하네스 문제였습니다 — 팝업을 연 PowerShell 프로세스와 항목을 고른 프로세스가

확인한 연쇄:

1. 폴더 머리줄 선택기가 여섯 항목을 내고, Digital Color 를 고르면 그 폴더에 적용·저장됩니다

확인 뒤 필름 룩을 없음으로, 프로세스를 C-41 로 되돌렸고 실촬영 현상 지문이
`561D12AF…` 그대로임을 다시 확인했습니다.

받아들입니다(900×600 RGBA16 orient=1). 가져오기에서 나온 "not a supported TIFF image" 는
JPEG 미지원이 아니라 파일 대화상자가 다른 파일을 돌려준 결과입니다.

## 2026-08-12 Scanner plugin host foundation

Windows scanner adapters now have the first executable host boundary instead of only a design
document. Discovery accepts only bounded non-reparse plugin directories with a schema-v1,
protocol-v1/v2 scanner manifest; it records SHA-256 identities for both manifest and executable
and rechecks the approved identity immediately before launch. The process boundary passes
structured arguments, bounds stdout/stderr and NDJSON line sizes, applies operation-specific
timeouts, and kills the child process tree on cancellation or timeout. The reachable operations
are `detect`, `capabilities`, and `scan`: an approved adapter returns a bounded, unique device
list and then the device's exact resolution, mode, bit-depth, optional-IR, and output capability
set. A scan now emits the macOS v2 wire names, request ID, capability token, and host-owned
sibling staging path; its one terminal event must echo every applied option before the TIFF/IR
pair can be accepted. The artifact transaction rejects reparse paths, non-TIFF or
metadata-mismatched RGB/IR files, publishes IR before RGB with rollback, and never overwrites a
destination. Protocol-v2 progress/result/error streams are checked for request ID, strict
sequence, finite progress range, and exactly one terminal event.

The v2 result's reported dimensions, bit depth, and applied color mode now also constrain the
staged TIFF before publication, so a gray/line-art scan is no longer rejected by an RGB-only
artifact gate and an adapter cannot publish a differently configured TIFF under an accepted
result event.

x64 Debug/Release managed checks passed Catalog 605 and Shell 413 assertions with no build
warnings or errors. x64 Release native CTest passed 65/65. The complete ARM64 Release graph
cross-built, but was not executed on ARM64 hardware. `ScanAndPublishAsync` passes only the
verified committed TIFF/IR pair to the existing single-writer `LibraryHostService` boundary,
which persists the frame before optional IR recipe bootstrap. If catalog publication fails, the
committed source pair is intentionally left intact and returned to the caller. The durable
startup receipt is described below; approval persistence, WIA/TWAIN adapters, and real-device
evidence are not implemented.

scanner host·실물 preview/macOS golden 연결은 아직 없습니다.

## 2026-08-12 GrainMend IR item replay — ABI v25

ABI v24의 flat cluster replay는 겹치는 IR cluster에서 같은 attenuation을 반복 적용해 macOS보다
과보정되는 P1 결함이 독립 검토에서 발견됐습니다. v24의 통과 결과는 이 결함 발견 전 결과이므로
완료 증거로 채택하지 않습니다.

IR item 경계를 보존하는 append-only ABI 0.32/v25를 완료했습니다. 모든 cluster correction은 같은
item-level base에서 계산하고 `bbox(attenuation > 0 ∪ core > 8)`의 전체 사각 patch만 원래 cluster 순서와
item strength로 합성합니다. cluster별 ROI scratch를 즉시 해제하고 bounded bbox patch만 보관해 대형 스캔의
whole-frame snapshot을 피합니다. v25는 item range의 contiguous·gapless·exact-once와 order 참조를 검증하고,
flat cluster 4,096개와 native expanded order 8,192개 상한을 하위 할당 전에 거부합니다.

fingerprint는 macOS canonical v2를 바꾸지 않고 attenuation 결합을 명시적 v3로 분리했습니다. v2 sidecar는
읽을 수 있으며 재저장 시 v3 identity로 이동합니다. 합성 TIFF의 v25 preview/export가 같은 recipe와 수학을
사용하고 8-bit 표시 양자화 최대 1 code 안에서 일치하며, 원본 bytes와 SHA-256이 변하지 않음을 확인했습니다.
x64 Debug/Release native 61/61, Catalog 592, Shell 336, Interop 169(ABI 0.32)가 통과했고 ARM64 Release native·
managed graph는 교차 빌드만 통과했습니다. 실제 ARM64 실행과 macOS-hosted pixel golden은 아직 없습니다.

## 2026-08-11 IR attenuation replay — ABI v24 사전 체크포인트(미채택)

최신 macOS의 비파괴 IR layer 계약을 post-baseline delta로 채택했습니다. Windows Defects sidecar v2는
기존 core mask와 별도로 optional compressed R16 attenuation을 보존하고, fingerprint·logical backup·
pending restore도 같은 authoritative bytes를 사용합니다. 필드가 없는 기존 sidecar는 mask-only
component repair로 계속 재생하며 손상 압축과 크기 불일치는 실패 폐쇄형으로 거부합니다.

Shell은 IR을 Region으로 접지 않고 ordered edit로 투영합니다. native pre-develop stage는
`RGB / max(1 - attenuation, 0.5)`를 먼저 적용한 뒤 core mask가 있으면 그 결과를 문맥으로 component
repair하고 item strength를 한 번만 혼합합니다. preview/export는 ABI 0.31의 같은 v24 request와 native
stage를 사용합니다. x64 Debug/Release native 61/61, Interop 163, Catalog 587, Shell 336 assertions가
통과했고 ARM64 Release 전체 graph의 순수 AA64 교차 빌드도 통과했습니다. ARM64 runtime 결과는 아닙니다.

이 체크포인트는 저장된 attenuation의 재생 경계입니다. 최신 macOS의 true-scale 후보 검출, local
alignment·visible confirmation, null/MAD, significance-dependent inverse-Mills bias, attenuation/core 분리,
scanner companion 입력·coordinator·WinUI와 동일 입력 macOS-hosted mask/R16/pixel golden은 남아 있습니다.
상세는 `verification/2026-08-11-ir-attenuation-replay-v24.md`입니다.

## 2026-08-10 macOS 커널 수식 대조

macOS pixel golden 은 macOS 호스트가 필요하지만, **Core Image 가 실행하는 Metal 커널 소스가
저장소 안에 있습니다.** 상수까지 1:1 로 대조했습니다.

Basic Tone, Parametric Tone Curve, Negative Inversion, Color Mixer, Color Grading, Primary
Calibration, B&W Toning, Texture 전체, Film Grain 이 **수식과 상수 모두 일치**합니다.
Film Grain 은 잡음원만 다릅니다(macOS `CIRandomGenerator` vs Windows 좌표 해시, 분포 동일).

차이는 하나 나왔고 표시 경계였습니다. 게시 경로는 오히려 Windows 가 맞았습니다 — macOS 도
8비트 출력에만 dither 를 겁니다. "macOS 에 있으니 옮긴다"로 갔으면 게시 결과를 잘못 바꿨을
것입니다. 상세는 `verification/2026-08-10-macos-kernel-audit.md`.

이 대조는 **부동소수점 결과의 동일성을 증명하지 않습니다.** 같은 수식이어도 Core Image GPU 와
Windows CPU 는 마지막 자리에서 다를 수 있고, 그건 여전히 macOS 호스트가 필요합니다.

## 2026-08-10 표시 경계 — soft clip과 dithering

macOS 소스 대조에서 미리보기 경로의 실제 차이를 찾았습니다. macOS는 8비트로 내리기 전에
`DisplayGamutMap`(hue-safe soft clip)과 `OutputDither`(±0.5/255)를 거치는데 Windows는 채널별
하드 클립과 `>> 8` 뿐이었습니다. 확장 범위 값이 색상을 끌고 잘리고, 매끄러운 하늘이
밴딩됐습니다.

`tone_safe_unit_rgb` 와 좌표 해시 dither 를 넣어 미리보기 경계를 맞췄습니다. **게시 경로는
바꾸지 않았습니다** — macOS도 8비트 출력에만 dither 를 걸고 Windows는 16비트만 게시하므로
현재 동작이 맞습니다. 실제 촬영본 export SHA-256이 그대로임을 확인했습니다. 미리보기는
전체 해상도 16비트 중간 이미지(17 MP에서 약 104 MB)도 더 이상 만들지 않습니다.
상세는 `implementation/display-boundary.md`.

## 2026-08-10 다중 IFD TIFF

사용자의 Photoshop TIFF 가 거부되던 원인은 사진이 아니라 **디렉터리가 두 개**라는 것이었습니다.
전체 이미지 뒤에 축소 미리보기가 붙는 흔한 배치입니다. `NewSubfileType` 으로 동반 페이지를
구분해 전체 이미지가 정확히 하나일 때만 진행하고, 다중 페이지 문서는 어느 것이 그 사진인지
추측하지 않고 계속 거부합니다.

디코더에서 WIC 프레임 번호가 디렉터리 번호와 같다는 가정이 틀렸다는 것도 확인했습니다. WIC 는
축소 해상도 페이지를 프레임으로 노출하지 않아 디렉터리 2개 파일이 프레임 1개로 도착합니다.
probe 가 정한 치수와 일치하는 프레임을 고르도록 바꿔 양쪽 모두에서 성립하게 했습니다.
상세는 `implementation/multi-directory-tiff.md`.
