## 확인한 계약

- **원본을 바꾸지 않습니다.** 내보내기 전후 원본 SHA-256 이 같고 크기도 그대로입니다.
- **preview 와 export 가 같은 레시피를 씁니다.** 둘 다 `DevelopRequestFactory.Create` 가
  만든 **같은 요청 객체**를 받습니다. 이 팩토리가 프리셋 합성·흑백 토닝·자동 GrainMend 세기를
  모두 여기서 채우므로, 한쪽만 다른 값을 쓰는 경로가 구조적으로 없습니다.

## 알아 둘 것: 지금 개발용 실행은 Debug 네이티브입니다

`out/build/managed/Negaflow.Shell/x64/Debug/.../Negaflow.Shell.exe` 는 빌드 스크립트가
`out/build/native/x64-debug/Debug/Negaflow.Native.dll` 을 복사해 옵니다. C++ Debug 빌드는
같은 일을 **20배 느리게** 합니다(위 표). **반응 속도를 이 실행으로 판단하지 마십시오.**
체감을 재려면 Release 네이티브 DLL 을 덮어써서 띄우거나 Release 구성으로 빌드하십시오.

## 미리보기 2.1 초가 어디서 오는지 (Release 네이티브, 같은 스캔)

| 요청 | 400×300 | 1600×1200 |
| --- | --- | --- |
| 조정값 있음 | 2,087 ms | 2,078 ms |
| 조정값 없음(중립) | 637 ms | 657 ms |

두 가지가 읽힙니다.

1. **비용이 출력 크기와 무관합니다.** 400×300 을 달라고 해도 1600×1200 과 같은 시간이
   걸립니다. 파이프라인이 5088×3401 전체 해상도로 돌고 **마지막에만** 축소한다는 뜻입니다.
   0.1 메가픽셀을 얻으려고 17 메가픽셀을 처리합니다.
2. **고정비 0.64 초, 보정 단계 1.44 초.** 중립 요청도 0.64 초가 드는데 이것이 디코드와
   반전·base 이고, 나머지 1.44 초가 톤·색·질감 단계입니다.

**그래서 인터랙티브 프록시 해상도를 낮추는 것은 아무 소용이 없습니다.** 만들기 전에 재서
알아냈습니다. 실제로 효과가 있는 것은 **미리보기에서 일찍 축소하는 것** — 디코드·반전 뒤에
요청 크기로 리샘플하고 나머지 단계를 그 위에서 도는 것입니다.

다만 그 변경은 미리보기 픽셀을 바꿉니다. 노출·대비·농도·색온도·채도 같은 화소별 단계는
축척과 무관해 결과가 같지만, **입자·선명도·헐레이션은 축척에 따라 보이는 것이 달라집니다.**
macOS 는 Core Image 가 출력 ROI 기준으로 평가하므로 그쪽도 미리보기는 축소 스케일에서
돌 가능성이 큽니다. 즉 이 변경이 macOS 에 **더** 가까울 수 있지만, 그건 추측이므로
**macOS 미리보기와 실제로 견주기 전에는 바꾸지 마십시오.** 바꾸려면 화소별 단계만 먼저
축소 후에 돌리고 질감 단계는 그대로 두는 절충이 안전합니다(0.64 초 + 질감만 남습니다).
