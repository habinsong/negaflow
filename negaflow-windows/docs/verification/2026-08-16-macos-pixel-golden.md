## 어긋난 것 — 현상 픽셀

여덟 조건 **전부** 다릅니다. `a-default-main-srgb` 기준(채널별 median / mean):

| 채널 | Windows | macOS | 차이 |
| --- | ---: | ---: | ---: |
| R | 44132 / 40257.4 | 44908 / 40985.7 | −776 / −728 |
| G | 45786 / 41720.2 | 47896 / 43601.6 | −2110 / −1881 |
| B | 47172 / 43200.1 | 49865 / 45653.3 | −2693 / −2453 |

**성질:**

- Windows 가 **일관되게 어둡습니다**. 여덟 조건 모두 같은 방향입니다.
- 차이가 **R < G < B** 로 커집니다. 전역 노출 차이가 아니라 채널에 매인 차이입니다.
- 출력 색공간 세 가지(sRGB · Display P3 · Adobe RGB)가 모두 같은 양상이므로, 원인은
  **색공간 변환보다 앞** 단계입니다.
- 현상 타깃 다섯 가지(MAIN · HS · SP · F135 · HR)도 모두 같은 양상입니다. 타깃 그레이드
  이후가 아니라 그 **앞**입니다.

## 아닌 것으로 확인된 원인 — 자동 base

맥이 잰 auto base 는 다음이고, **전부 float16 정밀도**입니다(Core Image 반정밀도 버퍼).

| 채널 | macOS | Windows | 차이 |
| --- | --- | --- | --- |
| R | 0.338134765625 | 0.338650912046 | +0.000516 |
| G | 0.293212890625 | 0.295434862375 | +0.002222 |
| B | 0.233398437500 | 0.236179560423 | +0.002782 |

초과분이 R < G < B 로 커져 픽셀 차이와 방향이 같아, base 가 원인으로 **보였습니다**.
그래서 맥이 잰 base 를 수동으로 그대로 넣고 다시 냈습니다.

| 채널 | 자동 base | macOS base 강제 | macOS 결과 |
| --- | ---: | ---: | ---: |
| R median | 44132 | 44117 | 44908 |
| G median | 45786 | 45737 | 47896 |
| B median | 47172 | 47108 | 49865 |

**거의 움직이지 않았고, 오히려 조금 멀어졌습니다. base 는 원인이 아닙니다.**

값의 방향이 맞는다고 원인으로 단정하지 않은 것이 이 항목에서 남길 교훈입니다 — 같은 실수를
GrainMend 조사에서 이미 세 번 했습니다. base 를 float16 으로 양자화하는 "수정" 을 먼저 했다면
증상은 그대로인 채 코드만 바뀌었을 것입니다.

## 찾은 원인 — 장면 통계 표본의 축소 방식

밀도 정규화 분모 `dmaxNorm` 은 채널별이고 base 다음·타깃 그레이드 앞에 있습니다. 그 값은
축소본에서 잰 최농부(p0.002)로 정해집니다. 게이팅 상수와 수식은 양쪽이 같았고, **표본을
만드는 축소 방식이 달랐습니다.**

| | macOS | Windows(이전) |
| --- | --- | --- |
| 축소 크기 | 320×488 | 317×484 |
| 축소 방식 | Core Image 렌더 = **면적 평균** | **bilinear 점 표본** |

1/7 로 줄일 때 bilinear 는 칸 안의 50여 화소 중 이웃 넷만 읽습니다. 입자·먼지 같은 극단값이
그대로 남아 p0.002 를 끌어내리고, 그것이 `dmaxNorm` 을 키워 정규화 밀도를 낮추고 결과를
어둡게 만듭니다. 채널마다 잡음이 다르므로 차이도 채널마다 달라집니다.

표본을 그 칸 전체의 면적 평균으로 바꾸고 다시 쟀습니다.

| 채널 | 이전 | 이후 | macOS | 이전 차이 | 이후 차이 |
| --- | ---: | ---: | ---: | ---: | ---: |
| R median | 44132 | 45887 | 44908 | −776 | +979 |
| G median | 45786 | 48115 | 47896 | −2110 | **+219** |
| B median | 47172 | 49624 | 49865 | −2693 | **−241** |
| G max | 59613 | 60393 | 60416 | −803 | **−23** |
| B max | 60392 | 61045 | 61186 | −794 | **−141** |

G·B 가 **열 배 가까이** 줄었습니다. 이 변경은 macOS 를 맞추려는 눈속임이 아니라 그 자체로
옳습니다 — 축소본에서 장면 통계를 잴 때 점 표본은 입자가 퍼센타일을 지배하게 둡니다.

## 표본 격자도 달랐습니다

macOS 는 폭만 320 으로 묶고 높이는 비율대로 두며 **상한이 없습니다**. Windows 에는
`maximum_sample_count = 320×480` 이 있어, 2:3 보다 조금 긴 보통 프레임에서 먼저 걸렸습니다 —
2272×3471 은 320×488 을 원하는데 317×484 로 줄어 다른 퍼센타일을 쟀습니다. 그 상한의 주석이
스스로 "320×480 격자를 지킨다" 고 적어 둔 의도가 바로 그 프레임들에서 깨져 있었습니다.

1:4 까지 허용하도록 올려(원래 목적인 극단 파노라마만 걸림) 다시 쟀습니다.

| 항목 | 면적 평균만 | 격자까지 | macOS |
| --- | ---: | ---: | ---: |
| G max | 60393 | **60416** | 60416 |
| B median | 49624 | 49653 | 49865 |

**G max 가 macOS 와 정확히 같아졌습니다.**

## 아닌 것으로 확인된 원인 2 — 어두운 비필름 게이트

R 잔차가 게이팅의 `R/B` 비(`neutralDarkRatioCut`)에서 오는지 보려고 그 게이트를 끄고
다시 냈습니다. **결과 파일의 SHA-256 이 완전히 같았습니다.** 이 프레임의 base R/B 는
1.434 로 게이트가 켜지는 1.5 에 못 미쳐, 애초에 동작한 적이 없습니다.

두 번째로 방향만 보고 지목했다가 측정에서 걸러진 가설입니다.

## 남은 것 — R 채널 +975

지금 잔차는 R +975 / G +295 / B −212 입니다. 시작할 때의 R −776 / G −2110 / B −2693 에서
G·B 는 열 배 가까이 줄었고 R 만 반대쪽으로 남았습니다(45883 대 44908, 2.2%).

base 는 두 번 다 아니었습니다 — 면적 평균을 적용한 뒤 맥이 잰 base 를 다시 강제해도
R 은 45887→45871 로 16 만 움직였습니다. 게이트도 아니었습니다.

남은 후보는 축소 표본을 만드는 **필터의 모양** 자체입니다. Core Image 의 축소가 정확한
박스 평균이 아니라면(부분 평균이나 밉맵), 세 채널이 각기 다른 만큼 어긋납니다. 다만 단일
혼합 비율로는 설명되지 않습니다 — R 은 필요한 이동의 44%, G 는 91%, B 는 110% 를 받았습니다.
그러므로 "얼마나 평균하느냐" 하나로 맞출 수 있는 문제가 아닙니다. 다음 측정은 축소본
자체의 채널별 퍼센타일을 맥에서 받아 대조하는 것이며, 그러려면 맥 하네스에 그 값을 찍는
항목이 하나 필요합니다.

## 재현

```
PixelGolden.exe <원본.tiff> <출력폴더> docs/verification/macos-golden/task1-pixels/pixel-stats.json
```

## OpticFilm 8100 — 사진이 나오지 않습니다

골든에는 8100 프레임(5136×3543)도 있습니다. 같은 조건으로 대조했습니다.

| | Windows | macOS |
| --- | ---: | ---: |
| base R / G / B | 0.0320 / 0.0120 / 0.0065 | 0.1913 / 0.0939 / 0.0711 |
| R median | **19** | 25353 |
| G median | **6** | 24632 |
| B median | **2** | 22817 |

**median 19 대 25353 — 결과가 거의 새까맣습니다.** V700 의 2% 차이와 달리 이것은 사진이
나오지 않는 수준이며, 사용자의 두 스캐너 중 하나입니다.

base 가 6~11 배 낮게 잡힌 것이 직접 원인입니다. Dmin 이 실제 필름 베이스보다 어두우면
대부분 화소의 밀도가 음수가 되어 검정으로 눌립니다.

### 원본 성질의 차이와, 아닌 것으로 확인된 둘

| | V700(정상) | 8100(까맣게 나옴) |
| --- | --- | --- |
| 엔디안 | II | **MM** |
| 채널 | 3 | **4 (RGBA, ExtraSamples=1)** |
| 압축 | 없음 | **LZW** |

셋 중 무엇인지 가리려고 **정상 동작하는 V700 을 변형**해 두 개를 만들어 돌렸습니다.

| 변형 | 결과 |
| --- | --- |
| RGBA 4채널 + 불투명 알파(ExtraSamples=1) | 원본과 **바이트 동일**(sha 1215ef549475) |
| 빅엔디안(MM) | 원본과 **바이트 동일** |

**엔디안도 알파도 원인이 아닙니다.** 남은 후보는 LZW 압축 경로, 또는 이 이미지의 내용에서
`AutoConnectedComponent` base 추정기가 실패하는 것입니다. macOS 는 같은 파일에서 0.1913 을
찾아냈으므로 파일이 못 읽을 것은 아닙니다.

다음 측정은 8100 원본을 무압축으로 다시 써서 돌려 보는 것입니다 — 그러면 LZW 인지
추정기인지가 한 번에 갈립니다.
