# 200장 라이브러리 실측 (2026-08-13)

지금까지 라이브러리·썸네일 확인은 **2장짜리 카탈로그**에서만 했습니다. 수백 장에서 무엇이
무너지는지 모르는 채로 "동작한다"고 쓸 수 없어 실제로 재 봤습니다.

## 방법

1000×667 JPEG 200장(합계 4MB)을 만들고, **격리 storage root** 에 제품 API 그대로
(`LibraryHostService.ImportFolders` → `LibraryFrameListItems` → `LibraryBrowserProjector` →
`LibrarySorter` → `LibraryQuickFilterState` → `ThumbnailService`) 통과시켰습니다. x64 **Release**
네이티브 엔진입니다. 사용자의 실제 카탈로그는 건드리지 않았습니다.

## 결과

| 단계 | 200장 비용 |
| --- | --- |
| 폴더 가져오기(probe + catalog write) | 765 ms |
| 목록 투영 | 0 ms |
| 폴더 묶기 | 4 ms |
| 이름순 정렬 | 1 ms |
| 별점 필터 | 0 ms |
| 검색(`frame_1` → 100건) | 1 ms |
| catalog 저장 | 10 ms |
| **썸네일 요청 200건 큐잉(UI 스레드 비용)** | **0 ms** |
| 썸네일 200장 완료(동시 3) | 5.6 s (장당 28 ms) |

가장 중요한 줄은 **큐잉 0 ms** 입니다. 그리드가 화면에 보이는 카드마다 요청을 던져도 UI
스레드는 붙잡히지 않습니다. 설계 의도가 실제로 성립합니다. 디스크 캐시에도 200건이 전부
남아(12,800 바이트 = 200 × stub 64B) 프레임별 coalescing 이 요청을 잃지 않는 것도 확인했습니다.

## 이 측정이 덮지 않는 것

- **JPEG 인코딩은 stub 입니다.** WIC 인코더는 WinUI 런타임이 필요해 헤드리스에서 못 돌립니다.
  잰 것은 **현상 렌더 처리량**이고, 실제로는 여기에 인코딩 비용이 더 붙습니다.
- **원본이 작습니다.** 1000×667 합성 이미지라 실촬영 3278×4944 스캔보다 훨씬 쌉니다.
  장당 28 ms 를 실촬영에 그대로 옮기지 마십시오.
## 실제 앱 그리드 (추가 측정)

`NEGAFLOW_STORAGE_ROOT` 를 넣어 격리 카탈로그로 앱을 띄웠습니다(`App.ResolveStorageRoots`).
사용자의 실제 카탈로그에 200장을 넣을 수는 없어서 만든 검증용 seam 이며, 설정했을 때만
갈라집니다.

| 항목 | 값 |
| --- | --- |
| 프레임 2장 (Debug) | 216 MB |
| 프레임 200장 (Debug) | 353 MB |
| 지연 디코드 적용 뒤 200장 | 359 MB |
| 목록 전체 재구성(정렬 변경) 뒤 | 363 MB |

## 가상화 — 계측으로 결론

`ContainerContentChanging` 호출 수를 세는 임시 계측 빌드로 확정했습니다(계측은 측정 뒤 제거).

| 프레임 수 | 한 번의 목록 구성에서 realize 된 컨테이너 |
| --- | --- |
| 200 | 200 |
| 1,500 | **370** |

**가상화는 정상입니다.** 1,500장에서 370개에 머무는데, 이는 보이는 한 화면(약 70장)에
`ItemsWrapGrid.CacheLength` 기본값 4화면분을 더한 값과 맞습니다. 200장에서 200개가 전부
만들어진 것은 **목록이 캐시 창(약 350)보다 작아서**이지 결함이 아닙니다.

가는 길에 판단을 두 번 뒤집었습니다. UIA 트리의 항목 수는 근거가 되지 못하고(WinUI 는
가상화된 항목도 접근성을 위해 노출합니다), 200장에서의 200/200 도 근거가 되지 못합니다.
**이 질문은 큰 목록에서 계측해야만 답이 나옵니다.**

## 재활용 카드의 비트맵 해제 — 실측 이득

1,500장을 띄우니 **1,270 MB** 였습니다. 원인은 재활용된 카드의 디코드된 썸네일을 놓지 않은
것이었습니다. `ContainerContentChanging` 의 `InRecycleQueue` 에서 `Thumbnail` 을 비우도록
고쳤습니다.

| | 1,500장 작업 집합 |
| --- | --- |
| 고치기 전 | 1,270 MB |
| 고친 뒤 | **861 MB** |

409 MB(32%) 줄었습니다.

### 썸네일 메모리 캐시는 **상한을 두지 않습니다** (macOS 와 같게)

남은 861 MB 의 다음 후보로 `ThumbnailService` 의 무제한 JPEG 캐시를 의심했지만, macOS 를
확인하고 생각을 바꿨습니다.

- macOS 의 메모리 FIFO(`FrameCacheManager`)가 묶는 것은 **풀해상도 버퍼**입니다
  (cleanedRaw 2, developed 3). **썸네일은 명시적으로 제외**돼 있습니다 —
  `ScanFrame.swift`: "메모리 FIFO 제거 대상이 아님 — 풀해상도 버퍼를 내려놓아도 썸네일은
  남아 스트립이 비지 않는다."
- macOS 는 썸네일을 압축 데이터를 lazy 디코드하는 `NSImage` 로 들고 있습니다. 즉 상주 비용이
  **JPEG 바이트**이지 펼친 비트맵이 아닙니다. Windows 의 `ThumbnailService.memory` 도 JPEG
  바이트를 들고 있어 같은 성질입니다.
- 실측 썸네일이 장당 약 20 KB 이므로 1,500장이면 **30 MB 남짓**입니다. 861 MB 를 설명하지
  못합니다.

**그래서 상한을 두지 않았습니다.** 두었다면 macOS 가 일부러 피한 "스트립이 비는" 동작을
들여오면서 메모리는 거의 못 줄였을 것입니다.

### 1,500장 메모리 — 가설 셋을 재서 셋 다 기각했습니다

**아직 원인을 모릅니다.** 다음 사람이 같은 길을 다시 파지 않도록, 시험하고 **틀린 것으로
확인된** 가설을 적어 둡니다.

| 가설 | 측정 | 결과 |
| --- | --- | --- |
| 썸네일 JPEG 메모리 캐시가 무제한이라 | 실측 썸네일 장당 약 20 KB → 1,500장 ≈ 30 MB | **기각.** macOS 도 썸네일은 FIFO 대상이 아니므로 상한을 두지 않았습니다 |
| `LibraryDocument` 의 catalog JSON payload | 격리 harness 에서 GC 측정: 1,500장 **6 MB**(장당 4,231 바이트) | **기각.** 투영을 더해도 증가 0 MB |
| 렌더 버퍼(518,400 B)가 LOH 에 쌓여서 | `ArrayPool` 로 바꿔 cold 비교: 1,258 MB → 1,251 MB | **기각.** 차이가 없어 변경을 되돌렸습니다 |

측정 조건도 함께 적습니다. **cold(디스크 캐시 비움, 1,500장 전부 렌더) 약 1,255 MB**,
**warm(캐시 있음, 렌더 없음) 약 858 MB** 입니다. 둘을 섞어 비교하면 안 됩니다 — 한 번
그렇게 해서 "좋아졌다"고 잘못 읽을 뻔했습니다.

설명되는 부분은 Debug 기준선 216 MB(프레임 2장)와 realize 된 370장의 디코드 비트맵 약
128 MB 정도입니다. **나머지 약 500 MB 의 출처는 미상이며, 다음에는 추측이 아니라 메모리
프로파일러로 접근하십시오.**

지연 디코드(카드가 realize 될 때만 디코드)는 200장에서 작업 집합을 움직이지 않았습니다
(353 → 359 MB). 그 변경의 이득은 재구성마다 전량을 다시 디코드하지 않는 CPU 쪽이지
메모리가 아닙니다.
