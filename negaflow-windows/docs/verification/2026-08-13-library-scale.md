# 200장 라이브러리 실측 (2026-08-13)

지금까지 라이브러리·썸네일 확인은 **2장짜리 카탈로그**에서만 했습니다. 수백 장에서 무엇이
무너지는지 모르는 채로 "동작한다"고 쓸 수 없어 실제로 재 봤습니다.

## 방법

1000×667 JPEG 200장(합계 4MB)을 만들고, **격리 storage root** 에 제품 API 그대로
(`LibraryHostService.ImportFolders` → `LibraryFrameListItems` → `LibraryBrowserProjector` →
`LibrarySorter` → `LibraryQuickFilterState` → `ThumbnailService`) 통과시켰습니다. x64 **Release**
네이티브 엔진입니다. 사용자의 실제 카탈로그는 건드리지 않았습니다.

## 결과

| 단계 | 200장 비용 |
| --- | --- |
| 폴더 가져오기(probe + catalog write) | 765 ms |
| 목록 투영 | 0 ms |
| 폴더 묶기 | 4 ms |
| 이름순 정렬 | 1 ms |
| 별점 필터 | 0 ms |
| 검색(`frame_1` → 100건) | 1 ms |
| catalog 저장 | 10 ms |
| **썸네일 요청 200건 큐잉(UI 스레드 비용)** | **0 ms** |
| 썸네일 200장 완료(동시 3) | 5.6 s (장당 28 ms) |

가장 중요한 줄은 **큐잉 0 ms** 입니다. 그리드가 화면에 보이는 카드마다 요청을 던져도 UI
스레드는 붙잡히지 않습니다. 설계 의도가 실제로 성립합니다. 디스크 캐시에도 200건이 전부
남아(12,800 바이트 = 200 × stub 64B) 프레임별 coalescing 이 요청을 잃지 않는 것도 확인했습니다.

## 이 측정이 덮지 않는 것

- **JPEG 인코딩은 stub 입니다.** WIC 인코더는 WinUI 런타임이 필요해 헤드리스에서 못 돌립니다.
  잰 것은 **현상 렌더 처리량**이고, 실제로는 여기에 인코딩 비용이 더 붙습니다.
- **원본이 작습니다.** 1000×667 합성 이미지라 실촬영 3278×4944 스캔보다 훨씬 쌉니다.
  장당 28 ms 를 실촬영에 그대로 옮기지 마십시오.
- **WinUI GridView 가상화는 재지 않았습니다.** 이 측정은 Shell.Core 까지입니다. 200장을 실제
  앱 그리드에 넣고 스크롤하는 것은 아직 남아 있습니다 — 파일 대화상자 자동화가 안 돼
  카탈로그에 넣지 못했습니다.
