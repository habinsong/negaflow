# 출력 설정이 실촬영 스캔에서 실제 파일에 닿는가

기준일: 2026-08-14

## 무엇을 확인했는가

출력 패널의 품질 값(DPI · 긴 변 · TIFF 압축 · 출력 선명도)이 **저장만 되고 요청에 실리지 않는**
상태가 아닌지, 그리고 그 값이 실제로 게시된 파일에 나타나는지입니다. 단위 검사는 값이
`DevelopExportRequest` 까지 간다는 것만 말합니다 — 파일을 열어 보지 않으면 그 다음이 비어 있어도
알 수 없습니다.

## 어떻게

앱을 띄우지 않고 셸이 쓰는 것과 같은 경로를 그대로 탔습니다. `ExportSettings` →
`ExportSettingsExtensions.ToEncodingOptions` → `DevelopRequestFactory.Create` →
`NativeDevelopExporterAdapter.Run`. 입력은 사용자의 실제 스캔
`OpticFilm8100_frame_1.tiff`(5088×3401, 16-bit, Plustek OpticFilm 8100)입니다.

고른 값: TIFF16 · 300 DPI · 긴 변 2048 · LZW · 출력 선명도 0.5(무광 용지).

게시된 TIFF 는 IFD 를 직접 읽어 확인했고, 같은 입력에 선명도만 0 으로 바꿔 한 번 더 내보내
비교했습니다.

## 결과

| 항목 | 값 |
| --- | --- |
| ABI | 0.44 / X64 |
| 치수 | 5088×3401 → **2048×1369** (긴 변 상한 적용, 비율 1.4960 보존) |
| Compression (259) | **5** = LZW |
| ResolutionUnit (296) | 2 = inch |
| XResolution (282) | **300** |
| 선명도 0.5 파일 | 21,987,848 바이트, SHA-256 `DF74FA5B…9053` |
| 선명도 0 파일 | 21,982,578 바이트, SHA-256 `A316EB46…0FE9` |
| 원본 SHA-256 | 두 번 모두 `F281DEEC…872B` (변경 없음) |

선명도만 다른 두 실행의 SHA-256 과 크기가 다르므로 **출력 선명도가 픽셀까지 닿습니다.** 파일
이름이 같은 자리에 두 번 쓰이지 않도록 서로 다른 폴더에 냈습니다.

시간은 Debug 네이티브에서 4.6 초(선명도 0.5) / 3.3 초(0)입니다. **Debug 실행으로 반응 속도를
판단하지 마십시오** — 같은 일을 Release 는 한 자릿수 배 빠르게 합니다(`2026-08-13-real-scan-export.md`
참고). 이 확인의 목적은 속도가 아니라 값이 파일에 닿는지입니다.

## 덧: Release 네이티브와 어려운 디코더 경로 (같은 날 나중에)

x64 Release 전체 게이트를 돌려 네이티브를 다시 빌드한 뒤(native 67/67, catalog 710, shell 642 통과)
같은 확인을 **frame_12** 로 다시 했습니다. 이 프레임은 big-endian **LZW** RGBA16 에 572바이트 ICC 가
박힌, frame_1 과 다른 디코더 경로입니다.

| 항목 | 값 |
| --- | --- |
| 치수 | 2048×1369 (긴 변 상한 적용) |
| Compression / XResolution | 5 (LZW) / 300 |
| 시간 | Release 네이티브 3.43 초 |
| 원본 SHA-256 | `FBB71DD6…FEC6` (변경 없음) |

## 확인하지 않은 것

- macOS 가 같은 입력·같은 설정으로 낸 파일과의 픽셀 대조. macOS 호스트가 필요합니다.
- 사이드카·원본 보관은 셸 코드비하인드에 있어 이 하네스가 타지 않습니다. 본문은 단위 검사가,
  파일 이름은 `ExportArtifactPairing` 검사가 덮습니다.
