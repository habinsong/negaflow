# 출력 색공간 행렬과 생성한 ICC 프로파일

기준일: 2026-08-14

## 무엇을 만들었는가

현상 파이프라인은 언제나 선형광 · sRGB/Rec.709 primaries 로 돕니다. 출력 색공간은 양자화 직전
마지막 한 걸음입니다 — 선형광에서 3×3 행렬로 목표 primaries 로 옮기고, 목표의 전달 곡선으로
부호화한 뒤, 그 공간의 ICC 프로파일을 붙입니다.

세 공간 모두 D65 이므로 **픽셀에는 색순응이 들어가지 않습니다.** D50 으로의 Bradford 적응은
프로파일의 XYZ 태그에만 들어갑니다 — ICC 의 연결 공간이 D50 이기 때문이지 그림이 D50 이어서가
아닙니다.

## 계산된 행렬 (linear sRGB → target, row-major)

```
display-p3  0.822462  0.177538  1.11022e-16
            0.0331942 0.966806  2.08167e-17
            0.0170826 0.0723974 0.91052

adobe-rgb   0.715126  0.284874  0
            0         1         0
            0         0.0411619 0.958838
```

Display P3 행렬은 널리 인용되는 sRGB→P3 값과 일치합니다.

Adobe RGB 에서 눈에 띄는 두 가지를 적어 둡니다.

- **빨강·파랑 열이 순수합니다.** Adobe RGB 는 sRGB 와 빨강·파랑 chromaticity 를 공유하므로 그
  채널은 다른 채널을 섞지 않습니다. 다만 **행렬 값이 1 이 되지는 않습니다**(0.7151) — 두 공간
  모두 흰색이 D65 에 놓이도록 다시 정규화하고, 초록이 넓어진 만큼 그 배율이 달라지기 때문입니다.
- **초록 대각이 정확히 1.0 입니다.** 이것은 우연이며 "sRGB 초록이 Adobe 초록과 같다" 는 뜻이
  아닙니다. 같은 열의 빨강 0.2849, 파랑 0.0412 가 함께 있어야 sRGB 초록이 됩니다. 실제로 그
  조합의 휘도를 Adobe 의 Y 계수로 다시 재면 0.7151 로, sRGB 초록의 휘도와 같습니다.

두 번째 사실 때문에 처음에 쓴 "대각은 1 보다 작아야 한다" 는 검사가 틀렸습니다. 지금 검사는
대신 **넓은 공간에서 sRGB primary 를 내려면 그 공간의 primary 가 덜 필요하다**(빨강 계수 < 1)와
**공유하는 primary 는 다른 채널을 섞지 않는다**를 봅니다.

## 전달 곡선

- sRGB, Display P3: sRGB 곡선(둘은 같은 곡선을 씁니다)
- Adobe RGB: 감마 563/256 — Adobe RGB (1998) 규격이 적는 값입니다

## 생성한 프로파일

Windows 는 sRGB 프로파일은 갖고 있지만 Display P3 와 Adobe RGB 는 갖고 있지 않습니다. 있을지
없을지 모르는 파일을 내보내기의 전제로 삼을 수 없으므로 바이트를 직접 만듭니다. v2 matrix/TRC
이며 태그 아홉 개(`desc`·`wtpt`·`rXYZ`·`gXYZ`·`bXYZ`·`rTRC`·`gTRC`·`bTRC`·`cprt`)입니다.
TRC 는 1024점 샘플 곡선입니다 — 정확한 조각별 sRGB 곡선을 담는 `para` 는 v4 태그이고, 1024점은
16-bit 한 스텝보다 훨씬 촘촘합니다.

세 프로파일 모두 **스캐너 프로파일에 쓰는 것과 같은 검증기**(`validate_icc_profile`)를 통과하고,
선언한 크기가 실제 바이트 수와 같습니다.

## 확인하지 않은 것

- **macOS 가 같은 설정으로 낸 파일과의 대조.** macOS 호스트가 필요합니다.
- 이 행렬과 프로파일은 아직 **내보내기 경로에 연결되지 않았습니다.** ABI·인코더·UI 는 다음
  단계이며, 지금은 색공간을 고를 수 있는 자리가 없습니다.
- 색역을 벗어나는 색의 처리(gamut clipping). 지금은 행렬 뒤에 0...1 클램프만 있습니다.
