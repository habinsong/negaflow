# 소프트 프루프 검증

날짜: 2026-08-10
빌드: x64 Debug / x64 Release, MSVC 14.51, ABI 0.30
실촬영: `negaflow-mac/Sources/ScannerKit/Resources/Frame.tiff` (읽기 전용)

## 1. 설치된 프로파일이 실제로 무엇을 담고 있는지

주장하기 전에 측정했습니다. `C:\Windows\System32\spool\drivers\color` 의 파일을 직접 파싱한
결과입니다.

| 프로파일 | ICC | 클래스 | 공간 | `wtpt` | `bkpt` | `chad` | rXYZ+gXYZ+bXYZ |
|---|---|---|---|---|---|---|---|
| sRGB Color Space Profile.icm | 2.1 | mntr | RGB | **0.950455, 1.0, 1.08905** (D65) | 0,0,0 | 없음 | 0.964279, 0.999969, 0.825089 |
| AdobeRGB1998.icc | 2.1 | mntr | RGB | **0.950455, 1.0, 1.08905** (D65) | 0,0,0 | 없음 | 0.964203, 1.0, 0.824905 |
| eciRGB_v2.icc | 2.4 | mntr | RGB | 0.964203, 1.0, 0.824905 (D50) | 없음 | 없음 | 0.964188, 1.0, 0.824905 |
| WideGamutRGB.icc | 2.1 | mntr | RGB | 0.964294, 1.0, 0.825104 (D50) | 0,0,0 | 없음 | 0.964203, 1.0, 0.824905 |
| ISOcoated_v2_eci.icc | 2.4 | prtr | CMYK | 0.84552, 0.876831, 0.747162 | 없음 | 없음 | 없음 (LUT) |

두 가지가 확인됐습니다.

**(a) v2 프로파일의 `wtpt` 는 신뢰할 수 없습니다.** 같은 v2.1 안에서도 sRGB·Adobe RGB 는 D65
를, WideGamutRGB 는 D50 을 담습니다. `chad` 태그는 다섯 개 중 하나도 없어 보정 여부를 알려주지
않습니다. macOS 의 계산을 그대로 적용하면 sRGB 의 파랑이 `1.08905 / 0.8249 = 1.320` 이 되어
상한 `1.2` 까지 클램프되고, **프루프를 켜는 순간 화면이 파래집니다.**

**(b) 색소 합은 신뢰할 수 있습니다.** matrix/TRC 프로파일 네 개 전부에서 rXYZ+gXYZ+bXYZ 가
D50 에서 **2e-4 안쪽**입니다 — D65 를 선언한 두 개도 포함해서. 정의상 색소는 PCS 흰색으로
합해지므로 이것이 프로파일 자신의 변환 데이터와 일치하는 값입니다.

**(c) LUT 프로파일에는 색소가 없고, 있을 이유도 없습니다.** ISOcoated 의 `wtpt` 는 측정된
용지이며(D50 대비 0.877/0.877/0.906 — 12% 어둡고 약간 따뜻함) 이것이야말로 시뮬레이션이
보여주려는 것입니다. 그래서 LUT 경로는 손대지 않습니다.

## 2. 스냅 허용치는 왜 필요했는가

색소 합 규칙만 넣고 실촬영 프레임으로 확인했더니 sRGB·Adobe RGB 는 프루프 없는 렌더와 **바이트
동일**했는데 eciRGB_v2 와 WideGamutRGB 가 **각각 1 코드씩** 움직였습니다.

원인은 재구성 오차입니다. eciRGB_v2 의 색소 합은 D50 대비 `(0.999988, 1.0, 1.000006)` 이고,
`1.000006` 배도 8 비트 양자화 경계에 딱 걸린 픽셀 하나는 넘깁니다.

허용치 `1.0e-3` 을 넣어 세 채널이 전부 그 안이면 정확히 중립으로 스냅합니다. 보이는 것보다 두
자릿수 아래, 관측된 재구성 오차(2e-4)보다 두 자릿수 위입니다. 실제 용지는 12% 떨어져 있으므로
근처에도 오지 않습니다.

## 3. 실촬영 parity

`native.develop_export_abi` 가 실촬영 네거티브를 512px 미리보기로 렌더한 결과.

| 목적지 프로파일 | 프루프 없는 렌더와의 최대 차이 |
|---|---|
| sRGB Color Space Profile.icm | **0 코드** |
| AdobeRGB1998.icc | **0 코드** |
| eciRGB_v2.icc | **0 코드** |
| WideGamutRGB.icc | **0 코드** |

`paperAndBlackInk` 모드를 켜고 렌더한 것입니다. 설치된 RGB 출력 프로파일 전부가 macOS 내장
프로파일과 같은 결과 — 아무 변화 없음 — 를 냅니다.

## 4. 비용

x64 Release, 같은 실촬영 프레임, 512px 미리보기.

| | wall |
|---|---|
| 프루프 없음 | 82,402 µs |
| sRGB 프루프 | 82,286 µs |
| Adobe RGB 프루프 | 83,397 µs |
| eciRGB v2 프루프 | 82,145 µs |
| Wide Gamut 프루프 | 83,775 µs |

**한 번은 프루프 쪽이 더 빨랐습니다.** affine 3 개는 옆에 있는 sRGB 인코드(채널당 `pow`) 대비
잡음 안입니다.

그래서 프루프가 꺼져 있어도 **분기 없이 그냥 계산합니다.** `scale = 1`, `bias = 0` 은
부동소수점에서 정확한 항등이므로 결과 동일성이 증명되고, 갈라질 수 있는 두 번째 경로가 생기지
않습니다. 위 표의 "0 코드" 가 그 증명입니다.

## 6. 확인하지 않은 것

**목적지 색공간 변환은 구현하지 않았습니다.** macOS 는 표시 이미지를 프루프 공간에 렌더해
프린터 gamut 밖 색이 잘리는 것을 보여줍니다. 지금 Windows 가 보여주는 것은 용지 흰색과 잉크
검정뿐입니다. 이 문서의 "parity" 는 **용지·잉크 부분에 한정**됩니다.

**`DestinationGamutWarning` 도 없습니다.**

**실제 프린터 RGB 프로파일로는 확인하지 못했습니다.** 이 기계에 설치된 RGB 프로파일은 전부
표시 프로파일이라 용지가 중립이고, 유일한 인쇄 프로파일(ISOcoated)은 CMYK 라 목적지로 거부
됩니다 — macOS 도 거부합니다. 용지·잉크 시뮬레이션이 실제로 그림을 옮기는 것은 합성 용지로만
확인했습니다(`native.develop_export_abi` 의 경계 검사). 실제 인쇄 프로파일을 구하면 다시
확인해야 합니다.
