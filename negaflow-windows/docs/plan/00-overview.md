## 0. 요구사항 (사용자 원문 기준)

> - GrainMend 를 macOS 에 구현된 **품질·성능·기능·속도·최적화·검출능력·오탐지 억제·UI/UX
>   (크기·모양·색깔·위치)** 모두 싹다 그대로 이식. **창작 없이.**
> - 자동은 **5초 미만**, 가이드·브러시·복제·IR 은 즉시.
> - **라이브러리/현상/인화 뷰의 좌측탭·중앙·하단·우측탭·상단 전부** macOS 와 동일하게.
>   좌측탭 안의 세로탭까지. **기능 하나 빼먹지 말 것.** 정렬 옵션, 세부 프레임, 뷰 전부.
> - 스크린샷 폴더(`C:\Users\habin\맥negaflow 스크린샷\`, PNG 50장. 목록 `docs/audit/11` 1.3절)와 Swift 코드를 **둘 다** 보고 맞출 것. 옛 `negaflow_mac_screenshot/` 는 폐기.
> - GPU 를 쓸 것. **Intel 내장·AMD 내장·외장(Intel/NVIDIA/AMD) 공통**으로 되는 것.
> - 하드코딩으로 문제를 회피하지 말 것. 가설·추측 없이 검증할 것.
> - 500줄 넘는 God object 금지(사유를 적으면 예외).
> - **전부 끝낸 뒤에 computer-use 로 확인할 것.**

## 1. 원칙

1. **측정 먼저.** "느리다"로는 어디를 고칠지 알 수 없습니다. 이번 세션에서 43초의 내역을
   나누고 나서야 진짜 원인이 나왔습니다(2절). 최적화·이식 전에 숫자를 만듭니다.
2. **1:1 대조는 파일 단위로 표를 만들고 시작합니다.** "있음"이라고 적힌 것을 믿고 넘어가면
   안 됩니다 — 이번에 `grain_mend_detector.cpp` 가 "오케스트레이션은 있음"으로 적혀 있었지만
   실제로는 macOS 의 **브러시 경로**를 자동에 쓰고 있었습니다.
3. **창작 금지.** macOS 에 없는 것을 만들지 않고, macOS 에 있는 것을 빼지 않습니다. 화면은
   Swift 코드와 스크린샷 **양쪽**으로 확인합니다. 스크린샷에 없는 화면(검출 중 캡슐 등)은
   그 사실을 문서에 적고 코드만으로 옮깁니다.
4. **한 파일 500줄.** 넘으면 `docs/implementation/god-object-remediation.md` 에 사유를 적습니다.
5. **앱은 마지막에.** 개발 중 확인은 CLI 계측기와 단위 시험으로 합니다(05 문서).

## 2. 이번 세션에서 확정한 사실

측정 대상은 `OpticFilm8100_frame_4.tiff` (5088×3401), x64 Release, 10코어/16스레드/32GB.

### 2.1 시간

| | 처음 | 지금 | 목표 |
|---|---:|---:|---:|
| 디코드(TIFF+ICC) | 2,730 ms | 2,695 ms | — |
| 현상 | 770 ms | 770 ms | — |
| **검출** | **18,560 ms** | **8,932 ms** | — |
| **합계** | **22,059 ms** | **12,397 ms** | **5,000 ms** |

앱에서 처음 쟀을 때는 43,420 ms 였습니다(1800px 다운스케일 + 풀프레임 미세입자 재계산).

검출 8,932 ms 의 CPU 작업 내역(12타일 합계, 4워커):

| 단계 | CPU 합계 | 비중 |
|---|---:|---:|
| 먼지 형태학 | 14,990 ms | 47% |
| 미세 입자 | 11,135 ms | 35% |
| 스크래치 각도 | 2,058 ms | 6% |
| 검출 이미지 생성 | 840 ms | 3% |
| 증거 조립 | 602 ms | 2% |
| 봉합 + 성분 | 115 ms | <1% |

**형태학(`opening`/`closing`) 하나가 검출 작업의 82% 입니다.** 먼지와 미세 입자가 같은
원시연산을 씁니다.

### 2.2 품질 — 정답지가 생겼습니다

같은 사진 자동 검출:

| 분류 | macOS | Windows | 차이 |
|---|---:|---:|---:|
| 먼지 | 13 | 0 | −13 |
| 핀홀 | 2 | 0 | −2 |
| 가로 스크래치 | 5 | 3 | −2 |
| 세로 스크래치 | 10 | 11 | +1 |
| 대각 스크래치 | 0 | 1 | +1 |
| **미세 입자** | **197** | **0** | **−197** |
| **합계** | **227** | **15** | **−212** |

**macOS 에서도 오검출이 많습니다**(사용자 확인). 목표는 "오검출 0" 이 아니라 **macOS 와 같은
것을 고르는 것**입니다.

다른 프레임의 macOS 기준값(합계): frame_2 **1,720** · frame_3 **623** · frame_5 **647** ·
frame_7 **956**. 미세 입자가 어느 프레임에서나 **76~91%** 를 차지합니다. 전체 표는
[06-detection-reference.md](06-detection-reference.md).

읽는 법: 스크래치는 자릿수가 맞습니다. 죽어 있는 것은 **먼지·핀홀 경로**와 **미세 입자**
입니다. 미세 입자는 CPU 11초를 쓰고도 성분을 0개 냅니다 — 마스크에만 더하고 컴포넌트로
승격하지 않기 때문입니다. **가장 비싼 단계가 화면에 아무 기여도 못 하고 있습니다.**

## 3. 작업 순서

각 단계는 **끝나야 다음으로 갑니다.** 앞 단계가 뒤 단계의 측정 기준을 바꾸기 때문입니다.

### 1단계 — 검출 품질 (01 문서)
먼지를 못 잡는 것이 가장 큰 결함입니다. 화면이 아무리 macOS 와 같아도 검출이 틀리면
쓸모가 없습니다. `DefectContrastField`·`DefectDustDetector`·`DefectScratchDetector`·
`DefectComponentMask.buildLabeled` 를 파일 단위로 대조해 빠진 것을 전부 채웁니다.

### 2단계 — 속도 (02 문서)
품질이 맞은 다음에 잽니다. 품질 이식이 연산을 더하면 지금 숫자가 무의미해집니다.
CPU 쪽 낭비를 먼저 걷어내고(버퍼 재사용·중복 패스 제거), 그래도 5초를 못 맞추면
**D3D11 컴퓨트 셰이더**로 형태학을 옮깁니다.

### 3단계 — GrainMend 화면 (03 문서)
캡슐 디자인 수정, 브러시 컨트롤 바, 복제 도장 오버레이, undo 스택.

### 4단계 — 세 뷰 전체 화면 (04 문서)
라이브러리/현상/인화의 좌측 세로 레일·좌측 패널·상단·중앙·하단·우측 인스펙터.

### 5단계 — computer-use 검증 (05 문서)
전부 끝난 뒤에 앱을 띄워 실제 클릭으로 확인합니다.

## 4. 완료 기준

| 항목 | 기준 |
|---|---|
| 검출 품질 | 같은 프레임에서 먼지·핀홀이 실제로 나오고, 전봇대 같은 직선 구조물이 안 잡힘 |

| God object | 모든 새 파일 500줄 이하 |
| 시험 | 로컬 게이트 통과, 경고 0 |

## 5. 주의 (이번 세션에서 배운 것)

- **앱 인스턴스를 여럿 띄우지 마십시오.** 같은 카탈로그를 두 프로세스가 잡으면 라이브러리가
  0장으로 보입니다. 이번에 `open_application` 을 반복해 3개가 떠서 그렇게 됐고, 하나만 남기니
  바로 복구됐습니다. 데이터는 안전했습니다.
- **`--defect-tools` 를 앱이 켜진 채로 프로덕션 저장소에 대고 돌리지 마십시오.**
- **MSBuild 가 네이티브 오브젝트를 낡은 채로 붙듭니다.** 시그니처를 바꾼 뒤 링크 에러가 나면
  해당 `.obj` 를 지우거나 소스 타임스탬프를 갱신하십시오.
- 커밋 메시지에 줄 수를 적기 전에 `wc -l` 로 먼저 재십시오.
