## 3. 측정 방법

```bash
negaflow-cli --grain-mend-detect "<source.tiff>" <dmin-r> <dmin-g> <dmin-b> [sensitivity] [guided]
```

다섯 장 한 번에:

```powershell
$cli = "out\build\native\x64-release\Release\negaflow-cli.exe"
$dir = "C:\Users\habin\OneDrive\바탕 화면\negaflow_test"
foreach ($n in 2,3,4,5,7) {
  $src = Join-Path $dir "OpticFilm8100_frame_$n.tiff"
  Write-Host "frame_$n"
  & $cli --grain-mend-detect $src 0.42 0.30 0.22 1.0
}
```

### 3.1 주의 — 검출 입력은 cleaned raw 다

macOS `AppModel.runRegionDetect` 는 `cleanedRawImage`(현상 전 선형 스캔)에서
`SoftwareDefectRemoval.detectComponents` 를 돌린다. dmin·반전·톤·필름룩은 검출 입력이
아니다. 예전 계측기의 `0.42 0.30 0.22` / `auto` dmin 은 호환용 인자일 뿐이며 지금은
쓰지 않는다(`input_domain: cleaned_raw`).

양화 뒤에서 검출하면 먼지 대비가 통째로 달라져 숫자가 맞을 수 없다.

### 3.2 민감도

macOS 자동의 기본은 슬라이더 최대(6.0) → 검출기 민감도 1.0 입니다
(`GrainMendSensitivity.defaultValue(automatic:)` = `automaticRange.upperBound`).
계측기의 기본 `sensitivity` 도 1.0 이라 같습니다.

### 3.3 미세 입자

macOS 자동은 `detectMicroSpecks` 가 켜져 있습니다(설정 기본값). 계측기도 켬 고정입니다.

### 3.4 앱이 지나는 길로 재기 (2026-08-19 추가)

계측기는 `imaging::detect_grain_mend` 를 **바로** 부릅니다. 앱은 그렇게 부르지 않고
`pipeline::develop_detect_grain_mend` 로 들어가 디코드 → 기존 recipe 적용을 지난 뒤 같은
검출에 닿습니다. 둘이 다르면 원인은 검출기가 아니라 그 **앞의 두 단계**입니다.

```bash
negaflow-cli --grain-mend-detect "<source.tiff>" auto 1.0 pipeline
```

`pipeline` 을 마지막 인자로 주면 앱과 같은 길로 한 번 돌고 같은 모양으로 냅니다
(`"path":"pipeline"`). 구현은 `src/Cli/commands/grain_mend_detect_pipeline.cpp`.

**frame_4 실측(2026-08-19):** 직접 호출·CPU(`NEGA_GPU=0`)·파이프라인 **세 경로가 성분
193개, 분류 13/2/5/9/0/0/164, 채택 4,658화소로 완전히 같습니다.** 앱이 검출기와 다른 것을
보고 있지 않다는 뜻이고, GPU 형태학·스크래치 각도도 CPU 와 비트 일치입니다.

### 3.5 개수만 보면 안 된다 — 면적도 함께 본다

`dump=<경로>` 로 성분별 좌표·bbox·면적을 CSV 로 받습니다. frame_4 자동:

| 분류 | 개수 | 총 면적 | 평균 면적 |
|---|---:|---:|---:|
| 먼지 | 13 | 79 px | **6.1 px** |
| 핀홀 | 2 | 2 px | 1.0 px |
| 미세입자 | 164 | 672 px | 4.1 px |
| 가로 스크래치 | 5 | 848 px | 169.6 px |
| 세로 스크래치 | 9 | 632 px | 70.2 px |

**1,730만 화소에서 "먼지" 13개의 총 면적이 79화소입니다.** 개수는 macOS 와 같은데 전부
6화소짜리이고, 뚱뚱한 먼지는 하나도 없습니다. 게이트 통계가 어디서 죽는지 말해 줍니다:

```
dust_components_collected : 13,711
dust_dropped_no_strong    : 13,580   ← 99.0%
dust_dropped_strong_fraction: 77
dust_kept                 : 34
```

뚱뚱한 먼지는 top-hat 이 덩어리 전체에 퍼져 **자기 국소평균(`noiseScale`)을 스스로
끌어올려** SNR 게이트를 못 넘습니다. macOS 의 구제 장치는 큰 이물 채널
(`largeDustMag` = luma − 반경 80 박스평균)인데, 그것은
`extendedDustScales: constrainedRegion` 이라 **자동에서는 꺼져 있습니다**
(`SoftwareDefectRemoval.swift:189`). Windows 도 같게 꺼 놨습니다.

같은 프레임을 가이드(부분 ROI)로 돌리면 그 채널이 켜지고 결과가 바뀝니다:

| 모드 | 성분 | 먼지 | 가로 | 세로 | 채택 화소 |
|---|---:|---:|---:|---:|---:|
| 자동 | 193 | 13 | 5 | 9 | 4,658 |
| 가이드 | 278 | 28 | 34 | **154** | **71,947** |

**따라서 "자동이 뚱뚱한 먼지를 못 잡는다"는 두 앱 공통의 알고리즘 성질입니다.**
macOS 쪽 성분 **면적**을 아직 못 재 봤으므로, 개수만 같고 면적이 다를 가능성은 남아
있습니다 — macOS 세션에서 같은 `dump=` 를 떠서 이 표와 맞대는 것이 다음 단계입니다.

## 4. 합격 기준

각 프레임에서 **분류별 개수가 macOS 의 ±20% 안**에 들 것. 미세 입자처럼 수백~수천 개인
분류는 개수 자체보다 **자릿수와 비중**이 맞아야 합니다.

절대 안 되는 것:

- 어떤 분류가 macOS 는 있는데 Windows 는 **0** (지금 먼지·핀홀·미세입자가 그렇습니다)
- 어떤 분류가 macOS 의 **3배 이상** (오검출 폭증)
