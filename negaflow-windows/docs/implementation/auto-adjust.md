# 자동 보정 (Auto Tone / Auto White Balance)

기준일: 2026-08-10

## 왜

도달 가능성 확인에서 나온 결과입니다. macOS `AutoAdjust` 는
`AppModel+AutoAdjust.swift` 에서 실제로 불리는 **사용자 기능**인데 Windows 에는 구현이 아예
없었습니다. `gamutSoftClip` 처럼 죽어 있는 코드가 아니라 진짜 공백입니다.

## 무엇

AI 가 아니라 고전 알고리즘입니다. 히스토그램 percentile 을 각 슬라이더의 **실제 전달함수로
역산**합니다. 그래서 `tone_mapping.cpp` 의 마스크·계수가 바뀌면 여기도 같이 움직여야 합니다.
(그 계수들이 macOS `basicTone` 커널과 일치한다는 것은
`../verification/2026-08-10-macos-kernel-audit.md` 에서 확인했습니다.)

**Auto Tone** — 노출 → 화이트/블랙 → 하이라이트/섀도 → 농도 → 대비 순서로, 앞 단계의 이동을
뒤 단계 percentile 예측에 반영합니다(순차 시뮬레이션).

- 노출은 **밝히는 방향만** 갑니다. 설경·하이키를 회색으로 끌어내리는 gray-world 실패를
  배제하기 위해서이고, 감광은 실질 클리핑(≥5%)의 복구 전용입니다.
- 하이라이트는 내리기만, 섀도는 올리기만 합니다(복구 전용).
- 블랙 상향 리프트는 `0.15` 로 캡합니다. 이미 깊은 검정을 목표점까지 끌어올리면 검정이
  씻겨 이미지가 들뜹니다.
- 블랙/섀도 포인트는 p02/p08 을 씁니다. 더 얇은 percentile 은 스캔 프레임 경계를 블랙
  포인트로 잡아 정상 이미지의 암부까지 찢습니다.

**Auto White Balance** — 근중립 부분집합의 linear 평균을 무채색으로 보내되, 부분 보정입니다.

- 측정 캐스트의 **85%만** 걷고 `±0.6` 으로 클램프합니다. 완전 중립화는 노을·숲처럼 한 색이
  지배하는 장면에서 반대 캐스트로 폭주합니다.
- 근중립 표본이 3% 미만이면 산술평균 대신 **Minkowski p=6**(Shades-of-Gray)로 폴백합니다.
- 채널비 오차가 1.5% 이하면 데드밴드로 건드리지 않습니다.

## Windows 쪽 입력

macOS 는 호출측이 슬라이더를 0 으로 리셋한 **중립 현상본**을 렌더해 그 통계를 넘깁니다.
Windows 도 같은 계약이고, 입력은 **미리보기 BGRA8 비트맵**입니다 — 이미 있는 경로를 그대로
씁니다. 200px 격자로 표본화하므로 17 MP 스캔에서도 즉시 끝납니다.

## 검증 (2026-08-10)

`native.auto_adjust` 가 고정한 것: 히스토그램 정규화, 어두운 프레임은 밝히고 밝지만 클리핑
아닌 프레임은 **절대 어둡게 하지 않음**, 진짜 클리핑에서만 감광, 하이라이트/섀도/바이브런스의
단방향성, 모든 값이 문서화된 범위 안, 중립 프레임 무보정, 따뜻한 캐스트의 부분 냉각(중립을
넘지 않음), 같은 입력의 결정성, 잘못된 버퍼 거부.

x64 Debug/Release 네이티브 CTest **59/59**.

## 아직 확인하지 않은 것 — 솔직히

실촬영 프레임 검사(`auto_adjust_real_scan`)는 **수동 Dmin 기본값의 중립 현상본**을 입력으로
줍니다. 그 현상본 자체가 제대로 된 그림이 아니라서 자동 보정이 **모든 값을 클램프까지**
밀어냅니다(노출 3, 대비 0.55, 섀도 0.8, 화이트 1, warmth/tint 0.6). 범위를 벗어나지 않는다는
것은 확인했지만, **자동 보정이 좋은 결과를 낸다는 증거는 아닙니다.**

제대로 확인하려면 잘 현상된 중립 프레임이 필요하고, 그건 Auto base 나 Film preset 으로
현상한 뒤에 해야 합니다. 다음 작업입니다.

macOS 와의 수치 비교도 아직입니다. 다운샘플 방식이 다르므로(macOS `CGContext` medium
보간, Windows 격자 표본) 통계가 완전히 같지는 않습니다. 알고리즘과 상수는 같습니다.

## ABI 와 셸 연결 (ABI v1 / 0.29)

`nf_auto_adjust_v1` 은 BGRA8 비트맵 하나를 받아 열 개의 값을 돌려줍니다. 요청 struct 를 새로
만들지 않았습니다 — 자동 보정은 현상 레시피를 소비하는 것이 아니라 **이미 렌더된 그림을 읽는**
분석 호출이고, 그 그림은 `nf_develop_preview_v22` 가 쓰는 버퍼와 같은 형식이기 때문입니다.
셸은 이미 그릴 줄 아는 미리보기를 그대로 넘깁니다.

관리 쪽 입구는 `NativeAutoAdjust.Compute` 이고, 셸 쪽은 `AutoAdjustCoordinator` 입니다.

**조정자가 지키는 것은 "무엇을 재는가" 입니다.** 톤과 warmth/tint 를 0 으로 되돌린 사본을
렌더해서 재고, 나온 값을 원래 frame 에 **대입**합니다. 현재 상태를 그대로 재면 이미 들어간
보정이 답에 섞여 버튼을 누를 때마다 결과가 흘러갑니다. 필름 base 와 나머지 recipe 는
건드리지 않습니다 — 자동 보정이 고치려는 것은 톤과 화이트밸런스이지 base 추정이 아닙니다.

거부와 예외도 성공과 같이 dispatcher 를 거쳐 돌아옵니다. 호출자가 경로마다 다른 규칙을
기억하지 않게 하기 위해서입니다.

검증: Interop `147 assertions`(ABI 0.29), Shell `325 assertions`. 셸 시험이 고정한 것은
중립화 대상(톤·warmth/tint 만, vibrance 와 base 는 보존), 대입 멱등성(두 번 적용해도 같은 값),
계산한 값이 전부 기록되는 것, 현상 불가 frame 이 엔진 호출 없이 거부되는 것입니다.

WinUI 버튼 연결은 UI 단계 작업입니다.
