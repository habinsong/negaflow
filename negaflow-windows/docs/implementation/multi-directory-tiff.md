# 다중 IFD TIFF — 전체 해상도 이미지 선택

기준일: 2026-08-10

## 왜

사용자의 실제 파일 중 Photoshop 이 내보낸 TIFF 가 `multiple_directories_unsupported` 로
거부됐습니다. 사진이 잘못된 것이 아니라 **디렉터리가 두 개**였을 뿐입니다.

```
IFD[0]  NewSubfileType=0  5100×3408  16-bit   ← 실제 사진
IFD[1]  NewSubfileType=1  1498×1001  16-bit   ← 축소 미리보기
```

Photoshop 과 대부분의 스캐너 소프트웨어가 이렇게 씁니다. "여러 디렉터리 = 지원 안 함" 은
너무 넓은 그물이었습니다.

## 규칙

`NewSubfileType`(태그 254)이 결정합니다.

| 비트 | 의미 | 취급 |
|---|---|---|
| 0 | 축소 해상도 페이지 | 동반 페이지 |
| 2 | 투명도 마스크 | 동반 페이지 |
| 태그 없음 | — | 전체 이미지 |

**정확히 하나**가 전체 이미지여야 합니다.

- 0개 — 파일에 동반 페이지밖에 없습니다. 거부.
- 2개 이상 — 다중 페이지 문서입니다. 어느 것이 "그 사진"인지는 **우리가 추측할 문제가
  아니므로** 계속 거부합니다. `multiple_directories_unsupported` 는 이 뜻으로 좁아졌습니다.

체인은 `max_directories`(기본 16)로 제한합니다. 스캔본은 이미지 하나에 동반 페이지 몇 개면
충분하고, 이 상한이 **자기 자신으로 되돌아오는 디렉터리 체인**도 함께 막습니다.

## 구현

`select_primary_directory` 가 **아무것도 파싱하기 전에** 체인을 돌며 각 디렉터리의 항목 수와
`NewSubfileType` 만 읽습니다. 축소 미리보기는 실제 이미지와 같은 태그를 갖고 있으므로, 먼저
고르지 않으면 probe 가 1500px 썸네일을 검증하고 그것을 스캔본이라고 보고하게 됩니다.

`TiffProbeInfo` 에 `directory_count`, `primary_directory_index`, `primary_ifd_offset` 이
추가됐습니다. `first_ifd_offset` 은 여전히 진짜 첫 디렉터리를 가리키며, 나머지 필드는 전부
**선택된 전체 이미지**만 설명합니다.

## 디코더 쪽에서 배운 것

처음에는 WIC 프레임 번호가 디렉터리 번호와 같다고 두고 `frame_count == directory_count` 를
요구했습니다. **틀렸습니다.** WIC 의 TIFF 디코더는 축소 해상도 페이지를 프레임으로 노출하지
않습니다 — 디렉터리 2개짜리 Photoshop 스캔이 프레임 1개로 도착합니다.

그래서 선택 기준을 **probe 가 정한 치수와 일치하는 프레임**으로 바꿨습니다. WIC 가 동반
페이지를 걸러 내든 아니든 성립하고, 일치하는 프레임이 여럿이면 모호하므로 거부합니다.
프레임 0을 그냥 믿는 구현이었다면 썸네일이 앞에 오는 파일에서 조용히 미리보기를 현상했을
것입니다.

## 검증 (2026-08-10)

**실제 사용자 파일.** 종전에 거부되던 `Untitled (4).tif`(5100×3408 16-bit + 1498×1001 미리보기)가
디코드 → 현상 → PNG16 게시까지 통과했습니다. 전체 해상도 `5100×3408` 로 나왔으므로 썸네일이
아니라 사진을 현상한 것이 맞고, 원본 SHA-256 은 그대로입니다.

`Untitled.tif` 는 8비트 파일이라 처음에는 `unsupported_tiff_layout` 이었고, 뒤이어 8비트 입력을
열면서 함께 통과했습니다 — 아래 "8비트 입력" 절을 보십시오.

**합성 회귀** (`native.tiff_probe`): 미리보기가 뒤에 오는 경우, **앞에 오는 경우**(프레임 0
가정이 깨지는 자리), 투명도 마스크 동반, 전체 이미지 2개 거부, 동반 페이지만 있는 파일 거부,
체인 상한 초과.

**단일 IFD 회귀.** 실제 OpticFilm 스캔 두 장의 현상 결과 PNG16 SHA-256 이 이 변경 전과
동일합니다(`1A4EB1A7DAF40D8B`, `2ED77091159AAC5F`). 순수 추가 변경입니다.

**게이트.** x64 Debug/Release 네이티브 57/57, Interop 139(ABI 0.28), Catalog 583, Shell 316,
경고 0·오류 0, ARM64 Release 네이티브·관리 교차 빌드 통과(실기 실행 아님).

## 8비트 입력

레이아웃 게이트가 채널당 16비트만 받고 있었습니다. 8비트도 받도록 넓혔고, 그 아래는 하나도
바꾸지 않았습니다 — WIC 가 이미 대상 형식(48bpp RGB / 64bpp RGBA)으로 변환하고 있었기
때문입니다.

**정확도를 잃지 않습니다.** WIC 는 8비트 표본을 바이트 복제로 넓힙니다(`v * 257`). working
변환이 65535로 나누므로 `v * 257 / 65535 == v / 255` 로 정확히 같습니다. 왼쪽 시프트 같은 다른
확대 규칙이었다면 모든 표본이 최대 1/256 만큼 어두워졌을 것입니다.

이것은 가정이 아니라 측정입니다. 실제 8비트 파일의 채널 최소·최대
`[3855, 2827, 0]` / `[41634, 33153, 26214]` 가 전부 257의 배수입니다(15·11·0 / 162·129·102).
합성 회귀 `native.wic_tiff_decode` 는 모든 픽셀이 `v * 257` 인지 확인합니다.

5104×3402 8비트 + 미리보기 IFD 파일이 현상·게시까지 통과하고 원본은 불변입니다.

## 남은 것

- SubIFD(태그 330)로 미리보기를 다는 파일은 아직 다루지 않습니다. 이번 코퍼스에는 없었습니다.
- 다중 페이지 문서에서 페이지를 고르는 UI. macOS 쪽 동작을 먼저 확인해야 합니다.
