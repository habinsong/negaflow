# 소프트 프루프 (Soft Proof)

기준일: 2026-08-10

## 왜

도달 가능성 확인에서 남아 있던 마지막 백엔드 공백입니다. macOS `SoftProof` 는
`DevelopFrameRenderer+Developed.swift` 의 표시 경로와 `PrintCanvasView` 에서 실제로 불리는
사용자 기능인데 Windows 에는 없었습니다.

## 무엇 — 그리고 무엇이 아닌지

**보기용 시뮬레이션입니다.** macOS 에서도 `renderDisplayCGImage` 안에서만 걸리고, 내보내기와
인화 패키지 렌더러는 이것을 부르지 않습니다. Windows 도 같습니다 — 그리고 **내보내기 진입점을
아예 만들지 않는 것**으로 이를 구조적으로 보장했습니다. `nf_develop_preview_v23` 에는 프루프
인자가 있고 `nf_develop_export_v22` 에는 없습니다. 인화물이 시뮬레이션을 담을 수 있는 경로가
존재하지 않습니다.

같은 이유로 프루프는 **현상 요청 struct 밖**에 있습니다. 레시피에 넣으면 언젠가 내보내기가
읽게 됩니다.

## 계산

macOS 와 같습니다.

- `wtpt`(용지 흰색)와 `bkpt`(잉크 검정)를 XYZType 태그에서 읽습니다.
- 각 성분을 D50 `(0.9642, 1.0, 0.8249)` 의 같은 성분으로 나눕니다. **색도 변환이 아니라 채널별
  비율**이고, macOS 가 하는 계산이 그것이므로 "더 올바른" XYZ→RGB 로 바꾸지 않았습니다.
- 흰색은 `1.2`, 검정은 `0.3` 에서 클램프합니다.
- `scale = max(0, white - black)`, `bias = black`. 잉크가 용지보다 어두우면 범위가 0 으로
  접힙니다 — 음수 scale 은 그림을 뒤집습니다.
- `paperAndBlackInk` 모드에서만 값이 바뀝니다. profile-only 는 보여주는 공간을 고르는 것이지
  값을 바꾸는 것이 아닙니다.

거는 자리도 같습니다: hue-safe 접기(`tone_safe_unit_rgb`) **다음**, sRGB 인코드 **전**. 프루프는
선형광에서의 affine 이고 인코드는 비선형이므로 순서를 바꾸면 다른 그림이 됩니다.

## macOS 와 다르게 한 한 가지 — 그리고 그 이유

macOS 는 프로파일을 **CGColorSpace 를 통해** 받습니다. `copyICCData()` 가 다시 직렬화해 주므로
`wtpt` 는 이미 D50 PCS 흰색입니다. Windows 는 **파일을 그대로 읽습니다.** 그리고 ICC v2
matrix/TRC 프로파일은 `wtpt` 에 보정되지 않은 매체 흰색을 넣어도 됩니다.

이 기계에 설치된 프로파일을 실제로 열어 확인한 결과:

| 프로파일 | 버전 | `wtpt` | 색소 합 |
|---|---|---|---|
| sRGB Color Space Profile.icm | 2.1 | **D65** (0.9505, 1.0, 1.0891) | (0.96428, 0.99997, 0.82509) |
| AdobeRGB1998.icc | 2.1 | **D65** | (0.96420, 1.0, 0.82491) |
| eciRGB_v2.icc | 2.4 | D50 | (0.96419, 1.0, 0.82491) |
| WideGamutRGB.icc | 2.1 | D50 | (0.96420, 1.0, 0.82491) |
| ISOcoated_v2_eci.icc | 2.4 | (0.84552, 0.87683, 0.74716) | 없음 (LUT) |

`wtpt` 를 곧이곧대로 쓰면 sRGB 를 프루프 목적지로 고르는 순간 파랑이 1.32 로 나와 `1.2` 까지
클램프됩니다 — **화면 전체가 파래집니다.** macOS 에서는 절대 일어나지 않는 일입니다.

그래서 **matrix/TRC RGB 프로파일에서는 색소 합에서 D50 상대 흰색을 얻습니다.** 색소는 정의상
PCS 흰색으로 합해지므로, D65 를 선언한 두 프로파일에서도 합은 D50 에서 2e-4 안쪽에 떨어집니다.
LUT 프로파일 — 실제 인쇄·프레스 프로파일은 전부 여기입니다 — 은 손대지 않으므로, 시뮬레이션을
의미 있게 만드는 측정된 용지 흰색은 그대로 살아남습니다.

**스냅 허용치 `1.0e-3`.** 색소 합은 프로파일 작성자가 반올림한 만큼만 D50 에 가깝습니다.
`1.000006` 짜리 scale 도 8 비트로 양자화될 때 픽셀 하나를 한 코드 움직입니다. 실측으로
eciRGB_v2 와 WideGamutRGB 가 실제로 1 코드씩 움직였습니다. 허용치는 보이는 것보다 두 자릿수
아래이고 관측된 재구성 오차보다 두 자릿수 위입니다. 실제 용지는 근처에도 오지 않습니다 — 여기
설치된 프레스 프로파일은 0.877 로 12% 떨어져 있습니다. 스냅은 세 채널을 **묶어서** 합니다:
두 채널만 중립인 용지는 진짜 용지입니다.

## 목적지 관문

`is_rgb_output_profile` — 유효한 RGB 프로파일이면서 **그 안으로 변환해 들어갈 수 있는** 태그를
가진 것만 통과합니다: matrix/TRC 여섯 태그 전부, 또는 `B2A0`. `A2B0` 만 있는 스캐너 입력
프로파일은 여기서 걸립니다. CMYK 프레스 프로파일도 걸립니다 — macOS `rgbOutputColorSpace` 도
`model == .rgb` 를 요구하므로 같은 결과입니다.

macOS 는 고르는 시점과 복원하는 시점이 같은 관문을 공유합니다. Windows 도 같은 판정 하나를
씁니다.

## 검증 (2026-08-10)

**`native.soft_proof`** — 설치된 프로파일의 헤더·태그 모양·흰색을 그대로 재현한 합성
프로파일로: D65 를 선언한 v2 표시 프로파일이 **정확히** 항등으로 풀리는 것, 프레스 프로파일의
측정된 용지가 정규화되지 **않는** 것, 허용치를 막 넘은 용지는 색조를 유지하는 것, 관문이
CMYK·입력 전용·손상된 프로파일을 거부하는 것, 클램프 상한, 잉크가 용지보다 어두울 때 범위가
0 으로 접히는 것. 설치된 실제 파일 3 개로도 같은 판정을 확인합니다.

**`native.develop_export_abi`** — 프루프를 끄는 **세 가지 방법**(null, disabled,
profile-only)이 전부 v22 미리보기를 **바이트 단위로** 재현하는 것. 용지·잉크를 켰을 때 그림이
바뀌는 것, 그리고 **인화물은 용지보다 밝을 수 없고 잉크보다 어두울 수 없다**는 두 경계.
경계가 헛돌지 않도록, 프루프 없는 프레임이 실제로 그 밖까지 간다는 것을 먼저 확인합니다.

**실촬영 프레임** — 설치된 RGB 출력 프로파일 4 개(sRGB, Adobe RGB, eciRGB v2, Wide Gamut)를
목적지로 실제 네거티브를 렌더한 결과가 프루프 없는 렌더와 **전부 바이트 단위로 동일**합니다.
이것이 parity 주장입니다: Windows 사용자가 실제로 가진 프로파일은 macOS 내장 프로파일과 같은
결과 — 아무 변화 없음 — 를 냅니다.

**비용** (x64 Release, 실촬영 프레임, 512px 미리보기): 프루프 없음 82.4 ms, 프루프 82.1 ~
83.8 ms. 한 번은 프루프 쪽이 더 빨랐습니다. affine 은 실행 간 잡음 안에 있습니다.

그래서 프루프가 꺼져 있어도 **분기 없이 그냥 계산합니다.** scale 1, bias 0 은 부동소수점에서
정확한 항등이므로 결과가 같다는 것이 증명되고, 갈라질 수 있는 두 번째 경로가 생기지 않습니다.

**게이트**: 네이티브 CTest 60/60 (x64 Debug/Release), Interop `155 assertions` (ABI 0.30),
Catalog 583, Shell 329, 경고 0.

## 아직 안 한 것 — 솔직히

**목적지 색공간 변환은 아직입니다.** macOS 는 `createCGImage(colorSpace: proofColorSpace)` 로
표시 이미지를 프루프 공간에 넣고, 화면에 나올 때 컴포지터가 다시 변환합니다. 즉 프린터 gamut
밖의 색이 잘리는 것이 보입니다. Windows 에서 같은 결과를 내려면 mscms 로
sRGB → 목적지 → sRGB 왕복을 돌려야 하고, 그것은 아직 없습니다.

지금 구현한 것은 **용지 흰색과 잉크 검정 시뮬레이션**뿐입니다. 사용자에게는 "종이가 화면보다
어둡고 약간 색이 있다" 는 부분이 보이고, "이 색은 이 프린터가 못 낸다" 는 부분은 아직
안 보입니다.

**`DestinationGamutWarning` 도 아직입니다.** macOS 는 ColorSync gamut-check transform 으로
재현 불가능한 픽셀을 판정해 빨간 오버레이(알파 166)를 만듭니다. Windows 대응은 mscms
`CheckBitmapBits` 이고, 채널 클리핑으로 근사하지 않는다는 macOS 의 원칙이 그대로 적용됩니다.
다음 작업입니다.

**UI 연결도 UI 단계 작업입니다.** 셸 쪽 입구는 `PreviewCoordinator.SoftProof` 이고,
프로파일을 고를 때 `NativeSoftProof.ReadMedia` 를 한 번 부른 뒤 결과를 들고 있으면 됩니다 —
프레임마다 태그 테이블을 다시 돌 이유가 없습니다.
