## 0. 제1원칙 — 재고 나서 가장 큰 것부터

## 3. GPU 없이 오늘 할 수 있는 것

### 3.1 스레드 풀 — `parallel_rows.cpp` 가 호출마다 스레드를 만듭니다

```cpp
// src/Native/core/parallel_rows.cpp:113
workers[started] = std::thread(
    [function, context, block]() noexcept { … });
```

화소 단계마다, 타일마다 이것이 돕니다. 슬라이더를 끄는 동안에는 **초당 수십 번**입니다.

**할 것**: 영속 워커 풀 하나(장치 수명과 같이). 작업은 큐에 넣고 스레드는 살려 둡니다.
**주의**: 지금 코드는 스레드 생성 실패 시 인라인 실행으로 복구합니다(`catch (...)`).
**그 복구 경로를 없애지 마십시오** — 풀이 포화일 때 같은 역할을 합니다.

> ⚠️ **얼마나 빨라지는지는 재야 압니다.** 스레드 생성 비용은 Windows 에서 수십 µs 급이라
> 큰 이미지 한 장에는 묻히고, **작은 프록시를 초당 수십 번 돌릴 때** 드러납니다.
> **프록시 크기에서 재십시오.**

### 3.2 컴파일러 스위치 — 켤 수 있는 것을 안 켰습니다

`cmake/CompilerWarnings.cmake` 는 `/W4 /WX /permissive- /Zc:__cplusplus /Zc:preprocessor /utf-8`
**`/fp:precise`** `/sdl /guard:cf` 를 겁니다. **`/fp:precise` 는 이미 명시돼 있습니다.**
없는 것은 **`/arch:` · `/GL` · `/LTCG`** 셋입니다.

| 스위치 | 효과 | ☠️ 위험 |
|---|---|---|
| `/GL` + `/LTCG` | 링크 시 최적화. 인라인이 파일 경계를 넘음 | 낮음. 빌드 시간만 늘어남 |
| `/fp:fast` | 부동소수 재배열 허용 | **높음. 절대 그냥 켜지 마십시오** — 골든값이 바뀝니다 |
| `/fp:precise` | **이미 켜져 있음**(`cmake/CompilerWarnings.cmake:12`). 유지할 것 | — |
| `/arch:AVX2` | 벡터 명령 + **FMA 축약** | **중간~높음.** FMA 로 반올림이 달라져 골든이 흔들릴 수 있음 |

**규칙: 스위치를 켤 때마다 골든 시험(`2026-08-16-macos-pixel-golden.md`)과 실측 17장 dmin 을 돌리십시오.**
바이트가 바뀌면 **그 스위치는 성능이 아니라 품질 변경**입니다. 값이 바뀌었는데 "빨라졌다" 고
보고하면 그게 구라입니다.

`/GL`+`/LTCG` 부터 하십시오 — **값을 안 바꾸면서 얻는 것**입니다.

### 3.3 SIMD — 화소 커널에 하나도 없습니다

지금 SIMD 는 `flatbed_frame_grid_fit.cpp` · `flatbed_frame_grid_types.h` ·
`flatbed_frame_profiles.cpp` **3파일뿐**입니다. 톤·커브·믹서·그레이딩·반전은 전부 스칼라입니다.

**그런데 이것들은 [`04`](04-gpu-plan.md) 의 GPU 이식 대상과 정확히 같습니다.**

**판단: GPU 가 먼저입니다.** 같은 커널을 SIMD 로 한 번, HLSL 로 또 한 번 쓰는 것은 낭비이고,
**두 벌이 되면 서로 어긋납니다.** SIMD 는 **GPU 폴백 경로가 확정된 뒤**, GPU 없는 기계를 위해
넣으십시오. 그때는 이미 커널 수식이 HLSL 로 정리돼 있어 옮기기 쉽습니다.

### 3.4 메모리

- `ArrayPool` 히트 0이지만 **프리뷰 경로는 이미 선할당**(`PreviewCoordinator.cs:112`)이라 급하지 않습니다.
- 진짜 문제는 **네이티브 쪽 `WorkingImage` 복사**입니다. 단계 시그니처를 보면
  `apply_finish_stages(… WorkingImage grain_image …)` 처럼 **값으로 받는** 곳이 있습니다.
  24MP 면 한 번에 **384 MB 복사**입니다. **전부 열어서 값/참조를 확인하십시오.**
- 메모리 압력은 `CreateMemoryResourceNotification` 으로 감지합니다([`10`](10-cache-and-optimization.md) FIFO 캐시).

## 4. GPU 커널 작성 규칙 — [`04`](04-gpu-plan.md) 보완

04 는 **무엇을** 옮길지, 여기는 **어떻게** 씁니다.

### 4.1 스레드 그룹

| 규칙 | 값 | 근거 |
|---|---|---|
| 그룹 크기는 **64의 배수** | `[numthreads(8,8,1)]` = 64 부터 | 모든 벤더에서 무난. AMD wave64 · NVIDIA warp32 둘 다 나눠떨어짐 |
| D3D11 그룹당 최대 | **1024 스레드** | |
| `groupshared` 상한 | **32 KB / 그룹** (D3D 제한) | float4 로 2,048개 = 45×45 타일 정도 |

**주의**: 큰 그룹은 점유율(occupancy)을 떨어뜨릴 수 있습니다 — 레지스터·LDS 를 많이 먹으면
동시에 도는 그룹 수가 줄어듭니다. **8×8 로 시작해서 재고 올리십시오.**

### 4.2 분리형 컨볼루션 — 가우시안·박스

1. 수평 1D 패스 → 중간 텍스처 → 수직 1D 패스.
2. 각 패스에서 **커널 반경만큼 넓은 타일을 `groupshared` 에 미리 읽고**, 거기서 곱합니다.
   같은 화소를 반경 배로 다시 읽지 않게 됩니다.
3. 박스 필터는 **슬라이딩 윈도우로 화소당 O(1)** — 반경과 무관합니다.

### 4.3 형태학 — 반경과 무관한 O(1)

**먼지 형태학이 검출 CPU 의 47%, 미세 입자까지 82%** 입니다. 여기가 가장 큰 덩어리입니다.

**van Herk / Gil-Werman (vHGW)**: 구조 요소 크기와 **무관하게** 화소당 상수 시간
(비교 3n)으로 최소/최대를 구합니다. 침식·팽창은 **분리 가능**하므로 수평·수직 두 패스로 갑니다.
CUDA 구현 논문이 있고 원리는 API 무관이라 HLSL 로 옮길 수 있습니다.

**주의**: 45° 같은 사선 구조 요소는 별도 취급이 필요합니다.
**지금 `grain_mend_morphology.cpp` 가 어떤 구조 요소를 쓰는지 먼저 읽으십시오.**

### 4.4 가이드 필터 — 이미 O(1) 형태

macOS 커널 `gfProduct`·`gfCoeffA`·`gfCoeffB`·`gfApply` 4단은 **박스 필터 기반 가이드 필터**입니다.
가이드 필터는 **창 크기에 무관한 O(1)** 이 원 논문 성질이고, 박스 평균만 O(1)로 만들면 됩니다
(적분 영상 또는 4.2의 슬라이딩 윈도우).

**즉 4개 커널 자체는 화소별이고, 그 사이의 박스 평균만 우리가 만들면 됩니다.**

### 4.5 다운로드 — 여기서 멈춥니다

**D3D11 의 `Map` 은 동기화합니다.** 스테이징 텍스처를 `Map` 하면 GPU 가 밀린 작업을 끝낼 때까지
CPU 가 **멈춥니다.** (D3D12 와 다른 점입니다.)

**할 것: 스테이징 텍스처를 2장 이상 두고 돌려 씁니다.** N 프레임을 GPU 가 쓰는 동안
N−1 프레임을 CPU 가 읽습니다. 이렇게 안 하면 프리뷰가 매 프레임 GPU 를 기다립니다.

### 4.6 캐시 지역성

넓게 흩어져 읽는 패스(디노이저 같은 큰 커널)는 **스레드그룹 타일링**으로 L2 지역성을 올립니다.
그룹 ID 를 재배열해 인접 그룹이 인접 메모리를 보게 합니다.
**이건 마지막 손질입니다** — 4.1~4.5 부터 하십시오.

```metal
target += clamp(blacksAmount, -2.0, 2.0) * 0.06 * blackMask;
```

> ### ✅ 고쳤습니다 — 엔진부터 슬라이더까지 7곳

> 후자가 더 컸습니다 — ±1 을 넘기면 값이 잘리는 게 아니라
> `valid_working_tone_adjust_parameters` 가 **요청 전체를 거부하고 픽셀을 버렸습니다.**

> `basic_tone.hlsl` 같은 clamp → `nf_tone_limits_v1` 필드 추가(기존 패딩 자리라 오프셋·
> `struct_size` 안 바뀜) → `ToneLimits.ClampEndpointToneControl` → `DevelopToneEditor` →

>
> **교훈: 한 군데만 고치면 다음 데서 다시 막힙니다.** 엔진에서 화면까지 전 경로를 따라가십시오.

## 12. 이식이 잡아낸 CPU/GPU 의미 차이 — "변화 없음" 은 복사입니다

`colorMixerHSL` 을 옮기다 동치 시험이 잡은 것입니다. **셰이더 수식은 맞았는데 결과가 갈렸습니다.**

CPU 커널들은 매개변수가 하나도 안 움직였으면 **커널을 돌리지 않고 원본을 그대로 내보냅니다**:

```cpp
// imaging/color_mixer.cpp:227
if (!has_color_mixer_change(parameters)) {
    negaflow::core::copy_validated_rows(input, output);
```

GPU 가 그 경우에도 커널을 돌리면 HSL 왕복이 `clamp(rgb, 0, 1)` 을 지나며 **[0,1] 밖 값을 잘라 냅니다.**
작업 이미지는 그 범위 밖 값을 **일부러** 남기므로(하이라이트 여유·포화색) 실제로 갈립니다 —
**실측 최대 delta 0.1.**

`apply_color_grading`. `GpuWorkingImage::copy_from`(`CopyResource`)가 그 자리를 맡습니다.

**아직 안 본 것: 나머지 커널의 조기 반환.** 옮길 때마다 확인하십시오.

## 13. 상수 버퍼 배치가 틀리면 조용히 틀린 값이 들어옵니다

박스 블러를 붙이다 동치 시험이 잡은 것입니다. **셰이더 코드는 맞았는데 결과가 delta 0.38 로 갈렸습니다.**

C++ 쪽은 화소별 커널과 같은 `GpuPointwiseExtent`(16바이트 = `uint2` + `float2` 패딩)로 시작했는데,
HLSL `cbuffer` 에는 그 `float2` 패딩을 안 적었습니다:

```hlsl
cbuffer BoxBlurConstants : register(b0) {
    uint2 Extent;
    int Radius;      // ← C++ 에서는 오프셋 16, HLSL 에서는 오프셋 8
    float Padding0;
};
```

**컴파일도 되고 실행도 되고 경고도 없습니다.** 값만 틀립니다.

**규칙 — 상수 구조체를 만들 때마다:**

1. C++ 쪽에 `static_assert(sizeof(X) == N)` 를 답니다. 크기가 바뀌면 빌드가 멈춥니다.
2. HLSL 쪽 첫 16바이트는 **항상** `uint2 Extent; float2 Padding0;` 입니다.
3. `float3` 는 16바이트 경계를 넘지 못합니다. `float3` + `float` 는 한 레지스터에 들어가고,
   `float` + `float3` 도 들어갑니다(뒤 것이 오프셋 4에서 시작해 15에서 끝남).
4. **배열은 원소마다 16바이트**입니다. `float[64]` 는 1024바이트를 먹고 인덱싱도 어긋납니다 —
   `float4[16]` 으로 묶어 `[i>>2][i&3]` 로 읽으십시오.
5. **동치 시험 없이는 이 오류를 못 잡습니다.** 커널마다 시험을 같이 만드십시오.

## 14. 러닝 섬은 순서를 지켜야 값이 같습니다

박스 블러 CPU 판(`film_scan_denoise_filters.cpp` `box_blur`)은 슬라이딩 윈도우라 화소당 O(1)
이고, **부동소수 누적 순서가 결과에 남습니다.**

GPU 도 **행 하나에 스레드 하나**(1D 디스패치, `[numthreads(64,1,1)]`)를 두어 같은 순서로
누적했습니다. 결과는 **전 반경에서 비트 단위 일치(delta 0)** 입니다.

> ### ☠️ 2026-08-18 정정 — 같은 파일 안에 `box_blur` 가 **두 벌**이고 괄호가 다릅니다
>
> 위 문단은 처음에 **틀린 참조에 맞춘 것**이었습니다. 실제 CPU 는 이렇습니다:
>
> ```cpp
> // film_scan_denoise_filters.cpp:145  box_blur(std::vector<float>&)
> sum += source[add] - source[remove];         //  sum + (a - b)
> // film_scan_denoise_filters.cpp:203  box_blur(std::vector<Rgb>&)
> sum = sum + source[add] - source[remove];    // (sum + a) - b
> ```
>
> `Rgb` 의 `operator+`·`operator-` 가 각각 따로 도는 이항 연산이라 **왼쪽부터** 묶입니다.
> `guided_base` 는 둘을 섞어 씁니다 — guide·guide² 는 float 판, source·guide×source·a·b 는
> Rgb 판. GPU 는 네 스칼라를 한 `float4` 로 흘리며 한 순서만 썼고, 시험 참조는 **또 다른**
> 한 순서만 썼습니다. **둘 다 실제 CPU 와 달랐는데 서로는 맞아서 delta 0 으로 보고됐습니다.**
>
> 실측: 순서를 통일하면 가이드 필터 결과가 반경 1 에서 **3.8e-05** 까지 벌어집니다.
> 지금은 셰이더가 **채널마다** CPU 판을 따릅니다 — RGB 는 `(sum + a) - b`, 알파는
> `sum + (a - b)`.
>
> **교훈 둘:**
> 1. **함수 이름이 같다고 한 벌이 아닙니다.** 오버로드를 전부 열어 보십시오.
> 2. **시험되지 않는 경로는 틀려 있습니다.** `blur_alpha = true` 에 동치 시험이 없어서
>    이 오류가 커널 두 개를 지나 가이드 필터까지 갔습니다.

"반경만큼 다시 더하기" 로 바꾸면 화소당 O(r) 로 느려질 뿐 아니라 **누적 순서가 달라져 값도
갈립니다.** 화소별 커널의 8×8 그룹을 여기 그대로 쓰지 마십시오 — 러닝 섬은 줄 방향으로 순차적입니다.

## 15. 러닝 섬은 창 안만 보지 않습니다 — 누적 이력이 따라옵니다 (2026-08-18 실측)

14절의 연장이고, **타일을 나누는 이유를 바꿉니다.**

박스 블러는 슬라이딩 윈도우라 화소당 O(1) 이고 **수학적으로는 `[x-r, x+r]` 만** 봅니다.
그런데 `sum` 은 그 행의 **0번 화소부터 더해 온 값**이라, `x` 에서의 부동소수 오차에는
**0부터 x까지 전부의 반올림 이력**이 들어 있습니다.

CPU `apply_film_scan_denoise` 는 512px 타일마다 그 행의 0에서 러닝 섬을 새로 시작합니다.
GPU 가 전체를 한 번에 돌면 이미지의 0에서 시작합니다 — **같은 화소인데 이력이 다릅니다.**

| 어떻게 돌렸나 | CPU 와의 최대 오차 | 최악 화소 |
|---|---:|---|
| 폭 400(타일 하나) 전체 한 번에 | 1.2e-07 | — |
| 폭 600(경계 512 지남) 전체 한 번에 | **4.3e-05** | x=531·534·580 — **전부 경계 너머** |
| 폭 600, CPU 와 같은 512/18 타일 | **1.2e-07** | — |

에이프런 18 은 **필터 지원**으로는 충분합니다(가우시안 4 + 가이드 7 + 7). 모자란 것은
지원이 아니라 이력입니다.

**규칙: 러닝 섬을 쓰는 단계는 GPU 도 CPU 와 같은 타일로 나눕니다.** 타일 크기·에이프런·
시작 좌표를 CPU 에서 그대로 가져오십시오. 이것은 성능 선택이 아니라 값의 조건입니다.

> 부수 효과로 메모리도 풀립니다 — `film_scan_denoise` 사슬은 중간 텍스처가 13장이라
> 24MP 를 통째로 올리면 **5 GB** 인데, 530×530 타일이면 **58 MB** 입니다.

## 16. 초월함수는 CPU 와 마지막 비트가 같을 수 없습니다 (2026-08-18 실측)

D3D11 은 산술 넷(add·sub·mul·나머지)에 **0.5 ULP**(정확 반올림)를 요구하지만,
**역수/나눗셈은 1.0 ULP**, `log2`·`exp2` 는 **상대오차 2^-21**(≈4.8e-07) 까지 허용합니다.
HLSL `pow(x, y)` 는 `exp2(y * log2(x))` 이므로 그 둘의 합성입니다.

즉 `pow`·`exp`·`log` 는 `std::pow` 와 **같게 만들 방법이 표준 안에 없습니다.**
`precise` 도 `/Gis` 도 이것은 못 고칩니다 — 재배열이 아니라 함수의 정확도 규정입니다.

**차이 자체는 작습니다.** 감마 리프트 `pow(x, 0.45)` 의 실측은 **1 ulp(WARP 5.96e-08) ·
2 ulp(NVIDIA 1.19e-07)** 입니다. 문제는 **그 뒤에 무엇이 오느냐**입니다.

`film_scan_denoise` 는 뒤에 가이드 필터가 있고 그 안에 `1 / (variance + 0.001)` 이 있습니다.
`variance = mean(guide²) − mean(guide)²` 는 평탄한 곳에서 **자리수가 거의 다 상쇄**되므로,
1 ulp 가 결과에서 **2.1e-05 ~ 6.2e-05** 로 커집니다. macOS 도 같은 식이라 이것은
이식이 만든 문제가 아니라 **알고리즘의 조건수**입니다.

**규칙:**

1. 초월함수를 쓰는 커널은 **그 뒤 사슬의 조건수를 같이 봅니다.** 화소별 커널 하나로 끝나면
   1e-07 급이라 아무 문제가 없습니다(`digitalBWFilm` 4.8e-07).
2. 동치 시험을 **초월함수 있음/없음 두 갈래로** 돌리십시오. CPU 결과를 올려 넣고 나머지만
   재면 "이식이 틀렸나 `pow` 가 다른가" 가 한 번에 갈립니다.
   (`gpu_film_scan_tests` 의 `LiftSource::cpu` 가 그것입니다.)
3. 맞춰야 한다면 HLSL 에 **double-float 로 직접 쓰는 것** 말고 길이 없습니다. 큰 작업이고
   그 자체로 검증이 필요합니다. **하기 전에 정말 필요한지 재십시오.**

출처: [Floating-point rules — Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/direct3d11/floating-point-rules)

## 15. ☠️ 실측이 예상을 뒤집었습니다 — GPU 형태학이 **더 느렸습니다**

**이 문서 4.3절이 "형태학이 검출 CPU 의 82% 이니 여기부터" 라고 적었고, 커널은 비트 단위로
정확했습니다. 그런데 붙이고 재 보니 느려졌습니다.**

2026-08-18 실측. 5100×3408 실제 스캔, RTX 4060 Ti, `negaflow-cli --grain-mend-detect`:

| 검출 | 1회 | 2회 | 3회 |
|---|---:|---:|---:|
| **CPU** (`NEGA_GPU=0`) | **9,312 ms** | **9,104 ms** | 9,176 ms |
| GPU 형태학 | 12,146 ms | 11,462 ms | — |

**결과는 같습니다** — 성분 1,367개, 채택 16,074 화소. 비트 단위 일치는 지켜졌습니다.
**틀린 것은 값이 아니라 판단이었습니다.**

### 왜 느려졌나 — 커널이 아니라 구조

1. **평면마다 왕복합니다.** 검출은 타일 12개 × 반경 여러 개로 형태학을 수십 번 부르고,
   지금 이음매는 **호출마다 업로드·다운로드**를 합니다. 커널이 아무리 빨라도 전송이 지배합니다.
   — 이 문서가 3절에서 "단계마다 올렸다 내리면 집니다" 라고 적은 것과 **같은 함정**입니다.
   톤 단계에서는 지켰는데 여기서는 안 지켰습니다.
2. **직렬화됩니다.** D3D11 즉시 컨텍스트가 스레드 안전하지 않아 GPU 호출이 자물쇠 하나를
   지납니다. CPU 경로는 **워커 4개로 병렬**인데, GPU 로 바꾸면 그것이 **직렬**이 됩니다.

즉 **4중 병렬 CPU 작업을 직렬 GPU 작업 + 왕복으로 바꾼 것**이라 느려지는 것이 당연합니다.

### 무엇을 했나

**기본에서 껐습니다.** `NEGA_GPU_MORPHOLOGY=1` 로만 켭니다.
커널·시험·이음매는 그대로 둡니다 — 오케스트레이터가 서면 바로 쓸 수 있습니다.

**되돌린 것이 아니라, 재서 확정한 것을 그대로 반영한 것입니다.**

### 다음에 할 일

**검출 전체를 GPU 에 머무르게 하는 오케스트레이터.** 타일 하나를 올려서 형태학·스크래치·
미세 입자를 전부 GPU 에서 돌리고 마지막에 한 번 내립니다. 그러면 왕복이 타일당 1회가 되고,
직렬화도 타일 단위라 병렬성 손실이 줄어듭니다.

### 이 절이 남기는 규칙

> **커널이 정확하다고 빨라지는 것이 아닙니다.**
> 붙인 뒤 **반드시 재고**, 느려졌으면 **느려졌다고 적고 끄십시오.**
> 재지 않고 "GPU 를 붙였다" 고 보고하는 것이 이 문서가 처음부터 금지한 것입니다.

**측정 스위치** — 둘 다 릴리스에서 됩니다:

```bash
NEGA_GPU=0 negaflow-cli --grain-mend-detect <source> auto
```

```bash
NEGA_TIMING=1 negaflow-cli --grain-mend-detect <source> auto
```

## 17. `tone_adjust` 가 왜 덜 빨라지나 — 재서 갈랐습니다

16절이 *"`tone_adjust` 가 이제 최대(296 ms)인데 왜인지 아직 안 봤다"* 로 끝났습니다. 봤습니다.

### 4방향 실측 (5100×3408, RTX 4060 Ti, 3회 중 마지막)

| | develop(반전) | tone_adjust | 합계 |
|---|---:|---:|---:|
| CPU · 커브 켬 | 348.56 | 356.43 | 911.35 |
| CPU · 커브 끔 | 368.92 | 216.24 | 809.04 |
| **GPU · 커브 켬** | **261.49** | **296.88** | **782.59** |
| **GPU · 커브 끔** | **255.33** | **152.61** | **630.53** |

`negaflow-cli --develop-timing <source> <dmin-r> <dmin-g> <dmin-b> 3 [nocurve]`
(`NEGA_GPU=0` 으로 CPU 만.)

### 읽는 법

| 무엇 | 값 |
|---|---|
| 반전 GPU 이득 | 348.56 → 261.49 = **−25%** |
| 톤 GPU 이득 (커브 끔) | 216.24 → 152.61 = **−29%** |
| 톤 GPU 이득 (커브 켬) | 356.43 → 296.88 = **−17%** |
| **전체 GPU 이득** | 911.35 → 782.59 = **−14%** (커브 켬) · 809.04 → 630.53 = **−22%** (커브 끔) |
| **파라메트릭 커브 한 단계의 값** | CPU **+140 ms** · GPU **+144 ms** |

### 범인 — 다운로드가 아니라 **밴드 측정**입니다

처음에는 *"GPU 한가운데서 한 번 내리는 것"* 이 비싼 줄 알았습니다. **아닙니다.**
커브 한 단계가 CPU 에서 +140 ms, GPU 에서 +144 ms 로 **거의 같습니다.**
GPU 쪽 4 ms 차이가 다운로드이고, 나머지 140 ms 는 **양쪽이 똑같이 내는 CPU 측정 비용**입니다.

`measure_parametric_tone_curve_bands`(`tone_curve_measurement.cpp:120`)가 하는 일:

1. `validate_finite_pixels(image)` — **전 화소** 유한성 확인
2. `downsample_for_statistics` — **전 화소**를 읽어 작은 프록시로 축소
3. 프록시에서 백분위 — 여기는 작아서 쌉니다

**1과 2가 전 화소를 CPU 로 훑습니다.** 그래서 GPU 로 톤을 돌려도 이 단계에서 CPU 로
내려와야 하고, 그 비용은 CPU 경로와 같습니다.

### 다음에 할 일 (아직 안 함)

**축소를 GPU 에서 하고 작은 프록시만 내립니다.** 그러면 전 화소 CPU 패스 두 번이 사라집니다.

☠️ **다만 축소가 CPU 와 비트 단위로 같아야 합니다.** 백분위가 달라지면 밴드가 달라지고,
밴드가 달라지면 **출력 화소가 달라집니다.** 박스 블러에서 했던 것처럼 **연산 순서를 그대로**
옮겨야 하고, 시험으로 고정한 뒤에만 붙입니다.

유한성 확인도 GPU 로 옮길 수 있지만(리덕션), **실패를 화소 단위로 올리려면 UAV 카운터**가
필요합니다 — `negative_invert.hlsl` 헤더에 적힌 것과 같은 제약입니다.

## 18. 밴드 측정 — 제 앞 판정이 틀렸고, 재서 고쳤습니다

### ☠️ 먼저 정정: `GpuMipHalve` 는 톤 밴드와 상관이 없습니다

17절에서 밴드 측정의 두 패스를 *"`validate_finite_pixels` + `downsample_for_statistics`"*
라고 적었습니다. **뒤엣것이 틀렸습니다.**

`measure_parametric_tone_curve_bands`(`tone_curve_measurement.cpp`)는
`downsample_for_statistics` 를 **부르지 않습니다**(히트 0). 대신 `sampled_luma` 로
**전 화소를 `double` 면적평균**으로 직접 훑습니다.

`downsample_for_statistics` 의 실제 사용처는 셋입니다 — `film_base_sampling.cpp`(자동 베이스
표본 격자) · `manual_negative_developer.cpp`(`scene_density_range`, 자동 Dmax) ·
`muted_scene_vibrance.cpp`. **`GpuMipHalve` 는 그쪽에 쓸 원시연산이고, 비트 단위 일치는
그대로 유효합니다**(아래 표). 다만 톤 밴드를 빠르게 하지는 않습니다.

**교훈: 파일명과 이름으로 짐작하지 말고 함수 안을 읽으십시오.** 이 문서가 처음부터
적은 규칙인데 제가 어겼습니다.

### `GpuMipHalve` — 비트 단위 일치 (유효함)

| 시험 | WARP | NVIDIA |
|---|---|---|
| 64×48 → 32×24 | **완전 일치** | **완전 일치** |
| 61×37 → 30×18 (홀수 변) | **완전 일치** | **완전 일치** |
| 5×3 → 2×1 | **완전 일치** | **완전 일치** |
| 1×9 → 1×4 (한 변이 1) | **완전 일치** | **완전 일치** |

허용 오차가 아니라 완전 일치를 봅니다 — 이 값이 백분위로 가므로 마지막 비트가 달라지면
출력 화소가 달라집니다. 가능한 이유는 `halve` 가 float32 덧셈 셋과 `* 0.25` 뿐이라서입니다
(`precise` 로 재배열 고정).

**최종 이중선형과 면적평균은 옮길 수 없습니다** — 둘 다 `double` 이고 D3D11 의 double 은
선택 기능이라 벤더에 따라 없습니다. 큰 축소만 GPU 가 하고 작아진 뒤는 CPU 가 그대로 합니다.

### 그래서 톤 밴드에서 실제로 뺀 것 — 유한성 확인

남은 한 패스는 옮길 수 있었습니다. `GpuFiniteCheck` 를 만들었습니다:
컴퓨트 한 번 + `InterlockedOr` 원자 플래그 + **4바이트 회수**.

`measure_parametric_tone_curve_bands` 에 `pixels_already_finite` 를 더해, GPU 경로는
그 확인을 GPU 에서 하고 CPU 패스를 건너뜁니다.

☠️ **플래그가 서면(비유한 화소가 있으면) CPU 판을 그대로 부릅니다.** GPU 는 "있다/없다" 만
말하고, **어느 행이 처음 실패했는지는 CPU 판만 압니다.** 실패는 드물고, 드문 쪽에 비용을
몰아주는 것이 맞습니다. 레이아웃 확인은 이 값과 무관하게 언제나 합니다.

### 실측 (5100×3408, RTX 4060 Ti, 커브 켬)

| | develop | tone_adjust | 합계 |
|---|---:|---:|---:|
| CPU | 348.56 | 356.43 | 911.35 |
| GPU (반전까지) | 261.49 | 296.88 | 782.59 |
| **GPU (유한성 확인까지)** | **256.49** | **257.95** | **735.20** |

**tone_adjust −13%(296.88 → 257.95), 전체 −6%(782.59 → 735.20).**
CPU 기준으로는 **−19%**(911.35 → 735.20).

native 83/83 통과 — 골든·내보내기 포함.

### 남은 것

`sampled_luma` 의 `double` 면적평균이 그대로 남습니다. **옮길 수 없습니다** — 위에 적은
이유 그대로입니다. 줄이려면 CPU 쪽을 병렬화하는 편이 현실적입니다
(`for_each_row_block` 는 이미 있습니다). **아직 안 했습니다.**

## 19. 병렬화가 더 느렸습니다 — 되돌렸고, 3.1절의 스레드 풀이 왜 먼저인지 증명됐습니다

### 왜

표본 격자가 **256×171 정도**입니다. 나눌 일이 적은데
`core/parallel_rows.cpp:113` 이 **호출마다 `std::thread` 를 새로 만듭니다.**
