# ADR-0023: CMS 일치 여부는 합성 프로파일 기준값으로 판정한다

- 상태: 채택
- 날짜: 2026-08-06

## 문제

Windows 네이티브 엔진은 임베디드 ICC → working 변환을 OS 색상 API(ICM/mscms)로 합니다
(`src/Native/imaging/icm_icc_converter.cpp`). ADR-0004 가 정한 "네이티브 엔진 제3자 런타임 의존성
0개"가 이 선택에 걸려 있습니다. ICM 이 macOS ColorSync 와 다른 숫자를 내면 두 플랫폼이 같은 파일에서
다른 사진을 만들고, 그때는 LittleCMS 를 들여야 합니다.

파이프라인을 더 쌓기 전에 답이 필요합니다. 그런데 판정에 쓸 공통 기준이 없었습니다.

- 실제 스캐너 벤더 ICC 프로파일은 저장소에 넣을 수 없습니다. 권리 문제가 있고
  `scripts/ci/verify-provenance.py` 게이트에 걸립니다.
- 프로파일이 없으면 "두 CMS 가 다르다"는 관찰이 CMS 차이인지 서로 다른 입력 때문인지 분리되지
  않습니다.

## 결정

CMS 일치 판정은 **저장소 안에서 코드로 합성한 matrix/TRC 프로파일 하나와 고정 패치 세트**로만
합니다. macOS 가 기준값을 방출하고 Windows 가 같은 입력으로 대조합니다.

- 프로파일: sRGB 프라이머리를 Bradford 로 D50 적응한 matrix/TRC 입력 프로파일, TRC 는 `curv`
  감마 하나(563/256 = 2.19921875). 규칙은 `Negaflow.Windows/docs/research/colorsync-icm-parity-profile.md` 가
  규범이고 SHA-256 으로 고정합니다.
- 패치: 34개. 근암부 0.000/0.005/0.010/0.020/0.050, 뉴트럴 램프 8단, R/G/B/C/M/Y 의 full 과
  50% 채도, 스킨톤 3, 하이라이트 숄더와 유채색 암부.
- 기준값: `colorsync-icm-parity-v1` JSON. macOS 는 제품 가져오기 경로
  (`CIImage(cgImage:)` + `ChromabaseEngine.sharedLinearRenderContext`)로 방출합니다. 별도 변환
  코드를 쓰지 않습니다. 별도 경로로 재면 제품이 아니라 테스트 하네스를 측정하게 됩니다.

matrix/TRC 를 고른 이유는 A2B/B2A LUT 이 없어 CMS 가 쓸 수 있는 경로가 행렬 1개와 곡선 3개로
좁혀지기 때문입니다. 게다가 프라이머리를 sRGB 와 같게 두면 행렬이 상쇄되어 **TRC 만 남습니다.**
차이가 나면 어디서 났는지 특정됩니다.

## 측정 결과 (macOS 쪽만)

ColorSync 는 순수 거듭제곱을 그대로 쓰지 않습니다. device 값 약 0.099 아래에서 곡선을 **기울기
1/16 인 직선**으로 대체합니다. `in = 0.005` 에서 측정값은 `in^2.19921875` 의 약 36배입니다.

이것이 렌더 경로의 부작용이 아님을 분리 확인했습니다. working format 을 `RGBAh`(제품 기본값)와
`RGBAf` 로 각각 렌더한 결과가 동일했고, Core Image 를 우회한 `CGColor` 변환도 같은 값을 냈습니다.
ColorSync 자체의 곡선 평가입니다.

## 검증

- `swift test` 전체 통과.
- `bash scripts/ci/verify-static.sh` 통과.
- emitter 를 환경변수를 준 상태로 실행해 JSON 34패치를 방출.

**Windows ICM 쪽은 측정하지 않았습니다.** 작업 환경이 macOS 라 네이티브 코드를 빌드·실행할 수
없습니다. 이 ADR 은 일치 여부를 판정하지 않고, 판정 방법과 기준값을 고정합니다.

## 결과

- ICM 비교가 재현 가능한 단일 기준을 갖습니다. 프로파일 바이트가 SHA-256 으로 고정돼 있어
  "서로 다른 프로파일을 읽고 있었다"는 실패 양상이 먼저 걸러집니다.
- ColorSync 의 암부 하한이 문서화된 수치로 남습니다. 이후 어떤 불일치를 보든 이 값과 먼저
  대조하게 됩니다.
- ADR-0004 의 의존성 0개 기준은 아직 유효합니다. 근암부가 갈리더라도 ICM 에 넘기는 곡선을 같은
  하한으로 리라이트하는 선택지가 먼저이고, 그것은 우리 코드 안에서 끝납니다.

## 되돌리는 조건

Windows 측정에서 근암부가 갈리고, 곡선 리라이트로도 맞출 수 없으며, 그 구간이 실제 필름 스캔
결과에 유의미하게 기여한다는 것이 확인되면 ADR-0004 를 다시 엽니다. 세 조건이 모두 성립할 때만
제3자 CMS 도입을 논의합니다.
